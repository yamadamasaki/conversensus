# template/types のテスト仕様

## 何を

`TemplateSchema` の検査を見る。型定義そのもの (`NodeKind` / `EdgeKind` の形) は自明なので
テストしない。テストするのは **`superRefine` に書いた検査**、すなわち型では言えない部分である。

## なぜ

`EdgeKind.from` / `to` は `NodeKind.id` を指すが、**型は「文字列の配列」としか言えない**。
綴り違いは型検査を通り、実行時に「その接続規則が誰にも当たらない」という静かな失敗になる。
黙って効かない規則は、警告が出ないことと区別がつかない。

step2 で書く template は手書きの表 1 つだけなので、間違えるとしたらここである。
そして template がユーザ定義になる step3 では、この検査がそのまま入力の検証になる。

## どのように

`safeParse` の **issue の `path`** を見る。「落ちること」だけでは足りない — どこが悪いかを
言えない検査は直せないし、種別の一覧が長くなるほど場所が要る。

- **`from` / `to` の未定義参照**: 両側とも見ることを固定する。片側だけ検査する実装は
  ありがちで、しかも `to` 側の抜けは「逆向きの接続だけ警告されない」という気付きにくい形で出る。
- **id の重複**: node 側・edge 側それぞれ。重複すると `find` が先勝ちになり、後に書いた
  定義が黙って無視される。**template を書いた人の意図と画面が食い違う**唯一の形なので落とす。
- **`label` が空でない**: 空の種別名はメニューに出せず、`node.setLabel` の値としても
  照合できない。**この制約が `isConnectionAllowed` の D5 を成立させている** —
  空の label がどの種別とも一致しないからこそ、「種別が空なら警告しない」を別扱いせずに
  書ける (`fold.test.md` を見よ)。ここを緩めると向こうが壊れる。
- **`from` / `to` が空でない**: 端点の無い接続規則は、どの接続にも当たらない。
  上の「黙って効かない規則」の一種である。
- **種別を持たない template は受理する**: 空の語彙は誤りではない (名前だけの template を
  作って後から足す道を塞がない)。**何を落とさないか**も検査の一部である。
