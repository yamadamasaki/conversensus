# template/fold のテスト仕様

## 何を

適用された template から **選べる種別の一覧** (`nodeKindsOf` / `edgeKindsOf`) と
**接続してよいか** (`isConnectionAllowed`) を出す畳み込みを見る。

## なぜ

`templateIds` は複数を許す。**当面は toulmin 1 つしか当てないが、畳み方を後から決めると
「1 つのときだけ通る実装」が固定される** (設計 §4)。したがってこのテストの主題は
toulmin が正しく引けることではなく、**複数のときの畳み方**である。

もう一つの主題は **`false` の意味**である。接続の警告は拒否をしない (設計 D5) ので、
`false` は「違反が確定した」だけを意味しなければならない。決まらないものを警告に上げると、
既存グラフに template を当てる途中が警告だらけになり、警告そのものが読まれなくなる。

## どのように

### toulmin の内容

spec の表 (5 種別 / 5 接続) をそのまま固定する。**順序込みで見る**のは、これがメニューの
並びになるからである。

### 接続の判定 — 3 値であること

実装は各 template を `allowed` / `violation` / `undetermined` の 3 値で判定し、
**「許すものが在れば許す、無くて違反が在れば警告、あとは許す」**の順に畳む。

- **規則どおりなら許す / 向きが逆なら違反 / 組み合わせが規則に無ければ違反**:
  `from` と `to` が非対称であることを含めて、素の判定を固定する。
- **決まらない場合は許す** (D5): template 無し・種別が空・語彙に無い種別名 (孤児)。
  孤児は設計 §7 の既知の穴 (template 側で種別名を変えると起こる) で、**穴が
  「警告が出ない」側に倒れている**ことをここで固定する。逆に倒れると、改名の直後に
  グラフ全体が警告になる。
- **空文字列は「無い」と同じ**: 空の種別名は `TemplateSchema` が禁じているので、
  空はどの種別とも一致しない。**この一致が D5 を別扱いなしに成立させている** —
  「未設定」と「知らない名前」は判定の上で同じ *語彙に無い* である。両者を別の分岐で
  書いた版も試したが、**どのテストでも区別できない枝**になったので落とした。

### 複数 template の畳み方 — 素朴な「和」が 2 度誤っていた

以下 2 件は**性質が見つけた反例を例として残したもの**である (乱数が毎回そこを引く保証は無い)。

- **template を当てていない状態から当てると許容は減る**: 空は「和の単位元」ではなく
  **「規則が無い = 全部許す」**である。したがって「template を足すと許容が減らない」は
  空を含めた形では成り立たない。ここに気付かずに単調性を課すと、実装を歪めることになる。
- **語彙を知らない template を足しても既存の警告は消えない**: `undetermined` を「許す」と
  数えると (`some(v !== 'violation')`)、**関係のない template を足すだけで警告が全部消える**。
  和を取るのは**規則**であって許容ではない。

その上で、和の意味を残る 2 方向から固定する。

- **片方が許していれば許す**: 一方が違反と言っても警告しない (設計 §4)。
- **同じ id は先に来た方を残す**: 種別の一覧は和だが、並びは安定していなければ
  メニューが揺れる。

## 性質 (fast-check)

「あらゆる template の組・あらゆる接続について」の主張なので、例ではなく性質で書く。

- **語彙を持たない template を足しても結果は変わらない**: `undetermined` の意味そのもの。
  上の誤り (`some(v !== 'violation')`) を直接に否定する **唯一の一般命題**である。
- **許す template を足せば許される**: 和のもう一方の向き。
- **種別の一覧は足して減らない**: こちらは本当に単調である (接続の可否と違い、
  語彙は足す一方なので)。**同じ「和」でも、一覧と可否で性質が違う**ことを言っている。
- **冪等**: 同じ template を重ねても変わらない。`templateIds` に重複が入り得る
  (step3 で編集を許すとき) 前提を先に固定しておく。
- **順序非依存**: 可否は並び順に依存しない (一覧は依存する — 上の「先勝ち」)。

**単調性 (「足すと許容が減らない」) は意図的に課していない。** 課すと、上記の誤った実装
しか通らなくなる。**課さなかった性質は、課した性質と同じだけ設計を述べている。**

### 生成器

**小さなプールから引く。** label を広い文字列生成器で引くと template の語彙に当たらず、
`undetermined` ばかりを引いて **`violation` の道を一度も通らない** — 単調性まわりの
性質が「決まらないものは足しても決まらない」を確かめただけになる。

プールは toulmin の語彙 + 語彙に無い名前 + 空文字 + `undefined` を混ぜてある。
template の母集団も 2 つに絞ってあり、**同じ template を 2 度引くこと**(冪等の確認) が
実際に起こるようにしている。

## 対象外

- **プロパティの定義** (`EdgeKind.properties`) は宣言だけで、食う画面が無い (設計 事実 D)。
  Phase 4 の property editor が入るまで検証しようがない。
- **2 つの template が同じ label の種別を定義したとき**。いまは「label で種別を決める」
  形なので破れるが、1 つしか当てない間は起こらない → step3 (設計 §7)。
