# properties.test.ts — プロパティのキー単位の変更のテスト仕様

## 何を

`properties.ts` の `diffProperties` (置換の意味論 → キー単位の変更の列) と `applyPropertyChange` / `applyPropertyChanges` (変更を properties に当てる) を検証する。

## なぜ

このモジュールは **「置換の意味論」と「キー単位の意味論」の変換点**である (#208)。

properties を全体で置換していると、A が `foo` を B が `bar` を編集しただけで競合と判定され、しかも負けた側のプロパティが丸ごと消える。ユーザから見ると「触ってもいないプロパティが消える」(`deepse/requirements/spec/merging.md` の「op の粒度」)。

同時に、client の `NODE_PROPERTIES_CHANGED` は from/to に**置き換え後の全体**を載せる契約のままである。その全体を差分に割るのがここで、**op へ落とす経路 (`toUnified`) とローカル reducer (`applyEvent`) の両方が同じ関数を通る**ことで、画面の状態と op-log の projection がずれないことを担保している (レビュー R4 で揃えた不変条件)。したがってこの変換の正確さが二重に効く。

## どのように

### diffProperties

- **追加 / 変更 / 削除**: `to` にだけあるものは値つきの変更、値が変わったものだけを拾う、`to` から消えたものは **値を省いた変更 (= 削除)** になることを確認する。値の省略が削除を意味するのは JSON に `undefined` が載らないためで、この対応が op の意味論そのものである。
- **値の比較は構造で行う**: `image` プロパティのように値がオブジェクトの場合でも、中身が同じなら変更として拾わない。参照比較だと画像を触っていない編集のたびに偽の変更が op-log に載る。
- **`undefined` と `{}` は同じ**: どちらも「プロパティが無い」として扱う (client の `computeOperations.sameProperties` と同じ規則)。

### applyPropertyChange

- **触ったプロパティだけを書き換える**: 他のプロパティが残ることを確認する。これが置換との唯一かつ本質的な違いである。
- **値を省いた変更は削除**: `diffProperties` が作る削除の表現と対になる。
- **元のオブジェクトを変更しない**: projection (`project.ts`) は畳み込みの途中でノードを共有するので、破壊的に書くと過去の状態まで汚染される。

### 往復 — ここだけ性質として書く (property-based testing のパイロット)

**なぜ性質なのか。**往復の主張は「**ある** from と to で成り立つ」ではなく「**あらゆる** from と to で成り立つ」である。例で書くと、コードが述べているのは 1 つの例で、一般命題はこの `.test.md` の日本語の側にしかない。**述べたい命題と、検証している命題が別の場所にある**状態になる。性質として書けばコードが一般命題そのものを述べるので、この文書は「なぜその性質が重要か」に専念できる。

step2 の中核は分散した op-log の畳み込みで、その正しさは「あらゆる配送順で」という全称命題の形をしている。ここはその方針 (`deepse/plans/step2-implementation.md` §5.4) の最初の 1 件である。

- **`∀ from, to. apply(from, diff(from, to)) = canonical(to)`**: この関数対の契約そのもの。右辺が `to` ではなく **`canonical(to)`** なのが要点で、diff も apply も新名へ寄せる以上、旧名は往復を通ると新名になって出てくる。「置換と結果が一致する」ではなく「置換した上で正規化した結果と一致する」が正しい主張である。
- **`∀ current, from, to. 差分に現れないキーは変わらない`**: これがキー単位化の目的そのもの。`current` には他者が並行して足したプロパティが入っていて、こちらの from/to はそれを知らない。全体置換なら消えるが、キー単位なら差分に名前が出てこないキーは触られない。
- **変更が 0 件でも結果は正規化される**: 上の性質が見つけた反例を、そのまま回帰テストとして残したもの。性質は乱数で引くので、毎回ここを引く保証がない。

#### 生成器の設計が結論を決める

性質を書くとき、**何を引くかが命題の強さそのもの**になる。ここでは 2 つの判断をした。

- **名前は旧名・新名・custom を混ぜる**。#137 の正規化が往復の意味に直接絡むので、旧名を引かない生成器では往復を確かめたことにならない。
- **値は小さなプールから引く**。`fc.jsonValue()` のような広い生成器だと `from` と `to` の値が一致することがほぼ起こらず、**変更が 0 件になる場合を引き当てられない**。実際、後述の欠陥は 500 回引いても当たらなかった。プールを 5 つに絞ると 194 回目で出た。**値の広さより、値の衝突の方が効く**。

#### このパイロットが見つけたもの

`applyPropertyChanges` が reduce の初期値を `{ ...properties }` と生のまま置いていた。`applyPropertyChange` は毎回正規化するので、**変更が 1 件以上あるときだけ結果が正規化される**という非対称になっていた。`from = to = { image: 'x' }` のように差分が空だと、旧名がそのまま残る。

既存の例ベースのテストが取り逃していたのは、例が `{ a: 1, b: 2 }` → `{ a: 9, c: 3 }` という **旧名も値の一致も含まない** ものだったからである。例を選ぶ人は、自分が気にしている軸で例を選ぶ。

### 名前の正規化 (#137)

`image` / `imageUrl` は step0〜step1 で `.` を含まない名前のまま書かれてしまった**システムの**プロパティである。プロパティ名の規約 (`spec/propertyEditor.md`) では `.` を含まない名前はすべて custom (グラフの編集者のもの) なので、このままだと step2 の property editor でユーザに見えて編集・削除できてしまう。op-log は追記のみで書き換えられないから、**読む側で新名へ寄せる**しかない。

- **旧名は新名へ寄る / 対応表に無い名前はそのまま**: 正規化の対象が対応表に載せた 2 つだけであることを固定する。`期限` のような custom を勝手に触らないことが規約 (custom に名前空間を要求しない) の担保である。
- **旧名が無ければ同じ参照を返す**: 正規化は projection の畳み込みで全 op に対して走る。毎回オブジェクトを作り直すと、変わっていないノードまで新しい参照になる。
- **新旧が両方あれば新名が勝つ**: 移行期には「旧名のまま残っている値」の上に新名で書き足す経路がある (画像 URL の編集)。旧名が勝つと、書き足したはずの編集が消える。
- **`diffProperties` は両側を寄せてから比べる**: 寄せずに比べると「旧名の削除 + 新名の追加」の 2 件に割れる。同じプロパティの変更は 1 件の op であるべきで、割れると merge の競合単位も割れて競合を取り逃す。
- **`applyPropertyChange` は変更の名前も当てる先も寄せる**: 旧名の op が新名のプロパティを消せることまで確認する。同じプロパティである以上、綴りの違いで別物になってはならない。
