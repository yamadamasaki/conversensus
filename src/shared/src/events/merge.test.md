# merge.test.ts — ログマージのテスト仕様

## 何を

`merge.ts` の `mergeBranches` (ブランチの batches を trunk へ追記するマージ) を検証する。

## なぜ

現行 `mergeBranchToTrunk` (レコード複製) を置換する Phase 2 の中核。conversensus の主題である「コンフリクト = 合意形成の機会」を成立させるため、**並行変更を対立として検出**しつつ、layout は静かに解決する (D7) という区別を正確に固定する必要がある。

step 2 で structure の競合検出を追加した (#206)。DtR (dialogue to resolve) graph は structure の競合から選択的に起動されるので、その検出がないと DtR の (2) が成立しない。仕様は `deepse/requirements/spec/merging.md` の「structure の競合」。

## どのように

### content (既存)

- **content 対立の検出 + LWW**: trunk と branch が同一ノードの content を別の値へ並行変更した場合、対立を 1 件検出し、projection では clock 最大が勝つ (LWW 暫定確定) ことを確認する。
- **layout は対立にしない**: 同一ノードの layout 並行変更は対立 0 件で、projection は clock 最大の値になる (静かな LWW, D7)。
- **同値の並行変更は対立にしない**: 同じ値への並行 content 変更は対立にならない (無意味な対立を出さない)。
- **structure の OR-Set**: ブランチ側で追加したノード・エッジがマージ後も保持される。
- **異なる target は非対立**: 別ノードへの content 変更同士は対立しない (対立は同一 target に限定)。

### structure の削除依存 (非対称)

片方が削除した要素を、もう片方が**前提にしている**場合を検出する。判定は「その op が成立するために存在していなければならない要素」(`prerequisitesOf`) 一本で、S1/S2/S4 をまとめて導く。

- **S1**: trunk が消したノードに branch が edge を張る。競合の `target` は **消された要素** であって edge ではないことを確認する — 主題は「何が消えたか」だから。
- **S2**: trunk が消したノードの content を branch が編集する。
- **S4**: trunk が消したグループに branch がノードを入れる。`setParent` の前提は `[対象ノード, 親]` の 2 つだが、消えているのは親だけなので **1 件**であることを確認する。
- **向きの対称性**: branch 側が削除した場合も検出する。このとき `ours`/`theirs` は「削除した/された」ではなく **常に trunk 側/branch 側**であることを固定する — 呼び出し側がどちらのログを追記するかで意味が変わるため。
- **両側が同じノードを消す**: 対立にしない。どちらも消したいだけで、争いがない。
- **消えたノードの layout 変更**: 対立にしない。layout の競合は「通知のみで DtR を起動しない」と決めたので、削除依存の判定に混ぜない。

### カスケード削除の推移的な検出 (S1' / S2', Phase 3 T1)

**判定の入力を「op に書かれた id」から「分岐点の状態にカスケードを当てて求めた、実際に消える要素の集合」に変えた**のがこのスライスである。`node.remove` は子孫ノードと端点を失うエッジも消すので (`cascade.ts`)、op の target だけを見るとグループ削除で子への依存を取り逃す。グループは中身をまとめて消す操作なので、共同作業では直接参照より起こりやすい。

`mergeBranches` の第 1 引数が分岐点のグラフになった。**カスケードが絡まない検出 (S1/S2/S4) は空のグラフでも成立する** — `cascadeOfRemoval` は対象自身を必ず返すからである。よって既存のテストは `NO_BASE` を渡し、**カスケードが主題のテストだけが本物の分岐点を組む**。

- **グループを消すと、子への編集が削除依存になる**: op に書かれた id は親だけ。子は分岐点の状態を見ないと出てこない。競合の `target` は「実際に消された要素」= 子であることを固定する。
- **巻き添えで消えるエッジへの編集も拾う**: 子が消えるので子に繋がるエッジも消える。**2 段のカスケード**である。
- **分岐点を渡さないと同じ編集を取り逃す**: T0 以前の振舞いをそのまま固定してある。退行するとここが緑に戻るので、この機能が生きているかの指標になる。
- **向きの対称性**: branch 側がグループを消した場合も拾う。`ours`/`theirs` は trunk/branch のまま。
- **グループの外は巻き込まれない**: カスケードが広がりすぎないこと。
- **複数の削除が同じ要素を壊すとき**: **clock の小さい方**に帰属する。競合の主題は「誰が最初に壊したか」であり、入力の並び順で答えが変わってはいけない。

**既知の限界**: カスケードは分岐点の状態に当てる。分岐後に相手側が `node.setParent` でグループに入れたノードは、分岐点では子孫でないので削除の巻き添えとして数えられない。取り逃すのは「分岐後に依存関係が生まれた」場合だけで、仕様が名指しする S1' / S2' (グループを消すと中身も消える) は分岐点で足りる。

### layout の競合 (Phase 3 T3)

仕様の 3 段の一番下。**検出して通知するだけで DtR graph は起動しない。**共同編集で二人が同じノードを動かすのは日常的なので、毎回「対話して決着すべき競合」に上げると DtR がノイズで埋まる。一方で検出しないと、位置が飛んだ理由が分からない。通知だけがその中間である。

**判定の単位は op ではなく「一つの操作」である。**`node.setLayout` は部分更新で、移動 (x/y) と リサイズ (width/height) は projection でも独立に畳み込まれる。op 単位で判定すると、A が動かし B が大きさを変えただけで競合になる — `setProperties` が抱えていたのと同じ粗さ (ANA-208) を、layout で作り直すことになる。そこで観点 (`aspect`) で割る。

| 観点 | 何を束ねるか |
| --- | --- |
| `position` | 移動 (x, y) |
| `size` | リサイズ (width, height) |
| `route` | edge の描かれ方 (sourceHandle / targetHandle / pathType)。経路の付け替えは一動作で決まる |

- **同じノードを二人が動かす** → `position` の対立 1 件。
- **🔴 移動とリサイズは対立にしない**: 別の観点なので混ざらない。projection でも両方そのまま残る。
- **移動とリサイズを両方触った op は 2 つの観点に割れる**: 一つの op が複数の単位を生む (`setProperties` と同じ形)。
- **触っていない観点は単位にしない**: 移動しかしていない op が「大きさを undefined に変えた」ことになると、リサイズした相手と偽の競合になる。
- **同じ値なら対立にしない / 別のノードなら対立にしない**: content と同じ扱い。
- **🔴 確認では止めない**: `requiresConfirmation` が false を返す。この分岐は T1 で書いたが、layout の category が無かったので**T3 で初めて生きた**。
- **🔴 削除依存に混ざらない**: 消えたノードを動かしただけで DtR が起動するとノイズになる (`prerequisitesOf` が layout を対象外にしていることの裏取り)。
- **content の対立とは別の単位**: 同じノードの content と layout を触っても混ざらない。

**解決は静かな LWW のまま。**検出が増えても畳み込みは変えていない — 通知の系列が 1 本増えただけである。

### 適用前の確認 (`requiresConfirmation`)

merge は不可逆なので、**適用前に人の確認を要する競合か**を種別で決める (Phase 3 T1)。content は DtR graph の強制起動、structure は通知から手動で DtR 起動 — どちらも人の判断が要る。layout は「通知のみ」なので止めない。

述語は `category !== 'layout'` である。**止める側ではなく止めない側を書く** — 種別が増えたときの既定が「人に問う」になるほうが安全で、通知だけで済ませてよいのは意図して決めた種別に限られる。

### structure の並行変更 (対称)

「一つしか持てない値」への並行変更。content の対立と同型なので、検出も同じ経路 (`collectParallelChanges`) を通す。

- **S3**: 同じ edge の端点を別々に付け替える (`edge.reconnect`)。
- **S5**: 同じノードを別々のグループに入れる (`node.setParent`)。
- **同値の並行変更は対立にしない**: content と同じ扱い。
- **別々のノードへの変更は対立しない**: 対立は同一 target に限定。

### プロパティはキー単位で判定する (#208)

properties の対立は **プロパティ 1 つを単位**に判定する。target 単位だと、別々のプロパティを触っただけの二人が競合になり、しかも projection の置換で負けた側のプロパティが丸ごと消える (`spec/merging.md`「op の粒度」)。

- **別々のプロパティは対立にしない**: 対立 0 件であること**に加えて**、projection で両方のプロパティが残ることまで確認する — 「対立を出さない」だけでは、データが消えないことの証明にならないため。
- **同じプロパティの並行変更は対立にする**: `propertyName` に**どのプロパティで揉めたか**が載ることを固定する。DtR graph は対立を人に見せるので、target だけでは何を議論するのか決まらない。
- **同値の並行変更は対立にしない**: content と同じ扱い。
- **片方が削除・片方が変更**: 同じプロパティなら対立。削除は「値の無い変更」なので、値の違いとして自然に拾える。
- **edge も同じ規則**: `edge.setProperty` を node と同じ経路で判定する。
- **旧形式との混在**: 移行期は既存ログの `setProperties` (置換) と新形式が同じマージに混ざる。旧形式も**プロパティごとに割ってから**比べることで、別プロパティを触っただけの偽の対立を出さないこと、同じプロパティなら対立になることの両方を確認する。
- **旧名と新名の並行変更は 1 件の対立**: 移行期には片方の端末が `imageUrl` を、もう片方が `app.conversensus.imageUrl` を書き得る (#137)。単位キーを新名へ寄せないと別プロパティと見なして競合を取り逃す。載る `propertyName` が**新名**であることも固定する — DtR graph が人に見せるのは正規の名前であるべきで、綴りが端末ごとに違って見えては議論にならない。
- **content とプロパティは混ざらない**: 同じノードの `setContent` と `setProperty` は別の単位である。

### node の本文と種別は別の単位である (Phase 5 P1)

`node.setLabel` を足したことで、**content の対立単位を target だけで括れなくなった**。
node は本文 (`content`) と種別 (`label`) の 2 つのフィールドを持つので、target 単位のままだと
「片方が本文を直し、片方が種別を付けた」が対立として出る。**触った所が違うのに対話を
求めるのは誤検出**で、しかも DtR graph はそのノイズに埋まる。プロパティを名前ごとに
割ったのと同じ理由で、フィールドごとに割る。

- **本文と種別は混ざらない**: 対立 0 件であること。この 1 件が単位キーの分割そのものを
  述べている (分割を戻すとこれだけが落ちる)。
- **同じノードに二人が別の種別を付けると content の対立になる** (設計 D4): 種別は
  **人が決めた意味**なので、食い違いは合意形成の機会である。layout に置くと通知だけで
  流れ、structure に置くと削除依存の判定に混ざる。暫定確定が LWW であることも
  content の同名テストと同じ形で確認する。
- **同値の並行変更は対立にしない / 別々のノードは対立にしない**: content・プロパティと
  同じ規則がそのまま効くことを固定する。ここが揃っていないと、種別だけ別の規則という
  覚えるべき例外が増える。

## 対象外 (将来課題)

- **projection の add-wins 化**。検出はするが、決着までの間の既定の振舞いは現状の clock-LWW のまま。`spec/merging.md` の「検出後の既定の振舞い」で add-wins と決めたが、それは別イシューとする。
- **旧形式どうしの、置換が暗に行う削除**。`setProperties` はログに載っていないプロパティを消すが、プロパティごとに割った比較ではその削除を表せない。旧形式どうしのマージで「片方が消したプロパティを片方が編集した」を取り逃す。新規に旧形式を発行しないので、移行期の既存ログの間だけの穴である。
- ~~**カスケード削除の推移的な検出**~~ **対応済 (Phase 3 T1)**。上記の「カスケード削除の推移的な検出」を参照。残る穴は「分岐後に依存関係が生まれた場合」だけである。
