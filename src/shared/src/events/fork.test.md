# fork.test.ts — fork のテスト仕様 (step2 Phase 3 T6)

## 何を

implicit merge が競合を保留した記録 = fork と、それを生んだ競合の**凍結された記述**。

## なぜ凍結するのか

「implicit merge は冪等な導出なのだから、競合も畳み直せば再現できる」は成り立たない。

- 畳み直して得られるのは **今**の競合であって、fork を作った時点の競合ではない
- そもそも**競合が消えていることがある**。負けた側の要素がその後に削除されたり値が
  上書きされたりすれば、畳み直しても競合は出てこない。その時 fork は**理由のない fork**
  になる

fork を書くと決めた理由 (「同期のたびに再計算すると解決したはずの fork が毎回復活する」)
の裏返しである — 再計算に委ねると、今度は**説明の方が消える**。

## 器は branch と同じ

fork は branch の一種として作る (仕様の「ユーザから特殊な branch として見える」)。中身は
空で、分岐点は検出時点のログ先端になる — fork は「ここで保留した」という印であって、
編集を溜める場所として始まるわけではない。

**op-log への昇格と同期は T7 の仕事である。**ここで作る fork は手元に残るだけだが、
「同期のたびに復活する」問題はそれで解ける (Exit 5)。

## 同一性 — 競合そのものから導く

implicit merge は全参加者がそれぞれの手元で行う導出なので、**同じ競合を全員が独立に
検出する**。素直に作ると一つの競合に参加者の数だけ fork ができ、人間からは同じ理由の
fork が並んで見える (`step2-implementation.md` の S4)。

そこで `conflictKey` を競合そのもの (種別・対象・揉めた単位・対立した二つの batchId) から
導く。誰の手元でも同じ値になるので、独立に書かれた fork は畳み込みの段階で一つにまとまる。

- **🔴 ours / theirs が入れ替わっても同じ鍵になる**。ここが核心である — 私から見て
  「新着」の op は、**相手から見れば「手元」**である。batchId を整列してから繋ぐのは
  そのためで、揃えないと参加者の数だけ fork ができる。
- 対象 / プロパティ名 / layout の観点 / 種別が違えば別の鍵になる。**検出側の単位と
  同じ粒度**で分かれる (#208 のキー単位, T3 の観点)。
- **🔴 id は端末ごとに違ってよい**。畳むのは鍵の方であって、branchId ではない。

凍結した記述が食い違っていても同一性は変わらない — 名簿の食い違いで見えている範囲が
違えば記述は違いうるが、それは同一性の条件ではない。

## 何を凍結するか (仕様の表)

| | テストが見るもの |
| --- | --- |
| 種別 | `category` + structure の `kind` + layout の `aspect` |
| 対象 | id と、**その時点で人間に見える形** (`targetLabel`) |
| 双方の操作 | 対立した 2 つの op と、**batch から焼き込んだ actor / clock** |
| 分岐点 | `baseAt` = 検出時点のログ先端 |

- **🔴 actor と clock を batch から焼き込む**。`MergeConflict` は `batchId` しか持たず、
  後から batch を引ける保証が無い (相手の repo は参加期間の外に出ることも、読めなくなる
  こともある)。「誰と誰が、いつ」が分からなければ相談する相手も選べない。
  **相手の batch が手元に無ければ空で書く** — 書かないより良い。
- **🔴 対象の見える形を凍結する**。id だけでは、後でその要素が消えていると何も分からない。
- **分岐点は以後動かない**。ログが伸びても `base.at` は検出時点のままである。

## 名前

fork は一覧に並ぶので、競合を**一行で言い表す名前**を持つ。名前の無い対象は
「名前のない要素」と言い換えるが、**記述の側は空文字のまま残す** — 「名前が無い」と
「引けなかった」は別の話で、言い換えは見せる側の判断である。

## テストしていないこと

- **同じ競合から fork がいくつできるか**の実地確認。鍵が揃うことは単体で見たが、
  独立に書かれた fork が実際に畳まれるのは同期を作る **T7** である。
- **DtR graph の起動**。記述の唯一の用途は起動時の呼び出し対象の既定値を供給することだが、
  起動そのものは Phase 6 である。
