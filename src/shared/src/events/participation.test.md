# participation.test.ts — 名簿の畳み込みのテスト仕様

## 何を

`participation.ts` の `foldParticipation` (判断 batch 列 → 名簿) と `wasParticipatingAt`
(ある clock で参加していたか) を検証する。

## なぜ

**pre 条件の検証が名簿の中核である。**op を clock 順に畳みながら pre 条件を検証し、
満たさないものを捨てる。ここから 2 つの性質が同時に出る
(`deepse/requirements/spec/participation.md`)。

- **招待されていない actor の承認は無効になる。**参加コードは秘密ではない (被招待者の DID を
  含むだけ) ので第三者が入手しうる。「入手しても参加できない」を担保しているのは
  この検証だけである
- **取り消し合いが起きても、誰の手元でも同じ結論になる。**検証しないと、取り消された側が
  取り消し返せてしまい、手元によって名簿が変わる

名簿は同期の入口でもある。「参加していた期間の op-log だけを同期する」(Phase 2) の判定が
ここの `history` に乗るので、**名簿が狂うと同期する範囲が狂う**。

## どのように

### genesis — 名簿の起点

`file.create` op が無く genesis batch の actor は固定値なので、**作成者の DID がグラフの
op-log のどこにも載っていない** (事実 7)。名簿の起点は名簿の中に置く。

- **genesis を出した actor が最初の参加者になる**
- **genesis より前は、あらゆる op が pre 条件で落ちる**。名簿が空だと invite も accept も
  revoke も pre 条件を満たさない。これが「最初の 1 人は genesis でしか決まらない」ことの
  担保である
- **2 つ目の genesis は捨てられる**。自己申告でよいのは「起点と繋がっていなければ読まれない」
  からだが、読まれてしまった場合に 2 人目の起点を作らせない

### 招待と承認

- **招待されていない actor の承認は捨てられる** — 上記のとおり参加コードの秘密性に頼らない
- **参加者でない actor の招待は捨てられる**
- **他 PDS の DID への招待は捨てられる**。仕様は「やらない」ではなく**「無効とする」**と
  定めているので、UI の入力チェックではなく pre 条件である。判定は注入した `isLocalDid` で
  行う (既定値を持たせていないのは、配線を忘れた瞬間に検証が消えるため)
- **既に参加している actor への招待は捨てる / 招待済への再招待は捨てず招待者を上書きする。**
  非対称なのは、再招待 (参加コードの再発行) が正当な操作で名簿の結果も変わらないのに対し、
  参加者への招待は「invited と participating の両方に載る」矛盾した状態を作るからである
- **招待者を一覧に出せる**。UI の表が「invite されているアクタと invite しているアクタ」を
  並べるので、`invited` は集合ではなく被招待者 → 招待者の写像である

### 取り消しと参加取りやめ

- **取り消しは承認の前後を問わず同じ op である** (仕様の決定)。別の op にすると境界に
  「どちらでもない」状態が生まれるので、両方の経路で同じ結果になることを固定する
- **取り消し合いは誰の手元でも同じ結論になる。**a が a' を取り消した後、それを知らない
  a' が「a の取り消し」を出しても、clock 順では a' は既に名簿にいないので捨てられる

### actor は端末単位だが、名簿は DID 単位である

**同じ DID の別端末は 1 人として数える。**actor は `<did>#<deviceId>` なので、そのまま
名簿に入れると 2 台目で開いただけで参加者が増える。

### 参加期間

- **参加・取りやめ・再参加が期間として残る。**再参加は新しい期間になるので、非参加期間が
  履歴に穴として残る
- **期間は閉じた始点・開いた終点** (`from <= clock < to`)。取りやめた瞬間の clock を持つ op は
  既に参加者でないものとして扱う

## 引き取り (`participation.reopen`)

### なぜ

**行き止まりがあった。**最後の 1 人が参加を取りやめると名簿が空になり、そこからは
招待が `issuerNotParticipating` で、起点の置き直しが `duplicateGenesis` で落ちる。
**誰も二度と参加依頼を出せない** — File は手元に残っているのに共同作業だけが永久に
閉じる (2026-09-05 に実機で行き止まりを確認した)。

起点と別の op にしたのは、起点が「File に 1 つ・clock 0 固定」だからである。
引き取りは何度でも起こりうるので同じ op にはできず、分けることで
「最初の 1 人は genesis でしか決まらない」も保たれる。

### どのように

- **⚠️ 引き取りが無ければ行き止まりになる。**これを最初に固定する — 招待も起点の
  置き直しも落ちることを見せないと、なぜ op を足したのかがテストから読めない
- **名簿が空なら引き取れる** / **作成者でなくても引き取れる**。畳み込みは「その File を
  持っているか」を見ない。名簿の読み出しが起点から辿れる repo しか訪ねないので、
  読まれる範囲では「判断ログに名前のある人」に自然に限られる
- **引き取った人はそのまま招待できる。**引き取りの目的がこれである
- **誰かが参加していれば引き取れない** (`rosterNotEmpty`)
- **起点が無ければ引き取れない** (`noGenesis`)。起点の無い File には引き取る名簿が
  そもそも無い。これは `ensureOwnGenesis` が直す別の状態で、混ぜると起点の修復が
  2 通りになる
- **同時に 2 人が引き取っても通るのは 1 人だけ。**clock 順で先の 1 人が入り、
  後の 1 人は名簿が空でなくなっているので落ちる。**誰の手元でも同じ結論になる**
- **⚠️ 引き取りは新しい期間を開くだけ。**誰もいなかった間は期間に含めない
  (仕様の決定, 2026-09-05)。遡って開くと「取り消した後の操作は反映されない」を、
  名簿を空にする経路で迂回できてしまう
- **引き取りは参加歴になる。**そうでないと、一度も参加していない人として
  一覧から行ごと消える

## 性質として書いたもの

CLAUDE.md「全称命題は性質として書く」に従う。どちらも例では原理的に書けない。

- **∀ 配送順. 同じ op 集合を畳めば同じ名簿になる。**これが「誰の手元でも同じ結論」の本体で
  ある。手元によって受信順は違うので、例で書いてもある 1 つの順序を確かめたことにしかならない
- **∀ op 列. 捨てられた op を取り除いてから畳んでも結果は同じ** (`rejected` の健全性)。
  捨てた op に副作用が残っていたらここで落ちる

### 生成器の設計

- **actor は 3 人の小さなプールから引く。**広く振ると同じ相手への invite / revoke が並ばず、
  **取り消し合いに当たらない** (PBT パイロットで得た「値の広さより値の衝突の方が効く」と
  同じ形である)
- **clock も狭い範囲 (0〜12) から引く。**同じ clock の batch を並べて、tiebreak
  (actor → id) が効く場合を通す
- **op を足したら生成器にも足す。**引き取り (`reopen`) を加えるときに、例のテストだけを
  書いて生成器を放置しかけた。2 つの性質は op の種類ごとに書き直すものではないので、
  **生成器に入れない = 新しい op だけが全称命題の外に残る**ことを意味する

### この性質が見つけたもの

`RejectedJudgment` が **batch 内のどの op か**を指せていなかった。同じ内容の op が 1 つの
batch に 2 つ並ぶと (`[resign, resign]`)、一方だけが捨てられるのに両者を区別できない。
UI が「この op が invalid」と示せないので `opIndex` を足した。

例ベースでは出なかった。**同じ op を 2 つ並べた batch を、人は例として書かない。**

## 出来事の列 (step2, 2026-09-04)

`history` を「参加期間の列」から「**出来事の列**」に広げた。参加履歴の画面が
「依頼日時 / 参加日時 / 取り止め日時と, 誰がそれを行ったか」を出すためである。

**なぜ畳み込みが持つのか。**材料 (`timestamp`, `actor`) は batch に載っているので、
生の判断ログから画面側で組むこともできる。しかしそれをすると **pre 条件で捨てられた
依頼や取り消しまで履歴に出る**。「採択された op だけが履歴に載る」は畳み込みにしか
言えない。`rejected` が捨てた op の出所を残しているのと対になっている。
テストは「参加していない actor による取り消しが履歴に載らないこと」でこれを見る。

**期間は導出にした** (`periodsOf`)。期間と出来事の両方を持つと書き込み先が 2 つになり、
片方だけ更新する事故が起きる。1 DID あたりの出来事は参加ラウンドの数しかない (数件) ので、
Phase 2 の同期フィルタが都度導いても足りる。

**`history.has(did)` は「一度でも参加したか」ではなくなった。**依頼も出来事として
載るからである。仕様の「依頼中に依頼が取り止められた場合, 今までに参加したことが
なければ一覧に表示されない」はこの区別を要るので、`hasEverParticipated` を別に置いた。
**両方を 1 つのテストで並べて見る** — 片方だけ見ても、取り違えていることに気づけない。

**依頼のまま取り消された場合も出来事は記録する。**参加期間は開かない (`periodsOf` が
空を返す) が、履歴の「依頼取り止め」列はこれを出す。期間と出来事が食い違う唯一の
場面なので、同じテストで両方を確かめている。
