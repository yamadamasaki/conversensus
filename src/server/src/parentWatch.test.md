# parentWatch.test.ts — 親プロセスの生存監視のテスト仕様

## 何をテストするか

「親プロセス (Tauri アプリ) が消えたことを検知して知らせる」判定そのもの。
**知らせる場合と知らせない場合の両方**, および**一度しか知らせない**ことを固定する。

## なぜテストするか

**アプリが正常終了したときは Tauri が sidecar を kill する**ので, この仕掛けは要らない。
要るのは**アプリが異常終了したとき**である。実測 (2026-08-14):

```
app=67412 daemon=67464
$ kill -9 67412        ← アプリを強制終了
67464 …/conversensusd  ← デーモンは生き残る
:39847 → 200           ← 待受も続いている
```

残った孤児は**次回の起動を壊す**。同じポートを掴んでいるので新しいデーモンは
`EADDRINUSE` で死に (Phase 8 §2.3), アプリは前回の古いプロセスと話し続ける。
アプリ側は強制終了されたら何も実行できないので, **デーモンが自分で気付くしかない**。

`onGone` は `process.exit` を呼ぶ。**二度呼ばれる形にしてはいけない**し,
**生きている親を誤って死んだと判定してもいけない** (使用中のアプリが突然閉じる) ので,
判定の両側を検査する。

## どのようにテストするか

- **`isProcessAlive` はシグナル 0 の意味に依存する** — 「送らずに存在だけ確かめる」という
  POSIX の約束である。取り違えるとデーモンは親の死を永遠に検知しない。
  自分自身 (生きている) / 存在しない PID / **実際に終了させたプロセス** の 3 つで見る。
  3 つ目は `Bun.spawnSync(['true'])` の PID を使う — 本物のプロセスで確かめる
- **監視の側は生存確認を差し込んでテストする** (`isAlive`)。本物のプロセスを殺す形にすると,
  タイミングに依存して不安定になる。ここで見たいのは「判定結果をどう扱うか」だけである
- **一度知らせたら繰り返さない** — `onGone` が `process.exit` である以上,
  2 回呼ばれる設計は誤りである
- **止めたら知らせない** — 戻り値の停止関数が効くこと

存在しない PID には `2 ** 31` を使う。PID は 32bit の範囲を超えないので,
**割り当てられることがない**。
