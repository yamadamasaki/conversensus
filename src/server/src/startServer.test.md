# startServer.test.ts — 待受開始のテスト仕様

## 何をテストするか

デーモンが**実際に bind できたときだけ「起動した」と名乗れる**こと。および
**bind に失敗したときに理由が分かる形で落ちる**こと。

## なぜテストするか

以前は `export default { port, fetch }` を bun に渡して起動を任せ, 成功メッセージは
モジュール評価の時点で出していた。実際の bind はその後なので, **ポートが埋まっていると
「起動した」と言ってから落ちていた**:

```
server running on http://localhost:3000      ← 先にこれが出る
error: Failed to start server. Is port 3000 in use?
```

step1 が一貫して守ってきた「無言の失敗を作らない」の逆で, **嘘の成功**である。
Tauri 配布 (Phase 8) では利用者がログしか手掛かりを持たないので, ここが嘘だと
何も診断できない (`deepse/plans/step1-phase8-tauri.md` §2.3 / D5)。

**気をつけるのではなく構造で塞いだ。** `startServer` は bind を終えてから
**実際に掴んだポート**を返し, 呼び出し側はその値を使って初めてメッセージを組める。
このテストはその構造が保たれていることを見る。

## どのようにテストするか

- **実際に掴んだポートを返す** — `port: 0` (OS 任せ) で起動し, 戻り値が正の番号であること。
  **戻り値が bind の後にしか存在しない**ことが, ログの嘘を構造的に防いでいる根拠である
- **掴んだポートで実際に応答する** — 名乗る資格を, 名乗る側と同じ根拠 (実際の応答) で見る
- **使用中のポートでは理由の分かる例外になる** — 素の例外は
  `Failed to start server. Is port 3000 in use?` という**推測形**で原因も書かれていない。
  断定形にし, 最も多い原因 (開発用デーモンとの衝突) を書き添えたことを固定する
- **例外は元の原因を捨てない** — 文面を差し替えるときに元のエラーを落とすと,
  想定外の失敗が追えなくなる。`cause` が残ることを見る
- **停止したポートは再び掴める** — `stop()` が本当に解放していること。
  孤児プロセスが残ると次の起動が死ぬ (Phase 8 D1 の前提)

**ポート番号は固定しない** (`port: 0` で OS に割り当てさせる)。固定するとテストが
開発中のデーモンや他のテストと衝突して, 実装と無関係に赤くなる。

**踏んだ罠**: 応答の確認は **`Bun.fetch` を使う**。グローバルの `fetch` は
`bunfig.toml` が読み込む happy-dom のもので, 実プロセスの HTTP サーバには届かない
(`NetworkError: ... Parse Error` になる)。
