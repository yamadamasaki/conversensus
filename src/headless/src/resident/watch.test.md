# watch.test.ts — 参加している File を同期し続ける (agent 段 5 S2)

## 何を

常駐の agent が同期する**契機**を見る。始めたとき・流れの合図・遅いポーリングの 3 つで、
どの File を同期するか (そして見つけ直すか) が正しいこと。同期そのものは `Headless.sync` で、ここでは偽物にする。

## なぜ

- 常駐の agent には「画面を開いた」「今すぐ同期を押した」という契機が無い。**合図とポーリングだけ**が
  新しい依頼に気づく道である。どちらかが抜けると、依頼は答えられないまま残る
- 合図には知らない File のものも来る。それは**新しく参加した File**かもしれない — 見つけ直さないと、
  agent は参加した File の依頼にいつまでも気づかない (計画 F9)
- 合図は続けて来る。同期を積み上げると、細い回線と小さな PDS に無駄な負荷をかける (連合の前提)

## どのように

`files`・`discover`・`sync`・`onSynced` を、呼ばれた順を記録する偽物にする。流れは手で合図を出す偽物。
ポーリングは試験の間に来ない長さにし、ポーリングを見る例だけ数ミリ秒にする。

- 始めると、見つけてから手元の File を全部同期する
- 知っている File の合図は、その File だけ (見つけ直さない — 見つけ直しは判断ログを読む往復がかかる)
- 🔴 **知らない File の合図は、見つけ直してからその File を同期する**。始めた後に参加できるようにして試す
  (始める前から参加できると、最初の見つけ直しで見つかってしまい、合図の扱いを試せない)
- `null` の合図 (繋がった・切れた) は全部を同期する
- 合図が無くても、ポーリングが見つけ直して全部を同期する
- 流れに繋がっている間は、ポーリングの間隔を延ばす (延ばした間隔の中では見つけ直さない)
- 同期が失敗しても `onSynced` は呼び、次の File へ進む (1 つの File の失敗で他の依頼が止まらない)

### 性質

**どんな合図の並びでも、同期は 1 本ずつで、合図を受けた知っている File はすべて同期される。**

- 生成器: 合図は 2 つの File と `null` の小さなプールから 12 個まで引く。同じ File が続く並びが
  よく出るので、まとめる (積み上げない) 所に当たる
- 「すべて同期される」は、**まとめても落とさない**ことを言う。まとめる実装は、溜まった契機を
  取り出してから次の合図が来るまでの間で落としやすい
