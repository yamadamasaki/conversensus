# applyEvent.test.ts — テスト仕様

## 何をテストするか

`applyEvent.ts` の `applyEvent(event, nodes, edges)` 関数。
GraphEvent を React Flow のノード/エッジ配列に適用した結果を返す。

## なぜテストするか

- undo/redo の中核であり、誤ったイベント適用はグラフ状態の破壊につながる
- structure/content/layout/presentation の4カテゴリにまたがる多様なイベント型が存在する
- 純粋関数なのでテストが容易

## どのようにテストするか

| カテゴリ | テスト内容 |
|---------|-----------|
| NODE_ADDED | ノード追加・座標反映・エッジ非影響 |
| NODE_DELETED | ノード削除・接続エッジ同時削除・無関係エッジ維持 |
| EDGE_ADDED | エッジ追加・markerEnd 自動付与 |
| EDGE_DELETED | エッジ削除・ノード非影響 |
| EDGE_RECONNECTED | source/target 変更・labelOffset リセット |
| NODES_GROUPED | 親ノード挿入・子ノード parentId/position 更新 |
| NODES_UNGROUPED | 親削除・子ノード位置復元・parentId 解除・**孤児を残さない不変条件** |
| NODE_REPARENTED | グループへの追加・グループからの離脱・グループ間移動と配列順序保証 |
| NODES_DELETED | 選択ノードと子孫・巻き込むエッジの一括削除 |
| NODES_RESTORED | 削除したノード/エッジの復元 (undo で親子関係と位置が戻る) |
| NODES_PASTED | 既存選択解除・新規追加 |
| NODES_PASTED_UNDO | 指定 ID のノード/エッジ一括削除 |
| NODE_CONTENT_CHANGED | data.content 更新 |
| EDGE_RELABELED | label 更新 |
| NODE_PROPERTIES_CHANGED | data.properties へ **from → to の差分**を当てる。`from` と一致していれば `to` のとおりになり、`from` が知らないプロパティは残る。`to` が空なら `from` にあったものが消える (#208) |
| NODE_MOVED | position 更新 |
| NODE_RESIZED | style.width/height 更新 |
| EDGE_STYLE_CHANGED | data に style マージ・既存 data 保持 |
| NODE_STYLE_CHANGED | style にマージ・既存 style 保持 |
| EDGE_LABEL_MOVED | labelOffsetX/Y 更新 |
| round-trip | apply → invert → apply で元の状態に戻ること |

## 不変条件: 孤児を残さない (ANA-107 S3)

`NODES_UNGROUPED` は「存在しなくなった親を指すノードを残さない」ことを追加で検証する。
React Flow は親が居ない子の相対座標の扱いを規定していない (未定義動作) ため、
孤児は「中身が別の場所に飛ぶ」形で表面化する — ANA-111 / ANA-112 の原因である。

イベントの `children` に載っている子だけを直す実装では、**載っていない子**が
孤児になる。リモートから届いたイベントや、イベント生成後に増えた子がこれに当たる。
そこで `applyEvent` 側でも、消えるグループを指したままのノードをグループの位置ぶん
ずらして一段上へ移す。テストは「適用後、全ノードの `parentId` が実在する」ことを
直接主張しており、実装の手順ではなく結果を固定している。

解除 → undo → redo の往復も見る。グループの位置を `(0,0)` にしないのは、
相対座標と絶対座標を取り違える実装が `(0,0)` では両者一致ですり抜けるためである
(既存テストが見逃していた条件)。

グループ化 → 解除の座標が正しいこと自体は `graph/grouping.test.ts` が担当する
(こちらはイベントの組み立て側)。

## 一括削除と復元 (ANA-107 S3b)

`NODES_DELETED` / `NODES_RESTORED` は「選択したノードとその子孫をまとめて消す /
戻す」対。1 ノード 1 イベントにしていないのは undo のためである。グループと子を
別々のイベントで消すと、undo の途中で**親がまだ復元されていないのに子だけ居る**
状態が現れる。React Flow はその状態の相対座標を規定していない (未定義動作)。

テストは削除そのものより **undo の結果** に重きを置いている。子の `parentId` と
`position`、グループ自身の位置、巻き込んだエッジが 1 回の undo で戻ること、そして
復元後も「全ノードの `parentId` が実在する」不変条件が成り立つことを見る。

適用側は `NODES_PASTED` / `NODES_PASTED_UNDO` と同じ分岐を共有している
(「まとめて足す / まとめて消す」という操作が同じであるため)。
何を消すかを決めるのは `graph/deletion.ts` で、そちらでテストする。

### EDGE_PROPERTIES_CHANGED (step2 Phase 4 Q0)

**この節は、無かったこと自体が欠陥だった。**`applyEvent` はこのイベントを
`return { nodes, edges }` で素通りしており、**edge のプロパティ変更が画面に出なかった**。
このテストファイルは 20 種のイベントを扱いながら、**これだけ一度も現れていない**。
網羅から漏れたものは、実装からも漏れる。

**穴の系譜**: step1 の設計段階で発見され、`deepse/spikes/o3-report.md` の
「Phase 1 に引き継ぐ課題」に「**統一時に実装を補う**」と書かれたまま落ちた。同じ表の
他の 4 件 (Lamport の `max+1`、add-wins、layout 対応、複合イベントの粒度) は解決済みで、
**これだけが引き継がれなかった**。`toUnified` の op 化も `invertEvent` の undo も
`project.ts` の畳み込みも揃っており、**欠けていたのはローカル reducer 1 箇所だけ**である。

**1 年近く誰も踏まなかったのは、発行元が 1 つも無かったからである。**`EDGE_PROPERTIES_CHANGED`
を dispatch する画面が存在しない。property editor が edge のプロパティを編集可能にすると
**真っ先に踏む**ので、画面を作る前に塞ぐ。

固定するのは 3 つ。node 側と**同じ規則**であることが要点である。

- **触ったキーだけが変わり、他のキーは残る**。全体置換だと、他者が並行して足した
  プロパティが消える (#208 がキー単位にした理由そのもの)
- **`from`/`to` は置き換え後の全体で、差分はここで採る**。発行元の契約が node 側と
  同じであること — `toUnified` も同じ `diffProperties` を通すので、**画面の状態と
  op-log の projection がずれない** (R4 の不変条件の edge 側)
- **対象の edge 以外は触らない**

#### 例の選び方が命題の強さを決めた (変異試験が 2 件の穴を出した)

最初に書いた 4 件は、**要点を述べているのに要点を検証していなかった**。

- **置換の意味論へ戻す変異が生き残った。**「触ったキーだけが変わる」の `from`/`to` に
  同じ値のキーしか置いておらず、**差分を採っても `to` を全体代入しても結果が一致した**。
  守りたいのは「**発行元が知らないキーが残ること**」なので、`from`/`to` のどちらにも
  載らないキーを手元に置かなければ何も言っていないことになる。
  `properties.test.md` が「値は広い生成器より小さなプールが効く / 差分が空になる境界に
  当たらない」と記録した失敗と**同型**である
- **対象で絞らない変異に対して `toBeUndefined()` が弱かった。**他の edge を空にして
  いたので、絞りが外れても「無いものが増える」形にしかならない。**既存の値を入れて
  おき、それが書き換わらないことを見る**方が確実に捕まえる

*要点を `.test.md` に書いたことと、その要点をテストが検証していることは別である。*

#### ⚠️ 変異試験そのものが 3 回空振りしていた

上の 2 件に辿り着くまでに、**測定が 3 回とも無効だった**。記録しておく。

| | 空振りの形 | 出た数字 |
| --- | --- | --- |
| 1 | `grep -c` が**別の行**を数え、「当たった」と読んだ | 偽の 38 pass |
| 2 | perl の `\Q...\E` 内で `\n` がリテラル扱いになり**一文字も置換されなかった** | 偽の 38 pass |
| 3 | `replace(old, new, 1)` が、**同じ字下がりで先に現れる `EDGE_RECONNECTED` の行**を書き換えていた | 偽の 38 pass |

**根は 1 つである — 置換対象が一意かを一度も検査していなかった。**
`          e.id === event.edgeId` という文字列は `EDGE_RECONNECTED` にも存在する。
3 回目は**無関係な分岐を壊して測っていた**わけだが、そちらを壊しても既存テストが
落ちないため、「全部緑 = 変異が生き残った」に見えていた。

対策は 2 つで、どちらも今後の変異試験に要る。

- **置換器に一意性の検査を入れる。**出現数が 1 でなければ測定を無効として止める。
  一意にならないときは、その分岐に固有の後続行ごと指定して一意にする
- **置換後のコードを目で見る。**`grep -c` の件数は当たりの証拠にならない。
  当たった行の前後を出して、**意図した `case` の中にあること**を確かめる

*変異が生き残ったように見えたら、まず変異が当たったかを疑う。*
この教訓は以前 zsh の word-split でも踏んでおり (`deepse/plans/step2-phase6-dtr.md`)、
**同じ形の失敗の 2 度目**である。

### NODE_LABEL_CHANGED (Phase 5 P4)

`data.label` を更新し、**`data.content` は触らない**。P0 で分けた 2 つのフィールドが
画面側でも分かれていることの確認で、`NODE_CONTENT_CHANGED` の対になる。
対象でないノードに `label` が生えないことも併せて見る。
