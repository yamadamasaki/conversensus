# propertyRows.test.ts — property editor の行を組み立てる部分のテスト仕様

## 何を

`propertyRows` (要素の properties → 画面に並べる行) と `addablePropertyNames`
(その edge に追加できる名前の候補) を検証する。**画面は含まない** (Q2)。

## なぜ

ここは**仕様の可視性の表そのもの**である。

| 種類 | 既定の可視性 / 変更可能性 |
| --- | --- |
| system | 見えない、追加/変更/削除できない |
| extension | 見える/見えないが混在。責務は拡張の仕組みが持つ |
| custom | 見える、追加/変更/削除できる |

**表と見た目を同じ場所に置いてはいけない。**一緒にすると「見た目を直したら system が
見えるようになった」が起こりうる。プロパティは op-log に載って**全参加者に共有される**
ので、見せてはいけないものを見せるのは表示の不具合では済まない — 編集させれば
`node.setProperty` が飛び、相手の projection まで変わる。

加えて、**間違えても静かである**。system が 1 つ余計に並んでも、行が 1 つ多いだけで
画面は壊れない。気づくのは誰かが本体のプロパティを書き換えてしまった後になる。

## どのように

### system は行にしない

仕様の表の 1 行目そのもの。`app.conversensus.image` / `app.conversensus.imageUrl` が
実在する (画像)。**判定は `propertyCategory` に委ねている**ので、ここで見るのは
「委譲が効いていること」である。

**検索 (Phase 7) と同じ規則であることに意味がある。**`searchSheet` も system を除く。
画面に出ないものが検索だけで出ると「開けない結果」になるので、**出す/出さないは
1 つの規則でなければならない**。片方だけ直すと食い違う。

### extension は行にするが、種別だけは編集させない

- `jp.co.metabolics.toulmin.kind` は**見えるが編集できない** (仕様 OnMutation:
  toulmin node / edge の種類は作成時に決まり変更できない)
- 同じ extension でも `.kind` で終わらないものは**編集できる**。仕様は extension を
  「見える/見えないが混在」とし、既定は見える側である

**判定に template を渡さない。**`isKindProperty` (語尾 `.kind`) で足りる — Phase 5 が
`kind.ts` にこの述語を置き、「『編集させてよいか』のように template を特定する必要が
無い問いに使う」と用途まで書いている。`EditableNode` / `EditableLabelEdge` が同じ
判断をしており、ここが 3 例目である。**描画側に template を配るより漏れない。**

### 編集できない理由を持つ

真偽値ではなく `readOnly: 'templateKind'` という**理由**にする。「編集できない」だけ
だと画面が説明できず、押せそうで押せない要素になる。Phase 5 が label で踏んだ形で、
あちらは「編集できるかで要素そのものを変える」(`div` か `button` か) ことで解いた。

### 構造を持つ値は編集させない

配列・構造体を文字列欄で直させると、**区切りの解釈規則をここで発明する**ことになり、
`['甲','乙']` と `['甲, 乙']` を分けられない。仕様は構造体の型の扱いを「別に決める
必要がある」として先送りしているので、step 2 では編集させない。**削除して追加し直す
口は残る**ので行き止まりにはならない。

**判定は値の形から取る。**型は宣言から来るので常に `'string'` であり、型を見ても配列は
見分けられない。ここで問うているのは「宣言された型」ではなく「**文字列欄で編集できる
形か**」なので、値そのものを見るのが正しい。

**権限が先、能力が後。**種別は「編集して**はいけない**」(仕様 OnMutation)、構造体は
「編集の**仕方が無い**」である。両方に当たる値 (op-log が壊れていて種別が配列になって
いる、など) では**禁止の方を出す** — 画面の説明として「変更できない種別です」の方が
正しい。順序を入れ替える変異がこの 1 件を落とす。

> **⚠️ `Array.isArray` の行は冗長だった。**当初は配列と構造体を別々に判定していたが、
> 配列を落とす変異が生き残った。`typeof [] === 'object'` なので、**配列が真なら
> 構造体の判定も必ず真**であり、**等価変異**である。テストを足すのではなく行を消した。
>
> *生き残った変異は、テストの穴とは限らない。コードの冗長さのこともある。*
> 逆に言えば、**変異試験は死んだコードを見つける道具でもある**。

### 型は宣言から来る (値から推論しない)

**型を指定するのは実装コードか template のような拡張であって、入力された値では
ない** (利用者判断 2026-09-20)。step 2 は型の宣言の仕組みを持たないので、編集できる
プロパティはすべて custom = **文字列**である。

一覧に「文字列」と出すのは**推測ではなく事実**である — 値が文字列だからである。
`2026-09-20` に「日付」と出すのは、宣言されていない型の推測になる。

**検索の結果一覧 (Phase 7) と同じ規則である**ことが要点で、同じプロパティが片方で
「日付」、片方で「文字列」に見えてはいけない。

> **⚠️ 当初は値から推論していた** (`inferPropertyType`)。撤回した理由は、推論した型を
> **使う場面が無い**こと、そして入力から型を決めて値を寄せると `3` と打っただけで
> 数値になり**文字列の `"3"` を入れる手段が無くなる**ことである。
>
> **型の出どころと編集可否は別の軸である** — 拡張が定義する属性には、型を持ちつつ
> 値をユーザが上書きできるものもありうる。だから `type` と `readOnly` を別に持つ。

### 並び順は挿入順に依らない

**`Object.entries` の順に頼らない。**挿入順なので、他者の op が届いた順で行が入れ替わる。

検索の結果一覧は「読む」ものなので走査順で安定すれば足りたが、**ここは編集する表**で
ある。押そうとした行が動くのは見え方の問題ではなく**誤操作の問題**になる。日本語の
プロパティ名 (`期限`, `優先度`) が普通に来るので `localeCompare(…, 'ja')` で比べる。

**固定するのは「安定であること」であって、特定の並びではない。**

当初この節には「名前順に並ぶ」と書き、`出典 → 期限 → 優先度` を期待するテストを
置いていたが **落ちた**。`localeCompare('ja')` の実測は `期限 → 出典 → 優先度` で、
**ICU の ja ロケールは漢字を読みで並べない**。私が書いたのは読み順のつもりだったが、
コードポイント順 (`優先度 → 出典 → 期限`) とも一致しない。**漢字の並びに人が読める
意味は無く、決まっているのは「同じ入力なら同じ結果」だけ**である。

実測に合わせて期待値を書き直すこともできたが、それは**実装を写しただけのテスト**に
なり、何も主張しない。そこで主張の方を正しい強さに直した。

- **入れる順を変えても同じ並びになる** (日本語の名前で 3 通りの挿入順を比べる)。
  これが誤操作を防ぐために本当に要る性質である
- **取りこぼしが無い** (並びを問わずに集合として一致する)
- **ASCII では名前順になる** — 読みの問題が出ない範囲では人の期待どおりであること
- **かなは読み順になる** — 漢字と違い `localeCompare('ja')` が読みで並べる。
  漢字だけが例外であることを示す

*テストが落ちたとき、実装ではなく期待値の方が間違っていることがある。*
ここでは期待値も主張も両方が間違っており、**実測に合わせるのではなく主張を弱めて
正しくする**のが筋だった。

### 追加できる名前の候補 (`EdgeKind.properties` の最初の消費者)

Phase 5 が「**step2 では宣言だけ**である。これを食う property editor は Phase 4 が
作る」(設計 事実 D) と書いて置いたものを、ここで初めて引く。**それまで `.properties` を
参照する箇所は 1 つも無かった** — 宣言は型の中で眠っていた。

固定するのは 4 つ。

- **その edge の種類が宣言した名前が出る**
- **既に値が入っている名前は出ない。**行として出ているものを「追加」に並べると、
  押しても何も起きないか、既存の値を消すことになる
- **判定は template ごとに閉じる。**種別プロパティ (`kindPropertyOf`) を見て、
  **同じ template の** `edgeKinds` から引く。混ぜると T1 の宣言が T2 の edge に出る
  (`edgeKindCandidates` と同じ判断)

  > **⚠️ この項目は最初、検証が成立していなかった。**宣言つきの template と TOULMIN を
  > 混ぜて `[]` を期待していたが、**TOULMIN の `edgeKinds` は宣言が空**なので、
  > 混線しても閉じていても `[]` が返る。変異 (`edgeKindsOf([t])` →
  > `edgeKindsOf(templates)`) が生き残って発覚した。
  >
  > **観測には「同じ種別 id を持つ、宣言の中身が違う 2 つ」が要る。**`edgeKindsOf` は
  > 種別 id で重複を除き**先に来た template を残す**ので、id が違えば混ぜても引き
  > 当たらず差が出ない。2 つ目の種別を渡し、**2 つ目の宣言が返ること**を見る
  > (混線していれば 1 つ目の宣言が返る)。
  >
  > *「他の template のものが出ない」を確かめるには、**出うる他のもの**を用意しな
  > ければならない。*空の相手と比べても、何も出ないことしか分からない。
- **解決できなければ候補なし。**種別を持たない edge、知らない template の種別を持つ
  edge のどちらでも空を返す。**知らない template のせいで追加を塞がない**
  (`templatesOf` が知らない id を黙って落とすのと同じ)

## テストしていないこと

- **画面**。行の見せ方、編集の口、追加のメニューは Q2
- **推論規則そのもの** (`inferPropertyType`) と**分類規則そのもの** (`propertyCategory`)。
  どちらも `properties.test.ts` が持つ。ここが見るのは委譲
- **node 側の追加候補**。`NodeKind` は `properties` の宣言を持たない (`EdgeKind` だけが
  持つ)。仕様が node について同じ宣言を求めたら、そのとき足す
- **編集した結果が op になること**。`NODE_PROPERTIES_CHANGED` / `EDGE_PROPERTIES_CHANGED`
  の発行は Q2 の仕事で、reducer 側は Q0 で塞いだ
