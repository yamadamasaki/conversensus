# OverwriteNotice.test.tsx — 上書きの報告の出し方 (step2 Phase 3 T8)

## 何をテストするか

検出した「あなたが書いたものが相手の編集で変わりました」を、**競合の通知とは別の
強さで**画面に出せること。

## なぜテストするか

### 鳴らし方が、この画面の設計判断そのものである

この報告は**順次編集でも鳴る**。相手が私の書いた文章を読んで直すたびに 1 件出るので、
競合の通知 (`ConflictNotice`) と同じ強さで自動表示すると、共同編集の間じゅう通知が
開き続ける。**一番まずいのは通知が信用されなくなることである** — 本当に人の判断が要る
content / structure の競合まで読み飛ばされる。

そこで「鳴る通知」ではなく**常設の控えめな印**にした。件数だけを出し、人が押したときだけ
一覧が開く。事実の報告なので、見に行く時機は人が決めてよい。`🔴` を付けたのは、
この決着が壊れると気付けなくなるものである:

- **畳んだ状態で出る** — 開いて出したら「鳴る通知」に戻る
- **`role="status"` を持たない** — `ConflictNotice` は読み上げに割り込むが、こちらは
  割り込まない。目に見える強さだけ抑えて読み上げが割り込むと、決着が半分しか守られない
- **「競合」と言わない** — `clock(自分) < clock(新着)` は、相手が私のを見た上で直した
  可能性を排除しない。並行だったと主張できないので、言うのは起きた事実だけである
- **対象を名前で出す** — target は UUID である。T4 の実機観察で「どれのことか伝わらないと
  通知は機能しない」ことが分かっている

## どのようにテストするか

### 見た目ではなく、決着を落とす形で書く

色や余白は試験しない。**変わったら決着が崩れるもの**だけを見る — 開閉の初期状態
(`details.open`)、role の有無、文言に「競合」が含まれないこと、id が出ないこと。

開閉状態を `details` の DOM で見ているのは、**この画面が開閉の state を持たない**
からである。持たない選択 (キーボード操作と支援技術がブラウザ側で済み、状態が無い分だけ
壊れない) をテストの側からも固定している。

### 3 段の言い分けは 1 本にまとめる

content / properties / structure / layout の 4 通りの言い方を 1 本で確かめる。
段ごとに扱いが変わる `ConflictNotice` と違い、ここは**全段が同じ扱い (報告)** なので、
分けて書いても読む人の得る情報が増えない。

### 行の同一性は「対象 + 観点」である

同じノードの position と size は別の報告である (検出側の単位キーと同じ)。
対象だけを鍵にすると React の key が重複し、片方が消える。

## テストしないこと

- **検出の条件**。`sync/overwrites.test.md` の担当である
- **溜める挙動**。`accumulateOverwrites` の単体で見る。この画面は渡された束を描くだけである
- **`ConflictNotice` との重なり**。位置は両者とも持たず、積むのは `App` の通知スタックの
  責務である
