# rangeFetch テスト仕様

## 何を

`listByRkeyPrefix` (step1 Phase 7 p7-2) をテストする。**rkey が prefix で始まるレコードだけを
読む走査**が、正しい結果を返すことと、**リクエスト数が repo 全体に比例しない**ことの両方を
固定する。

## なぜ

Phase 7 の目的は「remote の全件 list をやめる」ことなので、**結果だけを見るテストでは
目的が達成されたかを判定できない** — 全件を読んでから JS で捨てても結果は同じになる。
そのため各ケースで**リクエスト数と渡した cursor 列**を固定する。

走査が依存しているのは ATProto の**契約ではなく PDS 実装の性質** (設計 §6.1):

- `cursor` に検証が無く、rkey として直接比較される → 前回応答由来でない**合成 cursor**で
  任意の rkey 位置へ seek できる。
- `reverse: true` は **rkey 昇順** + `rkey > cursor`。
- 応答の `cursor` は**最後のレコードの rkey そのもの**。

これは p7-0 の実機 spike (設計 §5.1, 全 12 項目 PASS) で確定させた。ここでは
その意味論を模した pager で走査の論理だけを検証する。

また、この関数を `collections.ts` から切り出したのはテスト可能性のためである
(`collections.ts` は `getAgent()` の singleton に依存し、停止条件とリクエスト数を
単体で固定できない)。あわせて「壊れたときの差し替え面」も 1 ファイルに閉じた (§6.1 の緩和 b)。

## どのように

`fakePager(rkeys, pageSize)` が PDS の `listRecords` を模す: rkey 昇順に並べ、
`rkey > cursor` で絞り、`pageSize` 件返し、cursor に**最後のレコードの rkey**を入れる。
渡された cursor を記録するので、結果とリクエスト数と seek 位置を同時に検査できる。

- **prefix に合致するものだけを昇順で返す** — 隣接する `v1~A~…` / `v1~C~…` を含めない。
- **prefix を外れた 1 件で止まる** — 対象 2 件の後に 50 件を置き、**1 リクエスト**で
  終わることを固定する。境界検出のための 1 件の読み過ぎは正常動作 (設計 §3.2)。
- **複数ページを cursor で継ぐ** — 7 件 × ページ 3 件で 3 リクエスト。cursor 列が
  前ページ末尾の rkey であることまで固定する (合成 cursor から応答 cursor への
  引き継ぎが崩れると、静かに取りこぼす)。
- **旧 rkey を 1 件も読まない** — 旧形式 (hex UUID) 40 件を混ぜても、合成 cursor が
  それらをまたいで着地するのでリクエスト数が旧レコード数に比例しない。
  **これが `v1~` 前置 (§3.1) の効果そのもの**で、崩れると全件 list を別の形でやり直す。
- **0 件でも空で返る** — 空応答と「他ファイルしか無い」の両方。
- **空ページで cursor だけ返る応答でも無限ループしない** — cursor が前進しないまま
  回り続けると静かに固まる。1 リクエストで打ち切ることを固定する (§3.6)。
- **cursor が尽きたら終わる** — `cursor: undefined` の応答で止まること。

### 終端確認の 1 リクエスト

対象レコードがページ境界にぴったり収まる場合、PDS は「まだ続きがある」形の cursor を
返すため、**続きが無いことを確かめる 1 リクエスト**が余分に入る。旧 rkey のケースで
`requests` が 2 になるのはこれで、旧レコード数に比例しないので許容している。
