# rangeFetch テスト仕様

## 何を

batch コレクションの 2 つの走査をテストする。

- `listByRkeyPrefix` (Phase 7 p7-2): **rkey が prefix で始まるレコードだけを読む** (= 1 ファイル分)。
- `listBatchFileHeads` (Phase 7 p7-3): **存在する fileId を 1 ファイル 1 リクエストで降順に
  列挙する**。各ファイルにつき**着地した 1 レコード** (最大 rkey = 最大 clock の batch) を返す。

いずれも「正しい結果を返すこと」と「**リクエスト数が repo 全体に比例しないこと**」の両方を
固定する。

## なぜ

Phase 7 の目的は「remote の全件 list をやめる」ことなので、**結果だけを見るテストでは
目的が達成されたかを判定できない** — 全件を読んでから JS で捨てても結果は同じになる。
そのため各ケースで**リクエスト数と渡した cursor 列**を固定する。

走査が依存しているのは ATProto の**契約ではなく PDS 実装の性質** (設計 §6.1):

- `cursor` に検証が無く、rkey として直接比較される → 前回応答由来でない**合成 cursor**で
  任意の rkey 位置へ seek できる。
- `reverse: true` は **rkey 昇順** + `rkey > cursor`。
- 応答の `cursor` は**最後のレコードの rkey そのもの**。

これは p7-0 の実機 spike (設計 §5.1, 全 12 項目 PASS) で確定させた。ここでは
その意味論を模した pager で走査の論理だけを検証する。

また、この関数を `collections.ts` から切り出したのはテスト可能性のためである
(`collections.ts` は `getAgent()` の singleton に依存し、停止条件とリクエスト数を
単体で固定できない)。あわせて「壊れたときの差し替え面」も 1 ファイルに閉じた (§6.1 の緩和 b)。

## どのように

`fakePager(rkeys, pageSize)` が PDS の `listRecords` を模す: `reverse: true` なら rkey 昇順 +
`rkey > cursor`、省略なら降順 + `rkey < cursor` で絞り、`limit` 件返し、cursor に
**最後のレコードの rkey**を入れる。渡された cursor を記録するので、結果とリクエスト数と
seek 位置を同時に検査できる。

### listByRkeyPrefix (p7-2)

- **prefix に合致するものだけを昇順で返す** — 隣接する `v1~A~…` / `v1~C~…` を含めない。
- **prefix を外れた 1 件で止まる** — 対象 2 件の後に 50 件を置き、**1 リクエスト**で
  終わることを固定する。境界検出のための 1 件の読み過ぎは正常動作 (設計 §3.2)。
- **複数ページを cursor で継ぐ** — 7 件 × ページ 3 件で 3 リクエスト。cursor 列が
  前ページ末尾の rkey であることまで固定する (合成 cursor から応答 cursor への
  引き継ぎが崩れると、静かに取りこぼす)。
- **旧 rkey を 1 件も読まない** — 旧形式 (hex UUID) 40 件を混ぜても、合成 cursor が
  それらをまたいで着地するのでリクエスト数が旧レコード数に比例しない。
  **これが `v1~` 前置 (§3.1) の効果そのもの**で、崩れると全件 list を別の形でやり直す。
- **0 件でも空で返る** — 空応答と「他ファイルしか無い」の両方。
- **空ページで cursor だけ返る応答でも無限ループしない** — cursor が前進しないまま
  回り続けると静かに固まる。1 リクエストで打ち切ることを固定する (§3.6)。
- **cursor が尽きたら終わる** — `cursor: undefined` の応答で止まること。

### listBatchFileHeads (p7-3)

fileId は**実データと同じ UUID 固定長**で作る (`fileId('5')` = `5555…`)。長さが違うと
「ある fileId が別の fileId の prefix になる」状況を誤って作ってしまい、実際には成立する
分離が崩れて見える。

- **全 fileId をちょうど 1 回ずつ降順で返す** — 3 ファイル × 3 batch で
  **リクエスト数 4 = ファイル数 + 1**。設計 §3.3 の予測そのものを固定する。
- **各ファイルの着地レコードは最大 clock の 1 件である** (ANA-127 S3 の土台) — 削除の
  検出は「着地レコード = 最大 clock の batch」に乗っている (tombstone は最大 clock + 1 で
  置かれる, `sync/fileDeletion.ts`)。この性質が崩れると、他端末は本体を引くまで削除に
  気づけない。列挙が返す rkey そのものを固定して、性質を目に見える形にしている。
- **1 リクエスト 1 レコードしか要求しない** — `limit` が 1 であることを直接見る。
  ここで batch 本体を落とすと「全件取得の別の形」になる。
- **旧 rkey 領域に落ちたら 1 件見ただけで終わる** — 旧形式 30 件を混ぜても 2 リクエスト。
  止まらないとリクエスト数が旧レコード数に比例し、全件 list を再現してしまう。
- **remote が空なら空で返る** (1 リクエストで判定)。
- **壊れた新形式 rkey は 1 件だけ跨いで進む** — 飛ばす cursor が作れないので、その 1 件分だけ
  cursor を進める。止めると以降のファイルを見落とし、進めないと同じ場所を回り続ける。
  件数は `console.warn` に出す (§3.6)。
- **同じ fileId に再着地したら止まる** — cursor を無視する PDS を模し、前提が崩れても
  無言で回り続けないことを固定する (2 回目で検知)。
- **リクエスト上限を超えたら打ち切る** — 上限は「ファイル数 + 1 で収まる」前提が崩れた
  ことの**検知器**。超過してもその時点までの結果を返して警告する (§3.6)。

### 終端確認の 1 リクエスト

対象レコードがページ境界にぴったり収まる場合、PDS は「まだ続きがある」形の cursor を
返すため、**続きが無いことを確かめる 1 リクエスト**が余分に入る。旧 rkey のケースで
`requests` が 2 になるのはこれで、旧レコード数に比例しないので許容している。
