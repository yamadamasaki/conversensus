# noticeDismissalMapper.test.ts — 閉じた通知のマッピングのテスト仕様

## 何を

閉じた通知 (`NoticeDismissal`) と PDS レコードの相互変換と、rkey の組み立て
(`noticeDismissalRkey`) を検証する (step3 Phase 6 S6-0)。

## なぜ

- **rkey は自分の他の端末と一致しなければならない。**同じ通知を 2 台が閉じたら同じ rkey に
  なって 1 record に畳まれ、別の通知は別の record になって両方残る (設計 Q1: 足すだけの集合)。
  ここが崩れると、閉じた通知が他の端末で出直すか、別の通知の既読を上書きする
- **鍵は rkey にそのまま使えない。**`conflictKeyOf` は区切りに `\u0000` を使い、プロパティ名を
  含めば長さも決まらない。hash して文法と長さに収める
- **他の端末が書いたレコードを読む**ので、境界で検証して壊れたものを落とす (`judgmentMapper` と同じ)

## どのように

### rkey (性質)

全称命題なので性質で書く。

- **どんな鍵でも** rkey の文法 (`[A-Za-z0-9._:~-]`)・長さ (512) に収まり、`<fileId>~` で始まる
  (`listByFile` の prefix 範囲取得に乗る)
- **単射かつ決定的**: 同じ鍵なら同じ rkey、違えば違う rkey (`ra === rb` ⇔ `a === b`)
- 同じ鍵でも File が違えば別の rkey (例)

**生成器**: 実際の鍵の材料に近い小さなプール (`content` / `node` / `a` / `b` / `\u0000` /
300 文字の塊) を 1〜6 個つなぐ。小さいプールなので**同じ鍵や 1 文字違いの鍵を頻繁に引き**、
単射の検査が意味を持つ。300 文字の塊は「鍵が rkey の上限を超えても収まる」ことを引くため。

### 往復と検証

- レコードへ落として戻すと元に戻る (鍵は上の生成器)
- `$type` が付いた PDS の値をそのまま読める
- 壊れたレコード (fileId が UUID でない・鍵が空・日時でない・null) は `null`
