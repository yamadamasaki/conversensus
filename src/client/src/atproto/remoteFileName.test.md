# remoteFileName のテスト仕様

## 何を

他 actor の repo から File の名前を取り出す部分を検証する。**batch 列から今の名前を
決める規則** (`fileNameFromBatches`) と、`<did>/<fileId>` という合成キーの往復。

## なぜ

参加の承認ダイアログは「alice.test さんが, あなたを ファイル "test file" の対話への参加を
依頼しています」と出す。参加コードに載っているのは DID と FileId だけなので、
**名前は依頼者の repo から引くしかない**。

名前は `graph.file` レコードにあると思いたくなるが、**step1 Phase 6 で snapshot を書く口が
無くなった**ので、そのレコードは古い File にしか残っていない (実測: alice の 28 File に
対してレコードは 1 件)。名前は op-log の `file.setName` op にある。

したがって「batch 列から名前を決める」規則が要り、そこには**改名がある**。
最初の `file.setName` で止めると古い名前が出る。これがこのモジュールの中身である。

## どのように

- **最後の改名を採る。**2 件の `file.setName` を置いて、後のものが勝つことを見る
- **順序は clock で決まる。**同じ 2 件を**逆順の配列**で渡して同じ答えになることを見る。
  remote から返る順に依存すると、読むたびに名前が変わる
- **clock が同じときは actor と id で決まる** (`compareByClockActorId`)。
  グラフの projection と同じ全順序でなければ、改名が競合したときに**画面と中身が
  食い違う**。並びを入れ替えても同じ答えになることで見る
- **名前が無ければ `null`。**呼び出し側 (`labelCache`) が fileId を出す
- **渡された配列を並べ替えない。**呼び出し側が同じ配列を別の用途に使う
- **合成キーは最後の `/` で割る。**DID には `:` はあるが `/` は無い。`did:plc:x:y` の
  ような形でも repo 側が壊れないことを見る

## 引かなかったもの

- **`readRemoteFileName` そのもの** (ネットワークを叩く部分)。`batches.listByFile` を
  直接 import して束ねているので、単体で触るにはモジュールのモックが要る。
  このリポジトリでは `mock.module` がプロセス全体に効いて無関係なテストを壊した経緯が
  あるので (2026-09-01)、**規則の部分だけを切り出して**そちらを検証している。
  レコード → batch の変換は `batchMapper.test.ts` が持つ
- **性質 (PBT) にしていない。**「順序に依らない」は性質として書けるが、
  `compareByClockActorId` の全順序性は `unified` 側が既に持っている。
  ここで検証したいのは「その全順序を使っていること」で、例で足りる
