# labelCache のテスト仕様

## 何を

**id を人が読める名前に解決する一般機構**を検証する。まとめて引くこと、引き直さないこと、
引けなかったときの見せ方、覚えたものを捨てられること。

## なぜ

記録に残すのは id、人に見せるのは名前で、**この 2 つは常に食い違う**。

| 記録 | 表示 | 解決の口 |
|---|---|---|
| DID | ハンドル名 | `describeRepo` |
| FileId | ファイル名 | File のレコード |

名前を記録に持つことはできない — ハンドル名は付け替えられ、ファイル名は変わるので、
**記録した瞬間の名前は後から嘘になる**。かといって画面に DID を出すわけにもいかない。
したがって「id で持ち、見せる直前に引く」以外に道が無く、その引き方が画面ごとに
ばらばらだと、同じ DID を行数だけ引いたり、失敗したときの見せ方が場所ごとに違ったりする。
**引き方を 1 つに決めるためのモジュール**なので、決めたことがテストの対象になる。

## どのように

- **まとめて引く**: 同じ id を 3 つ並べても `fetch` は 1 回・1 件しか受け取らない。
  「依頼者」列は同じ DID が何行にも出るので、ここを素通しにすると行数だけ飛ぶ
- **引き直さない**: 2 度目の `resolve` には未知の id だけが渡る。引く必要が無ければ
  `fetch` を呼ばない (空の問い合わせを投げない)
- **解決できない id は id をそのまま返す**: 空欄にすると「引けなかった」のか
  「そもそも無い」のかが区別できない。`fallback` で見せ方は変えられる
- **失敗しても投げない**: `fetch` が例外を投げても `resolve` は返る。
  **名前が出ないことは、一覧が出ないことより遥かに軽い**。ただし黙らない (`console.warn`)
- **失敗を覚え込まない**: 引けなかった id は次の `resolve` でもう一度引く。
  失敗を「解決できない」として覚えると、通信が戻っても名前が出ないままになる
- **`peek`**: 引かずに今わかっている範囲で答える。解決前は id が返る
- **`forget`**: 覚えた分を捨てて引き直せる。ハンドル名の付け替えがあるので要る

## 引かなかったもの

- **並行呼び出しの重複排除**。同じ id への `resolve` が同時に 2 本走ると `fetch` も
  2 回飛ぶ。名前を引くのはダイアログを開いた瞬間だけで、そこが並行になる経路が
  今は無い。**必要になってから足す** (in-flight の Promise を持つ形になる)
- **TTL**。ハンドル名は変わるが、変わったことをこちらから知る術が無い。
  `forget` を明示的に呼ぶ設計にしてある
- 性質 (PBT) にしていない。主張が「あらゆる入力で」の形ではなく、
  「引く / 引かない」の分岐そのものが対象で、例で尽きる
