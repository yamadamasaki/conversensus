# InvitationDialog.test.tsx / ParticipateDialog.test.tsx — 名簿の UI のテスト仕様

## 何を

招待ダイアログ (一覧 + 新規招待) と参加ダイアログ (参加コードの貼り付け) を検証する。

## なぜ

**このコンポーネントに判断を持たせない**ことを固定するのが主目的である。

どの action が押せるかは `rosterView` が決めており、その条件は畳み込みの pre 条件と
対応していなければならない。ここに独自の活性判定を書くと、**押せるのに畳み込みで
捨てられる**という状態が生まれる — ユーザから見れば「押したのに何も起きない」である。

同様に、参加コードの検証もここではしない。「貼り間違い」と「古いコード」でユーザに
してもらうことが違うので、理由を出す責任を 1 箇所に集める。

## どのように

### 招待ダイアログ

- **行ごとにアクタ・招待者・状態を出す。**作成者 (genesis) の招待者欄は `—`
- **`available` に無い action はそもそも出さない。**グレイアウトではなく非表示にしてある —
  押せない理由を説明できないボタンを並べても迷わせるだけである
- **action を押すと種類と対象を返す**
- **招待済の行にだけコードのコピーを出す。**コードが無ければ出さない
- **`busy` の間はすべて押せない。**二重送信で同じ判断が 2 回書かれるのを防ぐ

### 読めなかった repo

**黙って隠さない。**「招待したのに相手が出てこない」を説明できる唯一の記録である。
全部読めていれば出さない (常時出ていると意味が薄れる)。

### 新規招待

- **ハンドル名を渡す (前後の空白は落とす)。**DID への解決は呼び出し側が行う —
  名簿に載るのは DID だが、人が入力するのはハンドル名である
- **空欄では何も起きない**

### 参加ダイアログ

- **貼られた文字列をそのまま渡す (前後の空白は落とす)。**検証は呼び出し側である
- **理由をそのまま出す**

## テストしていないもの

- **クリップボードへのコピー。**`navigator.clipboard` は権限とセキュアコンテキストに
  依存し、テスト環境では常に失敗する。失敗時に `window.prompt` へ落とす経路を持たせて
  あるのは、**コードを渡せたと誤解したまま相手を待つのが最悪**だからである
- **実際に名簿が動くこと。**それは `useParticipation` と実機の担当である
