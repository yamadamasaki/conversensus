# imageBlob.test.ts — テスト仕様

## 何をテストするか

`images/imageBlob.ts` — 画像を受け取ってから op に載る参照になるまで
(`saveImageBlob` / `imagePropertiesOf`) と、properties から画像の実体に戻るまで
(`readImageBlobLocation` / `resolveImageUrl`) の判断。

## なぜテストするか

このモジュールは **画像の「置き場」の約束そのもの** である (ANA-116, 設計
`deepse/plans/step1-refinement-ana116-image.md`)。守れないと次の 3 つが起きる。

1. **op-log に載る形が違うと PDS が blob を pin しない。** blob ref は
   `{$type:'blob', ref:{$link}, mimeType, size}` の形でなければならず、`ops` が
   lexicon 上 `unknown` でもこの形なら PDS が pin することを S1 で実測した。
   形が崩れると blob が孤児になり、他端末で画像が出なくなる (step1 で起きていた症状)
2. **書く形と読む形がずれると、作った本人にすら画像が出ない。** 旧 S4 を S3 に統合したのは
   この 2 つが同じ約束の裏表だからで、テストも 1 つのファイルで両方向を固定する
3. **未ログインで落ちてはならない。** 旧実装は表示のたびに `currentDid()` を呼び、
   未ログインでは throw していた。「ローカルだけでも画像が使える」(D5) は要件そのもの

サイズ上限も実測に基づく境界なので、ここで固定する。上限を超えたものを保存すると
S5 の push で必ず失敗し、batch が outbox に詰まり続ける。

## どのようにテストするか

IO の seam (ローカル blob ストア・PDS・キャッシュ) は**引数の `deps` で差し替える**。
`mock.module` を使わないのは、bun のそれがテストファイルをまたいでグローバルに効き、
他のテストを壊すためである (`ImageNode.test.tsx` の注記と同じ理由)。

`URL.createObjectURL` はスタブに差し替える。テスト環境の実装差に左右されず
「blob: の URL を返したかどうか」だけを見るためである。
**このモジュールは URL を revoke しない** — 解放は URL を持つ `ImageNode` の責務であり、
`fromCache` の真偽で「revoke してよいか」を伝えるところまでがここの契約である。

CID は S2 で実機 PDS から取得した実在のベクタ (`hello` の CID) を使う。
形式が本物であることに意味があるので、それらしい文字列を作らない。

### 観点ごとの意図

**`readImageBlobLocation` (読む形)**

- **新形式を読む / `size` が無くても読む**: 読み取りは書き込みより緩くしてある。
  旧データや他端末が書いたものを開けなくする理由が無い
- **旧形式の flat なキーを読む**: `imageBlobCid` / `imageBlobMimeType` は step0 〜
  step1 初期のデータに実在する。移行はしない (非目標) ので、読めることが互換の全部
- **新形式が旧形式より優先**: 両方あるときに古い方を見ると、更新が反映されない
- **`$type` が `blob` でない / `$link` が空**: blob ref と誤認して壊れた cid で
  取りに行かないこと。`{cid, mimeType}` の 2 キー形式を禁じているのと同じ趣旨
- **旧形式は cid と mimeType が揃って初めて有効**: 片方だけでは実体を引けない

**`saveImageBlob` (書く形)**

- **返す参照の形**: `$type` / `ref.$link` / `mimeType` / `size` の 4 つが揃うこと。
  `size` は現行の Cmd+V 経路が落としていた値で、3 経路を 1 関数に寄せた理由の 1 つ
- **キャッシュへ入れる**: 保存直後に `GET /blobs/:cid` を待たずに表示できること
- **上限超過は保存せずに弾く / 上限ちょうどは通す**: 境界は PDS の実測値
  (5 MiB ちょうどまで通り、+1 バイトで拒否される)。`put` が呼ばれないことまで見るのは、
  「弾く」が読み込み前に効いていることの確認である
- **画像でないものを弾く**: S6 で `ImageNode` へ直接落とす経路が増えるため、
  呼び出し側のフィルタに頼らない
- **保存の失敗をそのまま伝える**: 旧実装は `console.error` で握り潰しており、
  ユーザーには「落としたのに何も起きない」としか見えなかった (D7)

**`resolveImageUrl` (解決順序 D4 の 1〜3)**

- **1 で止まる / 2 で止まる**: 後段を呼ばないことまで見る。順序が守られないと
  ローカルにある画像のために PDS へ出て行き、オフラインで表示できなくなる
- **未ログインは 2 まで**: `undefined` を返し、**throw しない**。呼び出し元は
  そこで旧データへ落ちる。「無い」は他端末が作った画像で普通に起こる
- **PDS から取れた実体をローカルへ書き戻す**: 次回以降 PDS を触らずに済む。
  書き戻しは表示を待たせないので、テストでも解決後にマイクロタスクを消化して確かめる
- **書き戻しの失敗は表示を妨げない**: best effort であることの固定
- **PDS の取得自体の失敗は投げる**: 書き戻し (握り潰す) と取得 (投げる) の区別。
  呼び出し元 (`ImageNode`) がログに出す

**`collectImageBlobRefs` (送信前に上げる対象を決める, S5)**

- **`properties.image` の blob ref を集める / 同じ cid は 1 つに畳む**: 同じ画像を
  貼り直しても upload は 1 回で足りる (実体は content-addressed で 1 つ)
- **`node.setProperties` も見る**: 差し替え経路 (ANA-117 / S6) で入る op である。
  「作成時だけ」と決め打つと、差し替えた画像だけ pin されない形で壊れる
- **`properties` を持たない op / 画像でない properties を無視する**: 走査対象は
  op の判別共用体全体なので、`properties` の有無で落ちないことを固定する
- **旧 flat 形式 (`imageBlobCid`) は集めない**: PDS から見ればただの文字列で
  pin の対象にならないため、先に上げる意味が無い

**`createPdsBlobUploader` (PDS への先出し, D5)**

- **ローカルの実体を PDS へ上げる**: 送るのはローカル blob ストアから読んだバイト列。
  op に載っているのは参照だけなので、実体の出所はここしかない
- **同じ cid は 2 回目以降上げない**: flush や再送のたびに実体を往復させない。
  記憶はセッション単位で、provider ごと作り直されるので別 repo へ持ち越さない
- **画像を含まない op では PDS を触らない**: 大多数の batch で往復を増やさない
- **ローカルに実体が無ければ飛ばす (投げない)**: この端末では上げようがない。
  レコード側は PDS に既にあれば通り、無ければ push が失敗して未同期のまま残る。
  ここで投げると後者を先取りしてしまう (警告は出す)
- **PDS が別の cid を返したら投げる**: CID はバイト列から決まる (S1 U2) ので、
  食い違いは別の実体を上げたことを意味する。進めば参照先が pin されないレコードができる
- **食い違いで投げた cid は上げ済みにしない**: 再送で上げ直せること。
  「失敗したのに覚えている」と、以後その画像は永久に上がらない

**`replaceImageProperties` / `imagePropertiesChange` (差し替え, S6)**

- **新しい blob ref を image キーに置く / 古い blob ref を上書きする**: 差し替えの本体
- **画像以外の properties は残す**: `node.setProperties` は**置換**意味論なので
  (`events/toUnified.ts` の冒頭に既知の制約として書かれている), 差分だけを載せると
  projection で他の properties が消える。返すのは常に置き換え後の全体である
- **旧形式の画像キーは落とす**: 新しい画像が古いものを置き換えるので残す意味が無い。
  とりわけ `imageDataUrl` (base64) を持ち回すと, 差し替えのたびに base64 が新しい op へ
  載り直してレコード上限 (約 1 MB) に当たる — S3 で止めたことが復活してしまう
- **元の properties を書き換えない**: 呼び出し側は React の state を渡すので,
  破壊的に触ると再描画されない変更が生まれる
- **`from` は差し替え前の全体**: `invertEvent` は from と to を入れ替えるだけなので,
  片方が差分だと undo で properties が欠ける
- **旧形式の base64 は from / to のどちらにも残さない**: `to` から落とすだけでは
  足りない。`from` は差し替え前の全体なので, 旧形式のまま載せると**undo の op に
  base64 が乗る** (レビュー R3)。移行後の参照を両側に載せる

**`migrateLegacyImageProperties` (旧形式の移行, レビュー R3)**

`imageDataUrl` (base64) を持つノードを**触ったときだけ**, その場で blob 参照へ移す。
op に base64 を載せない一方で, 単に落とすと旧形式には blob 参照が無いため
**画像そのものが失われる**。両方を避けるための関数なので, 次を固定する。

- **base64 を blob へ移して参照に差し替える**: 移行の本体
- **移す実体は data URL のバイト列と MIME である**: ここを取り違えると別の画像が
  保存され, cid も変わる。`AAECAw==` が `[0, 1, 2, 3]` に戻ることまで見る
- **旧形式が無ければ保存を呼ばない**: 大多数のノードは新形式なので, 触るたびに
  ローカルへ書き戻すのは無駄である
- **新形式が既にあれば base64 は捨てるだけ**: 表示の解決順序 (D4) で新形式が勝つので,
  base64 は既に使われていない。保存も要らない
- **読めない base64 / data URL でない値は落とすだけ**: 表示できない値を op へ運ぶ
  理由が無い。ここで投げると, 壊れたノードに触った瞬間に編集ができなくなる
- **保存が失敗したら投げる**: 握り潰すと base64 が残ったまま op が組まれてしまう。
  呼び出し元 (`replaceNodeImage` / `commitUrl`) が利用者へ見せる
- **元の properties を書き換えない**: React の state を渡されるため

## ここでテストしないこと

- **upload とレコード書込の順序**: 保証しているのは `AtprotoSyncProvider` なので
  `atprotoSyncProvider.test.ts` の領分である

- **`ImageNode` の描画と Object URL の解放タイミング**: React の effect の話なので
  `ImageNode.test.tsx` の領分
- **貼り付け先の選び方**: `images/pasteTarget.test.ts` の領分
