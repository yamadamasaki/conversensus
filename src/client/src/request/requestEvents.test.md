# requestEvents.test.ts — 依頼の操作のテスト仕様

## 何を

`requestEvents.ts` (応答を求める node の操作 → GraphEvent: 送る・閉じる・開き直す・宛先・答える、と
答えを置く所) を検証する (agent 段 4 R3、設計 agent-actor.md D7・D12)。

## なぜ

system の property (`sent`・`closed`・`addressee`・`answers`) を書く口はここだけで、画面の「依頼」の区画と
MCP の専用の道具の両方が使う。ここが間違うと、送ったのに状態が下書きのまま・答えたのに未回答、になる。
答えは node と edge を**1 つの batch**で書かないと、edge が届く前の間、答えの無い node が宙に浮く。

## どのように

- **操作 → op**: 送ると `sent` が 1 増える / 閉じると `closed = true`、開き直すと `closed` を消す /
  宛先を変える (重なりは 1 つに) / 答えるは `node.add`・`node.setLayout`・`edge.add` の 1 batch で、edge に
  `answers` = 今の送った回数
- **できないこと**: 応答を求める node でなければ何もできない / 閉じた依頼は送れず答えられない /
  下書きには答えられない / 閉じたものは閉じられず、閉じていないものは開き直せない
- **答えを置く所**: 最初の答えは依頼の右、次の答えはその下
- **性質: 操作の列と状態**。どんな操作の列でも (できない操作は飛ばす — 画面がボタンを出さないのと同じ)、
  各時点の導出した状態が、最後にした操作と合う: 閉じたら閉じた、送ったら (前に答えがあっても) 未回答、
  答えたら回答あり、開き直したら閉じる前の状態。操作は依頼の一生の全称命題なので性質で書く
  - 畳み方 (`fold`) はテストの中に書く: 状態に効く property の変更と、node・edge を足すことだけを畳む
  - 生成器: 4 つの操作を最大 12 回。できない操作が混ざる列も引く (飛ばされることを含めて見る)
