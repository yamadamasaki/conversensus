# fileTransfer テスト仕様

## 何を

`.conversensus` ファイルの**書き出しと読み込み**をテストする (ANA-116 レビュー D1)。
中心は **画像の実体 (blob) の同梱と復元**である。

## なぜ

ノードの properties に載るのは blob 参照 (cid) だけなので、参照だけを書き出すと
**別の端末で開いた瞬間に全画像が「画像を読み込めません」になる**。v4 まではここが
base64 で自己完結していた (それがレコード上限に当たったので ANA-116 で参照へ移した) ため、
**自己完結性の回帰**だった。op-log に base64 を戻さないまま、配布物であるファイルの側で
実体を運ぶ — その約束を固定する。

回帰すると静かに壊れる点が 4 つある。

1. **同梱そのもの**: `blobs` に実体が入らないと、export/import は「参照だけのコピー」に戻る
2. **順序**: import で実体を戻すのは**グラフを送る前**でなければならない。逆順だと
   直後の描画で解決に失敗し、後から入れても再解決の契機が無い
3. **base64 の往復**: 0x00 を含むバイト列が落ちると、壊れた画像が静かにできる (S2 の教訓)
4. **`blobs` を server へ送らないこと**: 送ると op-log へ base64 が入り、
   ANA-116 で直したレコード上限の問題が再発する

## どのように

依存 (`ExportFileDeps` / `ImportFileDeps`) を引数で差し込む。書き出しは `download` を
記録するだけの実装に、読み込みは `put` / `post` の呼び出し列を記録する実装に差し替える。
**書き出した JSON は `parseConversensusFile` で読み直す** — 実際の import 経路と同じ
解釈を通すので、スキーマから外れた形を書いていれば気付ける (id が UUID でなければ
落ちるのもこのため)。

### exportFile

- **参照されている画像の実体を base64 で同梱する**: `blobs` に `{cid, mimeType, data}`
  が入り、`version` が最新であること
- **同じ画像を参照するノードが複数あっても 1 回だけ**: cid で重複排除する。
  ローカルストアの読取も 1 回に畳まれる (同じ実体を何度も base64 化しない)
- **実体がこの端末に無い画像は `missingBlobs` で返す**: 他端末が作って一度も表示して
  いない画像はローカルに無いのが普通なので、書き出し自体は成功させる。
  ただし**黙って落とさない** — 呼び出し側 (`useFileSheetOperations`) が利用者に伝える
- **画像を含まないファイルには `blobs` 欄を付けない**: v4 と同じ見た目のままにする
- **ファイル名の使えない文字を置き換える**: `a/b:c*d` → `a_b_c_d.conversensus`

### importFile

- **実体をローカルへ戻してからグラフを送る**: 呼び出し列が `put → post` の順であること
- **base64 を 0x00 込みでバイト列に戻す**: `[1, 0, 2, 255]` が完全に往復すること
- **`blobs` は server へ送らない**: `post` に渡る値に `blobs` が無いこと
- **実体の書き戻しが失敗しても import は続ける**: `put` が投げても `post` は走る。
  その画像が表示できないだけで、グラフは読める方がよい
- **cid が食い違っても投げない**: content-addressed なので入れた実体は別 cid で残るだけ。
  import 全体を落とす理由にはならない (警告は出す)

### 往復

- **別端末を模したストアでも画像の実体が戻る**: D1 の受入基準そのもの。
  export した JSON を空のストアを持つ端末で import し、バイト列が一致すること
