# ConflictNotice.test.tsx — 競合の通知のテスト仕様 (step2 Phase 3 T4)

## 何を

merge で検出した競合を人に見せる非モーダルの通知。

## なぜ

**ここが無いと T1-T3 の検出は誰にも届かない。**着手前の調査では、競合は
`console.warn` にしか出ておらず `conflicts` を受け取る `.tsx` は 1 つも無かった
(設計の事実 B)。仕様の 3 段のうち **structure と layout は通知が本体**なので、
検出だけあって通知が無い状態は「検出したが誰にも届かない」で終わる。

## どのように

### モーダルにしない

**layout の競合は日常的に起きる** — 共同編集で二人が同じノードを動かすことは普通にある
(`spec/merging.md` が layout を「通知のみ」にした理由そのもの)。毎回モーダルで止めると
通知が作業の障害物になる。`role="status"` の非モーダルにして、閉じる操作を人に委ねる。

- **モーダルではない**: `aria-modal` を持たないことを固定する。
- **競合が無ければ何も出さない**: 空の通知が出ると、通知そのものが信用されなくなる。

### 3 段の出し分け — ここがこのスライスの主題

件数を並べるだけなら段は要らない。**人の判断が要るのか、結果の報告なのか**が読めることが
3 段にした意味である。

| 種別 | 扱い | 見せ方 |
| --- | --- | --- |
| content | DtR graph を強制起動 | 開いた状態。「どちらを採るかは対話で決めます」 |
| structure | 通知し, 手動で DtR 起動 | 開いた状態。「もう片方の前提を壊しています」 |
| layout | 通知のみ | **畳んだ状態**。「対話は起こしません」 |

- **🔴 3 段を段ごとに分けて出す** / **無い段は出さない**。
- **🔴 段ごとに「どう扱われるか」を書く**。件数の前に扱いを読ませる。
- **🔴 content / structure は開き、layout は畳んで出す**。layout を開いたままにすると、
  通知が layout の一覧で埋まって**決着が要る段が押し出される**。扱いの違いを開閉で表す。
- **並びは content → structure → layout**。急ぐものが上。

### 対象は名前で呼ぶ

- **🔴 id ではなく名前で出す**。`target` は UUID なので、出しても何のことか分からない。
- **名前が引けなければ id を出す**。黙って落とすと「何かが競合した」だけになる。

名前を引くのは呼び出し側 (App) の仕事である。**いま開いているシートからは引けない** —
削除依存の対象はまさに消された要素なので居ない。merge の結果が運ぶ「分岐点での名前」から
引く (`mergeBranch.ts` の `labelsOfConflicts`)。分岐点には必ず在る — 相手がそれを前提に
した op を出せた時点で在ったからである。

### 1 行の言い方

検出側の単位をそのまま反映する。**同じ対象でも単位が違えば別の行**になる。

- content はプロパティ名があればそれを出す (#208 のキー単位)。
- structure は削除依存と並行変更を書き分ける (非対称と対称で起きたことが違う)。
- layout は観点 (位置 / 大きさ / 経路) を書き分ける (T3)。
- **同じ対象の複数の競合を 1 件に潰さない**: 移動とリサイズは別の単位なので 2 行になる。

## 相手が保留した競合の到着 (step2 Phase 3 T7-5)

### なぜ

競合を検出するのは LWW で勝つ側だけなので、**負けた側はこの通知でしか保留を知らない**
(T8 の控えめな印は「変わった」という事実の報告で、決着が要ることは言わない)。
仕様は fork の通知を対話グラフ (DtR) への入口としているので、控えめな印ではなく**この通知に出す**。
T8 の印は残す — 「変わった」と「決着が要る」は別の情報なので、重なりは許容する (2026-09-13 決定)。

### どのように

fork は `makeFork` で本物と同じ形に作る。名前と「何が起きたか」は fork に凍結された記述
(`origin`) から出す — 相手の手元で検出された競合なので、こちらの projection からは引けないことがある。

- **競合が無くても、届いた保留があれば出す**: 見出しは「相手が保留した競合が N 件届きました」。
  検出した競合が 0 件のときに何も出さない既存の規則が、到着を握り潰さないこと
- **1 行の言い方は検出した競合と同じ**: 同じ競合が「検出した」と「相手が保留した」で違う言葉に
  なると、別の出来事に見える
- **競合と並べて出す**: 見出しは検出した競合の件数のまま、到着は別の節として並ぶ
- **名前が無い要素は、無いと分かる形で出す**: 記述の `targetLabel` が空文字のとき

## まだ作らないもの

**DtR graph の起動口** (Phase 6)。ここで起動の見た目だけを作ると、押せないボタンか
何も起きないボタンになる。**行き先ができる T6 (fork) で付ける。**

**通知の畳み方** も持ち越す。同じ競合が繰り返し通知される問題は explicit merge では
起きない — merge は人が押す離散的な操作で、1 回の merge の中では検出側が単位ごとに
1 件へ畳んでいる (`lastByKey`)。**繰り返しが問題になるのは同期のたびに走る implicit
merge (T5) からである。**
