# dragStop のテスト仕様

## 何をテストするか

`dragStop.ts` — ノードのドラッグが終わった時点で **操作ログに何を記録するか** を決める
モジュール。React Flow のドラッグハンドラの引数から, 実際に動いたノードを取り出し,
それぞれについて `NODE_MOVED` (位置だけ変わった) か `NODE_REPARENTED` (親が変わった) を
組み立てる。

公開しているのは 4 つ。

| 関数 | 役割 |
|---|---|
| `draggedNodesOf` | ハンドラの第 2/第 3 引数から, 動いたノードの一覧を取り出す |
| `withDraggedPositions` | 全体のノード配列にドラッグ後の位置を反映する |
| `resolveDropTargets` | ドラッグ対象それぞれの新しい親を解決する (ドラッグ中のハイライト用) |
| `buildDragStopEvents` | ドラッグ確定時に記録するイベント列を組み立てる |

## なぜテストするか

### 1. 複数選択ドラッグの取りこぼし (ANA-124 の残り / S5 の本題)

以前は `onNodeDragStop` の第 2 引数 (掴んだ 1 個) しか見ていなかった。@xyflow/react は
**第 3 引数 `nodes` でドラッグ対象すべて**を渡す (`OnNodeDrag = (event, node, nodes) => void`,
`@xyflow/system` の `getEventHandlerParams` が組み立てる) ので, 複数ノードを選択して
まとめて動かすと **掴んだ 1 個以外の移動が操作ログに載らなかった**。

操作ログが正典なので, 載らない移動は

- 差分に出ない (S2 で layout を差分へ入れても, この分だけ抜ける)
- commit されない → 他の端末にも, merge 先にも伝わらない

という形で失われる。**動いたノードの数だけイベントが出ること**が, このモジュールの
一番大事な性質。

### 2. 位置が変わっていないノードを記録しないこと

React Flow は「動かさずにクリックした」場合もドラッグハンドラを呼ぶ。差分が空でない
ことが commit 可否の判定 (`pendingChanges`) を兼ねているので, 動いていないノードの
`NODE_MOVED` を出すと **何もしていないのに commit できてしまう**。

### 3. イベント間の相互作用 (グループ境界の再計算)

`NODE_REPARENTED` を適用すると `applyEvent` の中で `recalculateParentBounds` が走り,
子が余白 (`GROUP_PADDING` / `GROUP_TITLE_HEIGHT`) より内側にいるとき **グループ自身の
position が動く**。したがって複数ノードを同じグループへまとめて落とすと,
2 個目以降の相対座標を「元のグループ位置」から求めると**ずれる**。

`buildDragStopEvents` は直前までのイベントを適用した状態に対して次を組み立てることで
これを避けている。この性質は実装を読んだだけでは気付きにくいので, 数値で固定する。

### 4. ハイライトと実際の移動先が一致すること

ドラッグ中のハイライト (`onNodeDrag`) と確定 (`onNodeDragStop`) が違うドロップ先を
選ぶと, 見えていたものと結果が食い違う。両者が同じ `resolveDropTarget` を共用している
ことを, 結果の一致で確かめる。

## どのようにテストするか

純関数なので React Flow の描画は一切使わない。ノードは `Node` 型のリテラルを組み立て,
`measured` を明示する (未測定だと既定値へフォールバックし, 中心の計算がぼやける)。

**ドラッグ後の状態は「同じ id・違う position のノード」で表す** (`dragged` ヘルパ)。
これは React Flow が実際に渡してくる形と同じ — `getEventHandlerParams` は元のノードを
spread して `position` だけ差し替えた配列を作る。

期待値は座標の数値で書く。`toMatchObject` を使い, `makeEventBase` が生成する
`id` / `timestamp` は比較対象から外す。

### ケース一覧

| # | 対象 | 確かめること |
|---|---|---|
| 1 | `draggedNodesOf` | 第 3 引数があればそれを使う / 空のときだけ掴んだノードで補う |
| 2 | `withDraggedPositions` | position だけ差し替わる / `measured` など他は元のノードのものが残る |
| 3 | `buildDragStopEvents` | **動いた 2 個の両方に `NODE_MOVED` が出る** (S5 の受入基準) |
| 4 | 〃 | 単独ドラッグは 1 件だけ (従来の振る舞いの回帰) |
| 5 | 〃 | 位置が変わっていなければ 0 件 |
| 6 | 〃 | ドラッグ開始位置が控えられていなければ 0 件 |
| 7 | 〃 | グループへ入ると `NODE_REPARENTED`, 相対座標へ直る |
| 8 | 〃 | 複数まとめてグループへ落とすと全員分出る |
| 9 | 〃 | **先のイベントでグループがずれても後のノードの相対座標が合う** |
| 10 | 〃 | グループから出ると `newParentId` が undefined になり絶対座標へ戻る |
| 11 | 〃 | グループ内で動かしただけなら `NODE_MOVED` のまま |
| 12 | `resolveDropTargets` | ドロップ先は**ノードごとにそのノード自身の位置**で決まる |
| 13 | 〃 | 確定時 (`buildDragStopEvents`) と同じ結果になる |

### ケース 9 の数値

グループ `g1` は (400,0) / 400x300。n1 を絶対 (405,5) へ落とすと
相対 (5,5)。余白は左 `GROUP_PADDING` = 20, 上 `GROUP_TITLE_HEIGHT` + `GROUP_PADDING` = 50
なので, グループは左へ 15・上へ 45 広がり position が (385,-45) になる。
このとき n2 の絶対座標 (600,200) の相対座標は **(215,245)**。
元の (400,0) を基準にすると (200,200) となり, 上下に 45 ずれる。

### ケース 12 の設計判断

複数選択のドロップ先を「掴んだノードの結果を全員へ適用する」形にはしていない。
それをすると, ポインタから離れた位置にあるノードが**見た目と無関係なグループへ入る**。
また選択の中に「解決先グループの祖先」が混ざると循環になる。
ノードごとに自分の中心で解決すれば, `resolveDropTarget` が自分と自分の子孫を候補から
外すので循環も起きない。

## 積み残し

- **undo の粒度**。複数選択ドラッグは今のところ**ノード 1 個につき 1 イベント**なので,
  undo も 1 個ずつ戻る。まとめて戻したければ `NODES_DELETED` のような複数形イベント
  (`NODES_MOVED`) が要る。操作ログの記録漏れという穴自体は塞がっているので, 別課題とする
