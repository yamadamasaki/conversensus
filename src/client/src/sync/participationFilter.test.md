# participationFilter テスト仕様 (step2 Phase 2 S2 / step3 Phase 1 D5)

対象: `participationFilter.ts` — 参加期間の外の batch を、グラフの畳み込みに**入れる前に**
落とす述語。
設計: [step2 Phase 2](../../../../deepse/plans/step2-phase2-sync.md) §3 /
スパイク: [u6-p2-report](../../../../deepse/spikes/u6-p2-report.md)。

## 何をテストするか

**判断の畳み込みの結果を、グラフの畳み込みの入口の述語に翻訳する**ところだけである。
期間そのものの導出 (`periodsOf`) は `participation.test.ts` の担当である。ここでは
**期間の判定の意味論** (step3 Phase 1 D5) と、その上に乗る 3 つの判断を固定する。

1. 判定に使う DID は **batch の著者** (`<did>#<deviceId>` の DID 部分) である
2. **genesis は期間判定の対象外**である
3. 名簿にいない DID は落ちる

## なぜこの形なのか

### 期間の入力を「出来事の列」から与える

テストの名簿は `history` (出来事の列) だけを持ち、期間は書かない。**畳み込みが通る道と
同じ道を通す**ためである。Phase 1 で `history` を「参加期間の列」から「出来事の列」に
広げ、期間は `periodsOf` の導出にした (両方持つと書き込み先が 2 つになる)。テストが期間を
直に置くと、その導出を迂回して「期間の形」を二重に定義してしまう。

### 期間は因果で判定する (step3 Phase 1 D5)

batch がある期間の中で書かれた ⇔

1. **期間を開いた判断 (genesis / accept / reopen) が、その batch の因果の過去にある**
2. 閉じているなら、**その batch が、閉じた判断 (resign / revoke) の因果の過去にある**

2 が要点で、**取り消した人が見ていた操作までが有効**になる。step2 は期間を clock の区間
(`from <= clock < to`) で判定していて、取り消した人の clock と取り消された人の batch の clock
という、**別の actor の clock どうしを比べていた** (step3-entry §2.1 の 4 つ目の限界)。
🔴 の 2 件は clock で判定すると答えが逆になる例である — 取り消した人が見ていた clock の
大きい編集は通し、見ていなかった clock の小さい編集は落とす。

fixture の判断は因果の点 (`pt(actor, seq, deps)`) で書く。取り消しの `deps` が
「取り消した人が見ていたもの」である。グラフの batch の clock は既定で seq と同じにし、
**clock を見ないこと**を示すテストだけが別に与える。判断ログとグラフは連番を共有するので、
同じ actor の判断とグラフの batch が同じ seq を持つことは無い。

clock の区間に戻す変異で、🔴 の 2 件と「別端末で承認を受け取る前に書いた」が落ちる。

### 再参加の谷

`accept → revoke → invite → accept` で期間が 2 つ開く。**間の谷に落ちた op は取り込まない。**
これが「参加していた期間の op-log **だけを**同期する」の実質である。仕様の再参加時の
同期義務 (ワークフロー 6-3) はこの谷の存在を前提にしている。

### genesis を通すのは仕様ではなく構造の要請である

`GENESIS_ACTOR` は DID ではないので、どの参加期間にも入らない。しかし genesis は
**File の起源**であって誰かの判断ではない。落とすと、承認した側が起源を持たない op-log を
畳むことになり、シートが 1 枚も立ち上がらない。S0 の送信側フィルタが genesis を対象外に
しているのと同じ扱いで、**送信と受信の両方で同じ理由**である。

## テストケース

### `isWithinParticipation`

| ケース | 何を固定するか |
|---|---|
| 期間を開いた判断の後は通す | 承認の後に書いた |
| 参加より前は落とす | 参加する前に相手が書いた op は自分のグラフに入らない |
| 取り消した人が見ていたものは通し、見ていなかったものは落とす | **完了基準 3 の観測点** |
| 🔴 見ていたなら clock が取り消しより大きくても通す | clock の区間なら落ちる |
| 🔴 見ていなかったなら clock が取り消しより小さくても落とす | clock の区間なら通ってしまい、取り消された人の編集が誰の手元でも残る |
| 自分で辞めたなら辞める前の編集がちょうど入る | 辞退は自分の点なので同じ actor の seq で切れる |
| 再参加すると通り、間の谷は落ちる | 期間は複数開く。谷が落ちることが「期間だけ同期する」の実質 |
| 名簿にいない DID は落とす | 参加していない actor の op は入らない (`'local'` を返す未ログインの batch もここで落ちる) |
| 判定は DID 部分で行う | 相手の端末が増えても名簿は DID 単位である |
| 別端末で承認を受け取る前に書いたものは落とす | 同じ人でも、承認が見えていない端末の編集は参加してから書いたものではない |
| genesis は通す | 期間を持たないが File の起源なので対象外にする |
| 依頼されただけの actor は落とす | 参加期間が 1 つも開いていない |

### `filterByParticipation`

| ケース | 何を固定するか |
|---|---|
| 通る batch だけを入力順序を保って返す | 並べ替えはここではしない (順序の権威は `orderBatches`) |
| 空入力は空を返す | |

## テストしていないこと

- **自分の repo に適用しないこと** — 呼び出し側 (`receiveParticipantBatches` が他 actor の
  分だけを扱い、自分の分は `receiveRemoteBatches` が通す) の責務であり、そちらで固定する。
- **期間の導出そのもの** — `participation.test.ts` (`periodsOf` / `wasParticipatingIn`)。

## 引き取り (`reopen`) の後に何が届くか — 実装の記録 (2026-09-05)

**「引き取りはどの状態から始まるのか」への答えをここに固定する。**セーフネットの機能な
ので挙動を変える予定は無いが、**どう実装されているかが読めないと、後から静かに変わる**。

- **後から呼ばれた人には「その人が止めた状態 + 引き取った後の変更」だけが届く。**
  引き取りは新しい参加期間を開くだけなので (仕様の決定)、誰もいなかった間の op は
  著者の期間の外に落ちる
- **⚠️ 引き取った本人の手元は巻き戻らない。**このフィルタは**自分の repo には適用しない**
  (呼び出し側の責務)。引き取りは判断ログに op を 1 つ書くだけで、グラフの op-log には
  触らない。したがって、共有を止めた後にローカルで加えた変更もそのまま残る

つまり**両者の projection は食い違う** — 引き取った本人にだけ空白期間の変更が見える。
これは「新しい期間を開くだけ」を選んだことの帰結であり、意図した動作である
(`deepse/requirements/spec/participation.md`「引き取りは『どの状態』から始まるか」)。

2 つ目のテストが固定しているのは「**かけたら何が落ちるか**」であって、かける経路が
あることではない。落ちる中身が変わればこのテストが先に落ちる。

## merge の写しは merge した人の期間で判定する (step3 Phase 1 D2)

merge の写しは merge した人自身の batch なので、`actor` で判定すれば「op-log に積んだ人」の期間になる。
書いた人の期間で見ると、離脱した人の branch を残った人が merge したときに取り込みが落ちる
(step2 ではこのために `restampedBy` を見ていた)。

- bob が書き、bob の離脱 (20) 後に alice が clock 30 で merge した写しは**通る**
- 逆に alice が書き、離脱後の bob が 30 で merge した写しは**落ちる**

「書いた人」(`copyOf.actor`) で判定する実装では結果が入れ替わるので、1 つのテストで両側を見ている。
