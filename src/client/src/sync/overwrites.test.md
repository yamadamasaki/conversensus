# overwrites.test.ts — 上書きの報告 (step2 Phase 3 T8)

## 何をテストするか

`detectOverwrites` が「**私が書いたものが、届いた編集で別の値になった**」を拾えること、
および `accumulateOverwrites` がその報告を受信サイクルをまたいで溜められること。

## なぜテストするか

### 通知の向きを直すのがこの機能の存在理由である

T5 の検出は `clock(自分) >= clock(新着)` のときだけ発火する。LWW も clock 順なので
**検出する側 = LWW で勝つ側**になり、実 PDS で
「**自分の編集が残った人にだけ通知が出て、上書きされた人には何も出ない**」ことを確認した
(設計 `step2-phase3-conflict.md` の「⚠️ 実 PDS で出た観察」)。知らせるべき相手が逆である。

したがってここで確かめるべき中心は「**T5 が出さない側で出ること**」であり、
逆に「**T5 が出す側では出さないこと**」である。両者は補集合でなければならない —
重なれば同じ 1 つの出来事が「競合しました」と「変わりました」の 2 つの言い方で出る。
`🔴` を付けたのはこの補集合性そのものを固定するテストである。

### 「競合」と言わないことに意味がある

`clock(自分) < clock(新着)` は、相手が私の op を**見た上で**直した可能性を排除しない
(Lamport が言えるのは対偶の側だけである)。だから並行だったとは主張せず、事実だけを言う。
テストの名前も「競合」ではなく「報告」で書いてある。**偽陽性という概念が無い**ので、
「余計に出た」を落とすテストは存在しない — 代わりに「**二重に出さない**」を落とす。

## どのようにテストするか

### 例で書く (性質にしない)

主張が「あらゆる入力で」の形をしていない。中心は**境界の位置**
(`clock < oldestIncoming` か否か) と**言い方の切り分け**で、どちらも
「この形の入力ではこう分類される」という具体的な命題である。往復も冪等も畳み込みも無い。

境界そのものは 3 本の例で挟んである — 私の編集が新着より**古い** (報告する) /
**同値** (しない、T5 の担当) / **古いのと新しいのが両方ある** (しない、T5 が出す)。

### 生成器ではなく、clock の値そのものを設計する

`clock` を 2 と 5 に固定してあるのは、**境界 (`oldestIncoming = 5`) をまたぐ**ことを
読む人に見せるためである。ランダムに引くと、たまたま境界を跨がない組ばかりを引いて
「報告される」側しか通らないテストになりうる。

### 押さえた分岐と、その理由

| テスト | 何が壊れると落ちるか |
| --- | --- |
| 相手が見ていた私の編集を書き換えた → 報告 | 検出そのもの。ここが通らなければ機能が無い |
| 相手に見えていなかった → 報告しない | T5 と重なる。同じことが 2 通りの言い方で出る |
| 古い編集と新しい編集の両方がある → 報告しない | **clock で絞らず全部を `ours` に渡している**理由。単位ごとに「私の最後の値」を引かないと、既に競合として出た単位についてもっと古い値が拾われる |
| 私の最後の値が相手と同じ → 報告しない | 上と対になる。「競合の集合を引き算する」実装では落とせない (値が同じなら競合も出ないので、引く相手が無い) |
| 他人どうしの上書き → 報告しない | 「**あなたが**書いた」の判定 |
| 同じ人の別端末 → 報告する | actor (`did#deviceId`) 単位で見ると、自分の別端末が「他人」になる。読むのは端末ではなく人である |
| layout も報告する | **T8 を今やる理由の半分**。layout は fork にならないので、fork の同期 (T7) に委ねると負けた側に永遠に伝わらない |
| 移動とリサイズは別単位 | `LayoutAspect` の粒度 (T3) をここでも守る |
| 削除は報告しない | 意図した範囲外。「別の値になった」の言い方に乗らない (消えたものは「別の値」ではない) |
| 相手が何度も直しても 1 件 | `mergeBranches` は相手の op を 1 つずつ返す。畳まないと「3 回直された」が 3 行になる |
| プロパティは 1 つずつが単位 | ANA-208 の粒度をここでも守る |
| つなぎ替えは structure | 3 段のうち structure も報告に乗ること |

### 溜めることを別に試す

`accumulateOverwrites` は**画面の決着 (自動では開かない印にする) から出た要求**である。
検出は競合と同じく 1 度きり — 次のサイクルではその batch は手元にあり `incoming` に
入らない — なので、溜めないと**人が見に行く前に消える**。3 本で押さえた:
溜まること (名前も引き継ぐこと)、同じ単位は後の方で置き換わること、
0 件では束を潰さないこと。

## テストしないこと

- **`mergeBranches` の中身**。単位の割り方・値の比較は `merge.test.ts` の担当である。
  ここは「どの op を `ours` に渡し、結果をどの条件で残すか」だけを見る
- **incoming に自分の batch が混じる場合**。`receiveParticipantBatches` は自分の repo を
  読まない (`receiveRemoteBatches` の担当) ので、この経路では起こらない
- **画面の出し方**。`OverwriteNotice.test.tsx` の担当である
