# overwrites.test.ts — 上書きの報告 (step2 Phase 3 T8 / step3 Phase 1 D4)

## 何をテストするか

`detectOverwrites` が「**私が書いたものが、届いた編集で別の値になった**」を拾えること、
および `accumulateOverwrites` がその報告を受信サイクルをまたいで溜められること。

## なぜテストするか

### 見た上で直された人に知らせるのがこの機能の存在理由である

競合 (T5) は「互いに相手を見ずに書いた組」だけを拾う。相手が私の書いたものを**見た上で**
別の値にしたときは競合ではないので何も出ず、上書きされた人は気づけない。ここが拾う。

したがってここで確かめるべき中心は「**見た上で直された組で出ること**」であり、
逆に「**並行な組 (T5 が出す側) では出さないこと**」である。両者は排他でなければならない —
重なれば同じ 1 つの出来事が「競合しました」と「変わりました」の 2 つの言い方で出る。
`🔴` を付けたのはこの排他性そのものを固定するテストである。どの履歴でも排他であることは
`conflicts.test.ts` の性質が押さえている。

step2 は境界を「新着の最小 clock」で引いていたので、純粋な並行でも clock の大小で
こちらに振られていた (step3-entry §2.1)。いまは組の因果の関係 (`relationOfPair` が `seen`)
だけで決まる。

### 「競合」と言わないことに意味がある

相手は私の値を見た上で直している。だから並行だったとは主張せず、事実だけを言う。
テストの名前も「競合」ではなく「報告」で書いてある。代わりに「**二重に出さない**」を落とす。

## どのようにテストするか

### 例で書く

個々の分岐 (別端末、layout、削除、畳み方) は具体的な形で固定する方が読みやすい。
境界の全称命題 (排他) は `conflicts.test.ts` の性質の側にある。

fixture の `deps` は**その batch を書いたときに見ていたもの**である。相手が私の l2 を
見ていたことは `SAW_L2` で書く。境界は 3 本の例で挟んである — 相手が私の編集を**見ていた**
(報告する) / **見ていない** (しない、T5 の担当) / **古い方だけ見ていた** (しない、新しい方と
並行なので T5 が出す)。

### 押さえた分岐と、その理由

| テスト | 何が壊れると落ちるか |
| --- | --- |
| 相手が見ていた私の編集を書き換えた → 報告 | 検出そのもの。ここが通らなければ機能が無い |
| 相手に見えていなかった → 報告しない | T5 と重なる。同じことが 2 通りの言い方で出る |
| 古い編集だけを相手が見ていた → 報告しない | **自分の op を全部 `ours` に渡している**理由。単位ごとに「私の最後の値」を引かないと、既に競合として出た単位についてもっと古い値が拾われる |
| 私の最後の値が相手と同じ → 報告しない | 上と対になる。「競合の集合を引き算する」実装では落とせない (値が同じなら競合も出ないので、引く相手が無い) |
| 他人どうしの上書き → 報告しない | 「**あなたが**書いた」の判定 |
| 同じ人の別端末 → 報告する | actor (`did#deviceId`) 単位で見ると、自分の別端末が「他人」になる。読むのは端末ではなく人である |
| layout も報告する | **T8 を今やる理由の半分**。layout は fork にならないので、fork の同期 (T7) に委ねると上書きされた人に永遠に伝わらない |
| 移動とリサイズは別単位 | `LayoutAspect` の粒度 (T3) をここでも守る |
| 削除は報告しない | 意図した範囲外。「別の値になった」の言い方に乗らない (消えたものは「別の値」ではない) |
| 相手が何度も直しても 1 件 | `mergeBranches` は相手の op を 1 つずつ返す。畳まないと「3 回直された」が 3 行になる |
| プロパティは 1 つずつが単位 | ANA-208 の粒度をここでも守る |
| つなぎ替えは structure | 3 段のうち structure も報告に乗ること |

### 溜めることを別に試す

`accumulateOverwrites` は**画面の決着 (自動では開かない印にする) から出た要求**である。
検出は競合と同じく 1 度きり — 次のサイクルではその batch は手元にあり `incoming` に
入らない — なので、溜めないと**人が見に行く前に消える**。3 本で押さえた:
溜まること (名前も引き継ぐこと)、同じ単位は後の方で置き換わること、
0 件では束を潰さないこと。

## テストしないこと

- **`mergeBranches` の中身**。単位の割り方・値の比較は `merge.test.ts` の担当である。
  ここは「どの op を `ours` に渡し、結果をどの条件で残すか」だけを見る
- **incoming に自分の batch が混じる場合**。`receiveParticipantBatches` は自分の repo を
  読まない (`receiveRemoteBatches` の担当) ので、この経路では起こらない
- **画面の出し方**。`OverwriteNotice.test.tsx` の担当である
