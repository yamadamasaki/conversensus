# writeForks — 競合から fork を書く (step2 Phase 3 T6)

> 単体テストは `receiveParticipantBatches.test.ts` に置いてある。fork を書くのは受信の
> 一部であり、**検出と同じ受信の中で完結する**ことが性質そのものだからである
> (理由は検出時点の状態でしか凍結できない)。器の側だけを切り出して試すと、その順序が
> 見えなくなる。

## 何を守るか

| | なぜ |
| --- | --- |
| 🔴 人の判断が要る競合には fork を書く | 書かないと同期のたびに再計算され、解決したはずの fork が毎回復活する |
| 🔴 同じ競合に fork は 1 つだけ | 上と同じ理由の裏側。**T5 の「新着だけ検出する」に頼らない** — 二度と復活しないことは fork を書くと決めた理由そのものなので、器の側でも保証する |
| 🔴 layout では fork を作らない | 「通知のみで DtR graph は起動しない」種別なので、保留する判断そのものが無い |

判定は `requiresConfirmation` を explicit merge と共有する。**どちらも「人の判断が要るか」を
問うている** — 取り込む前に問うか、保留として記録するか、という違いだけである。

## 凍結の中身は受信経路でも確かめる

`fork.test.md` が `makeFork` の側を押さえているので、ここで見るのは**受信の文脈で正しい
値が入るか**である。

- `trunkFileId` / `sheetId` がぶら下がる先として正しいこと。シートは**対立した batch から
  引く** — content batch は必ず `sheetId` を持つ (§3.1) ので、どちらかから取れる。
  取れない競合は fork にしない (branch は per-sheet なので置き場所が決まらない)。
- `origin.ours.actor` が私、`origin.theirs.actor` が相手になること。**私から見た
  ours/theirs がそのまま actor に落ちる**ことの確認である。
- `origin.baseAt` が検出時点のログ先端であること。
- `origin.targetLabel` が**分岐点での見え方**であること (削除された対象は適用後の
  グラフには居ない)。

## 通知

fork を書いたことは通知に出す (`ConflictNotice` の `forkCount`)。**通知だけでは消えて
しまう** — 後から「何でこれが生じたんだ?」に答えられるのは記録の方である。

explicit merge では 0 になる。人が押した merge は保留ではなく取り込みだからである。
