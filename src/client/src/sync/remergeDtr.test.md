# remergeDtr.test.ts

## 何を

DtR の再 merge — 関門 (`canStartRemerge`) と、それを通ったときの取り込み
(`remergeDtr`) を検証する。

## なぜ

**再 merge は trunk を書き換える。**しかも op-log は追記のみで revert の経路が無いので、
「まだ通してはいけないもの」を通したら取り返しがつかない。関門はそのための装置である。

仕様は 2 つの条件を挙げる。

> 呼び出された actor 全員が承認したら (**そして, その後の変更がなければ**),
> 再 merge が可能になる

**この 2 つは効かせる場所が違う**、というのがこのモジュールの設計の中心である。

| 条件 | どこで効かせるか | なぜ |
| --- | --- | --- |
| 承認が揃っている | **ここと、畳み込みの手前の両方** | trunk を書き換えるので端末をまたいで一致しなければならない。早まって書いても `admissibleBatches` が落とす (二重の守り) |
| その後の変更がない | **ここだけ** | 仕様は「再 merge が**可能になる**条件」として書いており、捨てる pre 条件としては書いていない。判定に解決 branch の op-log の先端が要るので、表示のたびに別のログを読むことになる |

**後者を畳み込みに委ねなくて安全な理由**も併せて記す — 変更があったのに書いてしまっても、
承認の条件は依然として畳み込みが判定するので、**勝手に trunk が書き換わることはない**。

## どのように

### 関門を純粋な述語として切り出す

`canStartRemerge(dtr, resolveTip)` は I/O を持たない。読み込みと混ぜると
「**読めなかったから通らなかった**」のか「**規則が効いたのか**」がテストから区別できない。
分けてあるので、規則そのものを変異試験で固定できる。

固定するのは 3 つ。

- **承認が揃っていなければ通さない** (`notApproved`)。保留の状態である
- **🔴 承認の後に解決グラフが動いていたら通さない** (`changedAfterApproval`)。
  承認した人が見たものと、取り込む内容が違う
- **同着は通す**。解決 branch の先端が `satisfiedAt` と同じなら「その後の変更」は無い。
  `canRemergeAt` が同着を**通さない**のと**逆**であることに注意 — あちらは「承認がこの操作
  より前か」を問い、こちらは「承認の後に動いたか」を問う。同じ clock の比較でも向きが違う

### 新しい merge 機構を作らない

解決グラフは branch なので (決めたこと 10)、取り込みは `mergeBranchOnOplog` そのものである。
ここが足すのは関門と **merge コミットへの DtR の刻印**だけで、再スタンプ・べき等性・
競合検出は既存の経路が担う。テストは「関門を通ったら委譲していること」と
「**`dtrId` が渡っていること**」を見る — 刻印が落ちると、承認を経ていない再 merge を
projection の手前で落とせなくなる (印を辿る鎖が切れる)。

「再び競合したら繰り返す」に特別な仕掛けは無い。返ってくる `conflicts` が非空なら
DtR をもう一度起こせばよいので、**ここでは競合の有無を判断しない**。

### 通らなければ何も書かない

関門で止めたときに `mergeBranchOnOplog` を呼んでいないことを見る。理由を返すのは、
呼び出し側がなぜ進めないかをそのまま人に言えるようにするためである
(「まだ全員の承認が揃っていない」「承認の後に解決が変わった」)。
