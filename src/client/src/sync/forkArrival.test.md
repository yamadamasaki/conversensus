# forkArrival テスト仕様 (step2 Phase 3 T7-5)

## 何を

- `detectArrivedForks`: 受信で初めて現れた、**相手が書いた** fork を見つける
- `accumulateArrivedForks`: 見つけた fork を受信サイクルをまたいで溜める

## なぜ

implicit merge の競合を検出するのは **LWW で勝つ側だけ**である (Phase 3 の実 PDS 観察)。
勝った側は競合の通知を見て fork を書くが、負けた側には T8 の控えめな印しか出ない。
**判断を保留した競合があることを片側しか知らない。**仕様 (`spec/merging.md`) は
「implicit merging は merge できない場合には fork し、actor にはそれを通知する」と定めていて、
関係者は参加者全員である。fork は trunk の op-log に載って相手に届く (T7-1) ので、
その到着を通知すれば両側に揃う。

通知する範囲を誤ると 2 方向に壊れる。

- **広すぎる**: 自分が書いた fork、手元に既にある fork まで出すと、同じ保留が毎サイクル通知され、
  通知が信用されなくなる (T8 で避けた事態)
- **狭すぎる**: 負けた側に届かないなら、この機能の意味が無い

## どのように

fork は手書きせず、**本物の経路で作る** — `makeFork` で作り、T7-1 の記録口 (`branchMetaRecorder`) と
`graphEventToBatch` で op-log の batch にする。`foldBranches` は fork の記述をスキーマで検証するので、
形を手で書くと検証で落ちて普通の branch に化け、「届かない」をテストが見逃す。

### detectArrivedForks

- **受信で初めて現れた相手の fork を返す**
- **同じ競合の fork を手元に持っていれば返さない**: 両側が同時に検出した場合。id が違っても
  `conflictKey` が同じなら同じ競合で、畳み込みも 1 つに畳む
- **このサイクルで自分が書いた fork は返さない**: それは競合の通知が既に伝えている
- **既に受け取った fork は次のサイクルで返さない**: 受信は毎回全件を読むので、新着に絞らないと
  毎サイクル出る
- **届いた時点で削除されている fork は返さない**: 畳み込みが見えなくするものは届いていないのと同じ
- **別の競合の fork はそれぞれ返す**: 鍵で比べていることの対照

### accumulateArrivedForks

- **受信サイクルをまたいで溜める**: 競合の通知は検出のたびに置き換わるので、同じ入れ物だと
  次の検出で消える
- **同じ競合は先に届いた方を残す**: 記述は検出時点で凍結されたものなので、別の参加者の記述に
  差し替える理由が無い
- **何も届かなければ溜めてある束をそのまま返す**: 同じ参照を返して再描画を起こさない
