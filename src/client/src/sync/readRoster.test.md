# readRoster.test.ts — 名簿の読み出しのテスト仕様

## 何を

`readRoster` (起点から広げて他 actor の判断ログを集め、名簿に畳む) を検証する。

## なぜ

**名簿は自分の repo だけでは作れない。**「a が a' を招待した」op は a の repo にあり、
「a' が承認した」op は a' の repo にある。**op は書いた本人の repo にしかない**からである。

したがって誰の repo を読むかは名簿が決めるが、その名簿は読んだ結果で決まる —
**不動点計算**になる (`deepse/architecture/step2.md` §2)。素朴に書くと回り続けるので、
どこで止めるかを決める必要がある。ここが Phase 1 で最も判断の多い箇所である。

## どのように

### 起点だけでは名簿が作れない

- **承認は被招待者の repo にあるので、起点だけ読むと invited のまま。**`passes: 0` は
  被招待者が「本当に自分が招待されたか」を確かめる用途に対応する
- **1 パス広げると被招待者の承認が見える**
- **招待されただけで承認していない actor の repo も読む。**広げる先を participating だけに
  すると、承認を**永久に見つけられない** — 承認する前の actor は participating に居ないので、
  その repo を読む理由が生まれない。invited も広げる先に含めるのが要点である

### 1 パスで止める

**既定は 1 パス。**名簿の食い違いは正常な状態だと仕様が決めているので、収束を待つ必要が
無い。収束まで回すとラウンドトリップが名簿の深さに比例する。

- **2 ホップ先の承認は見えない。**A が B を招待し、B が C を招待して C が承認した場合、
  1 パスでは C の repo を読まないので C は invited のままである。「まだ同期していない」と
  同じことで、次のサイクルで追いつく
- **パスを増やせば追いつく**
- **広がりが止まれば残りのパスは走らない。**起点しか居なければ 1 回読んで終わる
- **同じ repo を 2 度読まない**

### 招待された側の起点 — 実機で発覚した穴

**自分の repo には承認しか無い。**genesis も invite も招待者の repo にあるので、起点を
自分自身にすると**辿る先が無く、名簿が空になる**。単体テストは判断ログを注入して閉じて
いたので気づかず、実 PDS で 2 つの repo に散らばらせて初めて出た。

`accept` が持つ `inviter` が「自分 → 招待者」の辺である。これは **pre 条件には使わない**
— 承認が有効かどうかは「招待済の集合に居るか」だけで決まる。検証に使うと、再招待で
招待者が変わったときに正当な承認が落ちる。あくまで読む先を示すだけの値である。

**辿る先は畳み込みの結果ではなく生の op から取る。**起点が自分のとき、最初の畳み込みでは
招待がまだ見えないので**承認は必ず捨てられる**。畳み込みの結果から辿ると、そこで止まる。

### 起点は自分とは限らない

- **被招待者は招待者の repo を起点にして、自分への招待を確かめられる。**「読む資格は
  名簿への所属と独立」— B はまだ参加者でないのに A の repo を読む
- **起点と繋がっていない genesis は読まれない。**`participation.genesis` を自己申告に
  してよい理由がこれである。誰かが勝手に genesis を宣言していても、起点から辿れなければ
  存在しないのと同じである

### 読めない repo があっても名簿を返す

相手の PDS が一時的に応答しないことは正常に起こり、そのとき「読めた範囲の名簿」は依然として
意味を持つ。ただし**黙って落とすと「招待したのに相手が参加者にならない」が理由不明のまま
残る**ので、`unreadable` として返して見せる。`rejected` と同じ方針である。

### 取り消しは広げた先で見つかる

**パス数を増やすと参加者は減りうる。**広げた先に `revoke` があれば、1 パスでは参加者だった
actor が 2 パスでは外れる。単調ではないことを固定しておく — 「パスを増やすほど参加者が
増える」と思い込むと、減ったときにバグと誤認する。

### 離脱した actor の repo も読む — 実機で発覚した穴 (step2 Phase 2)

**取り消すと、その人が参加していた事実そのものが見えなくなっていた。**

A が B を取り消すと、B は `participating` からも `invited` からも外れる。広げる先が
その 2 つだけだと、**次の読みで B の repo を訪ねなくなる**。B の承認 op は B の repo に
しか無いので、以後の名簿は「依頼されたが承認せずに取り消された人」を見ることになる。
仕様はそれを「その依頼はなかったものとする」と定めているので (`hasEverParticipated` が
false)、**一度参加した人が一覧から丸ごと消える**。参加履歴も同じところで失われる。

固定するのは 2 つである。

- 取り消した後も**離脱者の repo を訪ねる**こと (`reads` に出る)。参加履歴に
  `invite → accept → revoke` の 3 つが載ることまで見る — 承認が載っていることが要点で、
  これが無いと行ごと消える
- 離脱者を訪ねるようにしても、**依頼のまま取り消された人が参加歴を持たない**こと。
  「消えるのが正しい人」と「消えてはいけない人」の区別が壊れていないことの対照である

> 読む repo は離脱者の分だけ増える。名簿は数十人という前提なので許容するが、
> **離脱者は減らない**ので、参加者が入れ替わり続ける File では効いてくる。

## 性質として書いたもの

- **∀ repo の応答順. 同じ名簿になる。**読みは並行なので完了順は毎回違う。名簿が読む順序で
  変わってはならない。repo ごとに違う遅延を入れて完了順を入れ替え、結果と `readRepos` の
  両方が一致することを見る (畳む前に did で整列している)

## 実機で確かめたこと

単体テストは `fetchJudgments` を注入して閉じているので、**実 PDS に置いた判断が別 repo を
またいで同じ名簿に畳めるか**は確かめられていない。それは
`src/client/src/spikes/participation/rosterSmoke.spike.ts` が見る (alice の repo に
genesis + invite、bob の repo に accept を置いて 1 パスで畳む)。
