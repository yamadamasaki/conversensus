# convergence.test.ts — 多アクタの収束のテスト仕様 (step2 Phase 2 S7)

## 何を

**「同じ op 集合を見た 2 つの手元は、同じ projection を出す」**を性質として書く。
対象は `foldParticipation` → `filterByParticipation` → `projectBatches` の**組み合わせ**である。

## なぜ — 対応するモジュールを持たないテストである

このファイルには対になる `convergence.ts` が無い。**命題が組み合わせについてのもの**
だからである。名簿の畳み込みも、期間フィルタも、グラフの projection も、それぞれ単体では
正しい。step2 が主張しているのは**それらを繋いだときに手元によらず同じ結論になる**ことで、
どの 1 モジュールの仕様でもない (アーキテクチャ §2 の不変条件:
「同じ名簿を入力にすれば、誰の手元でも同じグラフになる」)。

**例では書けない。**手元によって受信順は違うので、例で書いてもある 1 つの順序を
確かめたことにしかならない。「取り消した後に 1 回編集してみる」も同じで、取り消しと
編集の並びを 1 通りしか通らない。

## どのように

### 性質

- **∀ 配送順. 同じ op 集合を見た 2 つの手元は同じ projection を出す。**
  判断ログとグラフの batch の**両方**を別々に並べ替えて比べる。名簿が揺れれば
  projection も揺れるので、片方だけでは足りない
- **∀ 参加期間の外の op. 足しても受け取った側の projection は変わらない。**
  **完了基準 3 を全称で述べたもの**である。前提 (`fc.pre`) は「その actor がその時点で
  参加していない」— **自分自身は除く**。ローカル正典にフィルタはかからないので
  (`participationFilter`)、命題の対象外である
- **∀ 配送順. 名簿そのものも配送順に依らない。**上の 2 つの土台を先に固定する

### ⚠️ 生成器の設計 — ここが命題の強さである

判断 op を一様に引くと、乱数が `genesis → invite → accept` の並びを引き当てないので
**名簿がほとんど空のままになる**。実測すると **500 回中 3 回しか参加者が 2 人以上に
ならなかった** — 多アクタの収束を述べたい命題が、ほぼ単独 actor だけを見ていた。

そこで**先頭に有効な導入部 (A が作る → B を招く → B が承認) を固定**し、後ろに乱数の尾を
付ける。導入部の clock を 0-2、尾を 3 以降にしたのは、尾が導入部より前に割り込んで名簿を
空に戻さないためである (割り込みの検証は clock の話ではなく**配送順**の話で、それは性質の
側が担っている)。

直した後の実測 (500 回):

| | 前 | 後 |
| --- | --- | --- |
| 参加者が 2 人以上 | 3 | **257** |
| 離脱した人がいる | 76 | **238** |
| 期間の外の op を足せた (性質 2 の前提が成る) | 312 | 225 |

尾には取り消し・参加取りやめ・引き取り・再依頼が入るので、**離脱と再参加は尾が作る**。

**値は小さなプールから引く** (actor 3 人 / ノード 3 つ / エッジ 2 つ / clock 0-12)。
広く振ると同じノードへの add / setContent / remove が並ばず、畳み込みの衝突
(LWW・カスケード削除) に当たらない。同じ clock を並べて tiebreak (actor → id) を通すのも
狭い範囲を引く理由である。

### ⚠️ 削除を厚く引く (Phase 3 T2 で足した)

add-wins は**削除の意味論そのものを変える**ので、「add-wins にしても ∀ 配送順で同じ
projection になる」がこのスライスの受入基準になった。ところが元の生成器は削除をほとんど
引いていなかった。

原因は名簿のときと同じである。op を一様に引くと `node.add` より前に `node.remove` や
`setContent` が来て無言の no-op になり、**グラフが空のままになる**。加えて `parentId` を
一度も引かないので、**カスケード削除とその復帰は 1 度も通っていなかった**。

直したのは 2 つ。

1. **グラフにも導入部を固定する** (判断ログと同じ手)。A が n1/n2/n3 を作り、n2 を n1 の
   子にして (カスケードの起点)、e1 で n2 と n3 を結ぶ。尾の clock は 3 以降。
2. **op に重みを付ける。**`node.setParent` と `edge.remove` を足し、削除の重みを上げた。
   削除だけを厚くすると今度はグラフが空になり **tombstone を解く側 (add-wins の本体) を
   引かなくなる**ので、「削除 : それ以外」がおよそ 1 : 2 になるようにしてある。

実測 (100 回):

| | 前 | 後 |
| --- | --- | --- |
| tombstone が出た | 10 | **32** |
| エッジの tombstone が出た | 8 | **43** |
| グループができた | 2 | **69** |
| 削除された node が復活した | 10 | **61** |

**`shape` に `removed` を足した。**live だけを比べると **tombstone 側のずれが見えない** —
「両方の手元で消えて見える」だけでは収束の証明にならない。

**この性質が確かめられるのは順序非依存だけである。**add-wins の規則そのもの
(何が tombstone を解くか) は決定論的なので、規則が間違っていても両方の手元は同じ間違いを
する。規則の正しさは `project.test.md` の例が押さえている。ここで生成器を強くした意味は、
**削除の経路を性質が通るようにした**ことにある — 前は 9 割の試行が tombstone を 1 つも
作らずに終わっていた。

### 性質が効いていることを確かめた

書いた性質が何も捕まえないことは起こる。2 つとも**壊して落ちること**を確認した。

- 期間フィルタを素通しにする → **性質 2 が落ちる**
- `orderBatches` の整列を外す → **性質 1 が落ちる**

## 引かなかったもの

- **PDS も分断もモデル化しない** (設計 §7 の「範囲を限る」)。入力は batch 列であって
  ネットワークではない。配送順・分断のモデル化は生成器の設計が本体になり、
  そこが本体になると命題より生成器の議論が長くなる
- **引き取り (`reopen`) が採択される場合は薄い** (500 回中 11 回)。名簿が空のときにしか
  通らず、導入部を固定した分だけ空になりにくいためである。引き取りの意味論そのものは
  `participation.test.md` が例で押さえている
