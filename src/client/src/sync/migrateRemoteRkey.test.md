# migrateRemoteRkey テスト仕様 (step1 Phase 7 p7-4)

対象: `migrateRemoteRkey.ts` — PDS 上の batch レコードを旧 rkey (batchId 単体) から
新 rkey (`v1~<fileId>~<clock>~<batchId>`) へ移行する 1 回きりの手続き。
設計: [step1 Phase 7 (範囲取得・R3)](../../../../deepse/plans/step1-phase7-range-fetch.md) §3.4 / §6.2 / §5.4。

## 何をテストするか

**「取りこぼさずに移行できること」と「やり直せること」**の 2 点に尽きる。

移行が必要な理由は、p7-1〜p7-3 で読取経路が `v1~` prefix の範囲だけを走査するように
なったこと。旧 rkey のレコードは `v1~` より小さいので**新経路の走査に現れない**。
放置しても邪魔にはならないが、**そのレコードにしか無い batch** (別端末が旧版で push し、
この端末がまだ受信していない分) は新経路からは永久に見えなくなる。

手続きは 3 段で、**順序そのものが安全性**である (設計 §6.2):

1. 旧経路 (`pullAllRemoteForMigration`, repo 全件) で 1 回だけ全件受信し、ローカル正典へ取り込む
2. ローカル正典を新 rkey で再 push する
3. 移行済 marker を立てる

1 を飛ばして 2 から始めると、PDS にしか無い batch が prefix 走査の外に取り残され、
ローカル正典にも無いので**復元できない**。よって「1 が失敗したら 2 へ進まない・
marker も立てない」がこのモジュールの中心的な不変条件になる。

## なぜこのテストの形なのか

### remote を rkey をキーにした Map で持つ

移行の眼目は「**レコードが増えないこと**」(rkey が batch の不変属性だけから決まる)
なので、batch 数ではなく**レコード数**で判定できる形にした。旧形式は `rkey = batchId`、
新形式は `batchRkey()` の出力をキーにして、新旧が rkey 空間に併存する実際の姿を再現する。

### まとめ書き (`applyWrites#create`) の非べき等性を fake に写す

p7-4 の実測 (設計 §5.4) で、再 push を `putRecord` の直列から `applyWrites` の
まとめ書きに変えた (200 件で 20.4ms/件 → 1.0ms/件)。ただし `#create` は
**既存 rkey があるとチャンクごと 500 で失敗し、書込は原子的に巻き戻る**。
`putRecord` の「上書き = べき等」とは決定的に性質が違う。

したがって fake の `createRemote` は**衝突したら投げる**ようにしてある。
差分計算 (`pullRemoteForFile` で「すでに新形式で載っている分」を除く) が抜けたら、
やり直し系のテストが例外で落ちる — これが「やり直せる移行」の検知器になっている。

### `pullRemoteForFile` が新形式しか返さない fake にする

差分計算で「旧形式で載っている」を「載っている」と数えてしまうと、移行が何も
書かずに marker を立てて完了する = **移行しないまま移行済になる**。fake は rkey の
prefix で絞ることでこの誤りを再現できないようにはせず、**実装が正しく新形式だけを
見ていること**を前提として固定している。

## テストケース

### `migrateRemoteRkey`

| ケース | 何を固定するか |
|---|---|
| 旧 rkey にしか無い batch を取り込んでから新 rkey で再 push する | 手続きの本体。未受信 (`a2`) がローカル正典に入り、**取り込んだ分を含めて**新形式で載ること。書いた rkey 列そのものを固定する |
| 2 回実行してもレコードが増えない (rkey の決定論性) | 受入基準 §5-2。marker を消しての再実行で**1 件も書かない**こと、レコード集合が同一であること、旧レコードが消えていない (§2.2 非目標) こと |
| 部分的に失敗したあとのやり直しで、載っていない分だけを書く | §6.2「marker が立つ前なら何度でもやり直せる」。1 回目に載った FILE_A は触らず FILE_B だけを書く。まとめ書きが非べき等な以上、やり直しの安全性は差分計算に懸かる |
| marker が立っていれば何もしない | 移行は起動のたびに走る位置にあるので、marker が効かないと毎回 repo 全件 list が走る |
| 全件受信が失敗したら再 push へ進まず marker も立てない | §6.2 の中心。例外をそのまま外へ出し、push を 1 件もせず、marker も立てない |
| 再 push が失敗したら marker を立てない (部分成功は許容) | 途中まで書けていても壊れない (べき等な差分やり直しが回収する)。marker が立たないことだけを保証する |
| remote に無いローカル専用ファイルは push しない | 移行は「PDS 上の旧形式レコードを載せ替える」作業。未同期のローカルファイルを送るのは通常の catch-up の担当で、移行のついでに上げてしまわない。**読みにも行かない**ことを `fetchedFor` で固定 |
| presentation だけの batch は再 push されない (D7) | remote leg のフィルタ (`filterBatchesForRemote`) は移行でも例外にしない |
| remote が空なら何も書かず marker だけ立てる | 移行すべきものが無い = 移行済。次回以降 repo 全件 list を実行しない |
| 新 rkey のレコードだけの repo でも安全に通る | p7-1 以降のクライアントで作られた repo。追記も書込も起きず、レコードが増えない |
| 複数ファイルを fileId ごとに 1 回ずつ束ねて追記する | 追記は fileId 単位に束ねる (1 batch = 1 リクエストにしない) |
| 所要時間を返す | 移行コストの実測 (§6.3) に使う値が返ること |

### marker (`hasRkeyMigrated` / `markRkeyMigrated`)

| ケース | 何を固定するか |
|---|---|
| 立てるまでは false、立てたら true | 基本動作 |
| DID ごとに独立する | 別アカウント = 別 repo なので、移行済かどうかも別 |
| キーは DID を含む | 端末 × アカウント単位で残ること (marker は端末ローカルの事実である, §3.4) |
| 保存に失敗しても例外にしない | 移行そのものは成功しているので、marker が残らずに次回もう一度走ること (べき等なので無害) の方が、成功した移行を失敗として扱うより正しい。ただし warn には出す (§3.6) |

## テストしていないこと

- **実 PDS に対する移行** — p7-6 の実機 e2e で行う。ここは in-memory で決定論的に固定する。
- **`applyWrites` の PDS 側の意味論** — 上限 200 件・create の非べき等性・チャンクの原子性は
  投棄前提の spike で実機観測し、設計 §5.4 に記録した。ここではその観測を fake に写している。
- **移行中に通常の送信が並走した場合の競合** — 差分を取った直後に別経路が同じ rkey を
  書くと、そのチャンクが原子的に失敗して移行全体がやり直しになる。marker が立たないので
  次回起動で回収され、データは失われない (テストでは再現しない)。
