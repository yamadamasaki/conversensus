# startDtr.test.ts

## 何を

explicit merge の競合から DtR を強制起動する `startDtrForConflicts` と、その判断を
成している 2 つの述語 (`needsForcedStart` / `defaultCallees`) を検証する。

## なぜ

**起動の線引きと、呼び出し対象の既定値**がここの全部である。どちらも間違えると、
後から直しても**既に書かれた判断ログは直らない** (追記のみ)。

- 線引きを広げすぎると、structure 競合だけで DtR が立ち上がる。仕様は structure を
  「そこから**手動で選択的に**起動」と定めており、自動起動は仕様違反であると同時に、
  日常的に起きる並行編集のたびに対話の場が増えることになる
- 既定値を間違えると、**起動した本人が呼び出し対象から漏れる**ことが起こりうる。
  そうなると `dtr.setCallees` の pre 条件 (発行者が呼び出し対象であること) を満たせず、
  **保留の出口を開けた本人が使えなくなる**

## どのように

### 線引きは `requiresConfirmation` と共有しない

似た述語が既に 2 つある。

| 述語 | 問い | 対象 |
| --- | --- | --- |
| `requiresConfirmation` | 取り込む前に人に問うか | content + structure |
| `needsForcedStart` (ここ) | **自動で DtR を起動するか** | **content だけ** |

`writeForks.ts` が前者を implicit merge 側と共有しているので「同じ線だろう」と寄せたく
なるが、**別の線である**。テストは content 単独 / structure 単独 / 両方 / layout のみ、の
4 つで線の位置を固定する。

### 呼び出し対象には起動した本人を必ず含める

名簿から引くので普通は含まれているが、**名簿が古い・自分が抜けている場合でも含める**。
根拠は上記のとおり「保留の出口を開けた本人が使えなくなる」ことで、これは畳み込み
(`foldDtr` の `issuerNotCallee`) と噛み合った要件である。重複は畳み、順序は安定させる
(記録がそのままログに載るので、端末によって並びが変わると差分が読みにくい)。

### 器は 2 つある (step2 Phase 6 D3)

| | 器 | なぜ |
| --- | --- | --- |
| **dialogue graph** (対話) | trunk の fileId 内の **sheet** | 対話は器を要るが **merge の対象ではない** |
| **resolve graph** (解決) | **branch** | 「競合を解消するために編集できる」= trunk の作業複製そのもの。**再 merge が既存の `mergeBranchOnOplog` で済む** |

**解決 branch は「競合が起きたシート」から切る。**branch は per-sheet なので、対話用に
作ったばかりの sheet から切ると、解決の場が**別物の複製**になってしまう。テストは分岐元が
`sourceSheetId` であることを固定する (変異で確認済み — 対話用 `sheetId` に取り違えると落ちる)。

### 器が先、判断が後

DtR は **2 つのログにまたがって**記録される — 器 (branch / sheet) は trunk の op-log、起動は
判断ログ。順序を逆にすると「器を指しているのに器が無い」判断が書かれる瞬間が生まれる。
テストは呼び出し順 (`branch` → `sheet` → `judgment`) を記録して固定する。
**片方だけが書かれる可能性そのものは消せない** (2 つのログに原子性は無い) が、
**残りやすい側を先に置く**ことはできる。

順序を崩す変異は 4 件のテストを落とした — 順序だけでなく、**判断に載る `resolveBranchId` が
未定義になる**ためである。順序の規則が値の正しさも支えていることが見える。

### 起動しないときは何も書かない

content 競合が無ければ `null` を返し、**器も判断も書かない**。中途半端に器だけ作ると、
DtR の無いシートが File に残る (しかも D5 の除外はそれを DtR と見なさないので、
普通のタブとして並ぶ)。

### fork からの起動 (step2 Phase 6 D4)

仕様の起動 3 — 「implicit merge で競合が生じた場合 → とりあえず fork されるが, 競合が
通知されるので, **そこから手動で選択的に起動**」。D1 (explicit の content 競合) と
**入口だけが違う**。

| | D1 (explicit) | D4 (fork) |
| --- | --- | --- |
| 引き金 | 適用した merge の競合 | **人が通知を見て押す** |
| 線引き | `needsForcedStart` (content だけ) | **しない** — 押された以上は起動する |
| 既定値の供給源 | 名簿 (共同作業者全員) | **凍結記述** (`origin.ours/theirs.actor`) + 本人 |
| 解決 branch の分岐元 | 競合したシート | fork のシート |

**器の作り方と記録の形は同じ**なので `openDtr` に括り出した。分けて持つと片方だけ直す
事故が起きる (T0 で `applicability` の写しが `applyOp` とずれていたのと同じ形)。

**線引きをしないのは意図的である。**種別で拒むと「通知に出ているのに起動できない」という
説明のつかない状態が生まれる。自動起動 (D1) は人の手を介さないから絞る必要があったが、
こちらは人が選んでいる。

**既定値を凍結記述から引く根拠**は仕様にある (`merging.md`「fork に競合の原因を記述する」)。

> ただし一つだけ用途がある。**この fork から DtR graph を起動するときの、呼び出し対象の
> 既定値を供給する**。既定値の供給源であって呼び出し対象そのものではない点は、名簿と同じ。

**畳み直して求めてはならない** — 畳み直すと「今」の競合になり、そもそも競合が消えている
ことがある (設計 事実 E)。テストは「凍結記述の actor が既定値に出る」ことを固定する。

`actor` は端末単位なので **DID へ落とす**。ここを落とさないと、同じ人の 2 台目が別の
呼び出し対象として数えられ、承認が永久に揃わない。

### 器の名前による判別 (step2 Phase 6 D5) — **仮の実装である**

画面が「どれが DtR の器か」を知るために、**名前の接頭辞で当てている**
(`DtR: ` / `DtR 解決: `)。**本来は `dtr.open` の記録 (`sheetId` / `resolveBranchId`) から
引くべきもので、名前は人が変えられる。**畳み込みの結果を画面へ供給する配線を作れば正しく
引けるが、**見せ方は差し替える前提**なので最小コストを採った (利用者判断 2026-09-19)。

**名前を作る場所と判別を同じモジュールに置いた**のは、捨てるときに剥がす範囲を 1 つに
閉じ込めるためである。画面側は述語を呼ぶだけで、接頭辞の文字列を持たない。

固定するのは 4 つ。

- 対話用 sheet / 解決用 branch をそれぞれ判別する
- 通常のシート名・branch 名を DtR と**誤認しない**
- **対話用の名前を branch の判別に通さない** — 接頭辞が別物であること。誤認すると
  サイドバーの印が嘘になる
- **🔴 起動が作る名前は、必ず判別を通る。**生成と判別は同じモジュールにあるが、
  片方だけ直すと**画面から DtR が消える**(あるいは通常の branch が DtR に見える)。
  実際に起動させて出てきた名前で確かめる — 接頭辞の定数を突き合わせるだけでは、
  **生成側が定数を使うのをやめた**ときに気づけない

## テストしていないこと

- **`handleMergeBranch` への配線**。実際に merge の後で呼ばれるか、`roster` から
  参加者が渡るかはフックの結線であり、ここでは見ない
- **structure 競合からの手動起動** (仕様の 2)。起動の口が別に要るので別のスライス
- **fork からの起動** (仕様の 3 / D4)。材料が凍結記述になるので入力の作り方が違う
- **重複起動の防止**。同じ merge を二度押せば DtR は 2 つできる。畳み込みが弾くのは
  「同じ `DtrId` の 2 度目」だけであり、ここは毎回新しい id を振る。merge そのものが
  二度押せないこと (branch は merged になる) に依っている
