# participationCode.test.ts — 参加コードのテスト仕様

## 何を

`encodeParticipationCode` / `decodeParticipationCode` (招待者 DID + 被招待者 DID + fileId を
1 つの文字列に載せる) を検証する。

## なぜ

参加コードは**招待者から被招待者への唯一の受け渡し物**である。仕様は「step2 では参加要請や
参加表明は conversensus の外で何らかの形で行われる」と定めているので、アプリの外を 1 往復
する — メールやチャットに貼られ、改行が混ざり、部分的にコピーされる。

**秘密ではない。**本人以外の承認は名簿の畳み込みの pre 条件で落ちるので、第三者が入手しても
参加できない。したがって暗号的な要求は無く、**署名も検証していない** — 署名を足すより
「招待者の repo にその invite op があるか」を確かめる方が確実で、しかも無料である。

したがってここで守るべきは秘匿ではなく、**壊れた入力で落ちないこと**と、
**壊れ方の区別がつくこと**である。

## どのように

### 往復

- **符号化して読み戻すと元に戻る**
- **前後の空白は落とす。**コピペで改行が混ざるのは日常的に起きるうえ、base64url の
  文字集合に空白は無いので、落としても曖昧さが生じない
- **base64url なので URL に置ける文字だけになる。**`+` `/` `=` が残っていると、
  URL やクエリに載せたときに壊れる (仕様は「URL にエンコードしてもいいかも」と述べている)

### 壊れた入力 — 例外を投げず理由を返す

入力はユーザが貼り付けた**任意の文字列**である。UI が理由で出し分けるので、
「貼り間違い」と「古いバージョンのコード」を混同させない。ユーザにしてもらうことが違う。

- **base64url でない / 空文字 / base64 だが JSON でない** → `malformed`
- **形式バージョンが違う** → `unsupportedVersion`。**項目不足より先に判定する** —
  古いコードは「項目が足りない」形で失敗しうるが、それを `invalidFields` と呼ぶと
  ユーザに「貼り間違えた」と読める
- **項目が欠けている / fileId が UUID でない** → `invalidFields`。fileId が壊れていると
  名簿を読む先が決まらない

## 性質として書いたもの

- **∀ payload. 符号化 → 復号で元に戻る。**DID の書式は方式が複数あり
  (`did:plc:` / `did:web:` / `did:key:`) 固定できない。例で 1 つ選ぶと、**選ばなかった書式で
  壊れても気づけない**
- **∀ 任意の文字列. 復号は例外を投げない。**ユーザが何を貼っても落ちてはならない。
  これは「復号は全域関数である」という主張そのもので、例では確かめようがない

## テストしていないもの

**base64url の実装そのもの** (`btoa` / `atob` の薄い包み) は往復の性質が覆っている。
個別に固定すると、実装を差し替えたときにテストの方が先に壊れる。
