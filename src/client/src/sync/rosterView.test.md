# rosterView.test.ts — 名簿を一覧に整形するテスト仕様

## 何を

`rosterRows` (名簿 + 見る人 → UI の表の行) を検証する。

## なぜ

仕様の UI 例が求めるのは「invite されているアクタと invite しているアクタ, 参加コード,
**状態**, **action** の表」である。**状態と action は名簿そのものではない** — 同じ行でも、
自分の行なら承認でき、他人の行なら取り消せる。**見る人の立場で変わる**。

この導出をコンポーネントに置くと、表を描く関心と「誰が何をできるか」の判断が混ざる。
後者は pre 条件と対応していなければならない (押せてしまって畳み込みで捨てられるより、
押せない方がよい) ので、単体で確かめられる形に切り出してある。

## どのように

### 状態

- **招待済は `sent`、承認済は `accepted`**
- **取り消しは `revoked`、自分から降りたのは `resigned`。**外から見て両者は区別がつかない
  ので、畳み込みの `departed` が覚えている
- **招待されていない actor の承認は `invalid`。**これは名簿の**外**から来る唯一の行である
  — 畳み込みで捨てられるので `participating` にも `invited` にも現れない。
  **`rejected` (捨てた op と理由) を返す設計にしたのは、この 1 行を出すためである**
- **`invalid` は後から正規に招待されたら上書きしない。**「承認しようとして弾かれた人」が
  その後ちゃんと招待されたなら、出すべきは `sent` である
- **他 PDS への招待は一覧に載せない。**名簿に関わったことが一度も無いからである。
  承認だけを `invalid` として拾うのは、「その人が参加しようとした」という事実が
  本人にも招待者にも見えるべきだからで、招待の失敗は招待した側が既に知っている
- **招待者を出す。**作成者 (genesis) には招待者が無い

### action は立場で決まる

| 行 | viewer | できること |
| --- | --- | --- |
| 自分・`sent` | — | `preview` / `accept` |
| 自分・`accepted` | — | `resign` のみ |
| 他人・`sent` or `accepted` | 参加者 | `revoke` |
| 他人 | 参加していない | 何もできない |
| 外れた行 (`revoked` / `resigned`) | — | 何もできない |

- **自分を `revoke` する action は出さない。**`resign` と同じことなので二重に出さない
- **参加していない viewer は他人に何もできない。**取り消しの pre 条件
  (`issuer ∈ participating`) と同じ条件でグレイアウトする

### 並び

**DID 順に並べる。**`Set` / `Map` の反復順に任せると、読み直すたびに表の行が入れ替わりうる。

## 表示名 (step2, 2026-09-04 追加)

**記録は DID、画面はハンドル名**である (`deepse/requirements/spec/participation.md` の図)。
名前を引くのはネットワークを伴うので、`rosterView` 自身は引かない — 引いた結果の
同期の関数 (`labelOf`) を受け取るだけである。これは `foldParticipation` が
`isLocalDid` を受け取るのと同じ形で、理由も同じ (**非同期を持ち込むと決定論が壊れる**)。

- **`rosterDids` は名簿からではなく行から集める。**名簿から集め直すと、行を組む条件と
  食い違ったときに「表には出ているのに名前が引かれていない」DID が生まれる。
  行に出る DID と引く DID が同じものであることを、両方向 (集める / 集めない) で見る
- **`sortRowsByLabel` は DID 順とは違う順序を作る。**テストでは A の DID を最小に、
  ハンドル名を `zoe.test` (最大) にしてあるので、**並べ替えが名前で行われていなければ
  この 2 つは区別できない**
- **名前が引けなかった行は DID の文字列として並ぶ。**順序が乱れることより、
  「引けるまで順序が決まらない」状態を作らないことを採る。`rosterRows` が DID 順で
  返すのはそのためである

## 操作と非表示 (step2, 2026-09-04)

仕様の操作一覧を反映した。

| 状態 | 操作 |
|---|---|
| 依頼中 | 依頼キャンセル (自分の行なら 中身を見る / 承認) |
| 参加中 | 参加取りやめ |
| 離脱中 | 再度参加依頼 |

- **`revoke` は依頼の取り消しと参加の取り消しを兼ねる。**仕様が「承認の**前後を問わず**
  同じ取り消しとして扱う」と定めているので op は 1 つしかなく、**見え分かれるのは文言
  だけ**である (`actionLabel`)。文言を状態から導いていることを、同じ op で 2 つの
  文言が出ることで見る
- **`resign` も文言は「参加取りやめ」。**仕様「自分で辞めたか, 辞めさせられたかは
  問わない」。誰がやったかは参加履歴に出るので、ここで区別する理由が無い
- **`reinvite` は新しい action だが、新しい op ではない。**畳み込みは既にこれを許して
  いる — `invite` の pre は「対象が参加者でないこと」であって「未依頼」ではない。
  したがってテストは「押せること」ではなく「**押せる立場が pre 条件と一致すること**」を
  見る: 参加者は呼べる / 離脱した本人は自分を呼び戻せない / 参加していない viewer は
  呼べない
- **依頼のまま取り消された人は、参加歴が無ければ一覧に出さない** (仕様「その依頼は
  なかったものとする」)。名簿に一度も載ったことが無い人を「離脱中」として並べると、
  依頼を取り消すたびに一覧が伸びていく。**参加歴がある場合は出す**ことを対で見る —
  片方だけだと `hasEverParticipated` を無条件 false にしても通ってしまう


## File の共有状態 (step2 Phase 2, 2026-09-05 実機で発覚)

**取り消されても File は手元に残る。**ローカル正典は自分の写しであって、共有が切れた
からといって消す筋合いは無い。しかし止まるのは取り込みであって表示ではないので、
**何も出さないと「もう同期されない File」が普通の File に見える** (実機で混乱した)。

`fileSharing` は名簿から「いま何人と共有しているか」「自分はまだその 1 人か」を導く。
同期サイクルが毎回名簿を読むので、表示のために名簿を読み直す必要は無い。

| ケース | 何を固定するか |
|---|---|
| 誰とも共有していない File | 参加者 1 人 (自分)。切れていない |
| 共有中の File | 人数が分かる (ダイアログを開かずに「誰かと共有している」が分かる) |
| 取り消された側は「共有が切れている」 | **残った側は切れていない**ことまで見る。状態は見る人ごとに違う |
| 自分で降りた場合も同じ扱い | 「自分で辞めたか, 辞めさせられたかは問わない」(仕様) |
| ⚠️ 名簿が空の File は数えない | 起点 (genesis) の無い古い File では誰も参加者にならない。これを切れている扱いにすると、**共有と無関係な File にまで「同期していません」が出る** |

## 捨てられた判断の知らせ (`describeRejected`)

### なぜ

畳み込みが捨てた op は、**招待だと行を持たない** — 招待された人は名簿のどこにも現れない
からである。理由を出さないと「招待したのに表が空のまま」が原因不明のまま残る
(2026-09-03 に実際に起きた)。

**ただし判断ログは追記しかされない。**一度捨てられた op は永久に残るので、
ログ全体の捨てた op を数えて出すと**一度出た警告が二度と消えない**。実際に消えなく
なった (2026-09-05 実機。名簿の入力欄に自分のハンドルを入れた 1 件が, alice と bob の
両方でずっと出続けた)。

伝えたいのは「**いまの操作が効かなかった**」であって、ログの健康診断ではない
(診断は `scripts/inspect-judgments.ts` の仕事である)。したがって対象は
**書いた本人の、書いたばかりの batch** に限る。

### どのように

- **いま書いた batch が捨てられたら知らせる。**文言もそのまま固定する — 画面に出る文である
- **⚠️ 名簿を開いただけのときは何も出さない。**ここが直した中身である。
  「捨てた op は残っている」ことを先に確かめてから `null` を見る —
  そうしないと「たまたま捨てた op が無いから null」と区別がつかない
- **他人が捨てられた分は、自分の操作として知らせない**
- **いま書いた batch が通っていれば何も出さない**
- **理由ごとにまとめる。**同じ理由で 3 件落ちても 1 つの句にする —
  10 件落ちたときに 10 行出しても読めない
