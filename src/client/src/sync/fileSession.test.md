# FileSession のテスト

## 何を

`FileSession` — File 1 つの書き込み (tap)・同期のサイクル・同期の契機を束ねるもの
(step3 Phase 3 S3-0)。

## なぜ

以前はこの中身が `useEventSyncTap` というフックそのものだった。フックは 1 つのコンポーネントで
1 回しか呼べないので、**同時に開ける File は 1 つ**という前提が React の構造に埋まっていた。
タブと multiple モードは複数の File を同時に開くので、React の外へ出した。

同期のサイクルそのもの (自分の repo → 名簿 → 参加者の repo、競合・上書き・fork の知らせ、
定期同期と可視性、別のタブの書き込み) の振る舞いは、**フックを通して既存の
`useEventSyncTap.test.ts` が固定している** (中身を移しただけなので、そのまま通ることが検証になる)。
ここで見るのは、React の外に出たことで新しく成り立たなければならない性質だけである。

## どのように

PDS は File ごとに batch を持つ偽物 (`FakeRepo`)、ローカル正典は空の偽物で置き、
受信の書き込み口 (`appendReceived`) を記録する。定期同期は発火しない間隔にして、
起動時の 1 回と明示の `syncNow` だけを見る。

- **2 つの File のセッションは、それぞれ自分の File だけを同期する** — 同じ PDS の上で
  2 つ同時に動かし、受信の宛先と `onReceived` の File が混ざらないこと。タブで別々の File を
  開く前提そのものである
- **知らせを差し替えても同期を走らせ直さない** — フックは毎レンダー `setListeners` を呼ぶ。
  そのたびに PDS を読み直すと、レンダーの数だけ相手の repo を叩くことになる。差し替えた後の
  サイクルでは新しい知らせに届くこと
- **止めた後は `online` でも同期しない** — 閉じたタブのセッションが裏で PDS を読み続けないこと
  (契機のリスナが外れていること)

## 流れの合図 (#252)

参加者の PDS の流れ (`LiveSignal`) から合図を受けたときの振る舞い。流れは手で合図を出す代役にする。

- **この File への合図で取りに行き、他の File への合図では取りに行かない。**合図は PDS の全員の書き込みから
  来るので、自分の File のものだけで動く
- **同期の最中に来た合図は、その後にもう 1 度だけ回す。**走っているサイクルに相乗りすると、そのサイクルが
  読み終えた後の書き込みを取りこぼす。合図が続けて来ても、後に回すのは 1 度だけ (合図の数だけ回すと、
  書き込みが続く間 PDS を叩き続ける)。読みを止められる repo で、開いたときの同期の最中に合図を 2 つ出し、
  完了した同期が 2 回 (開いたとき + 後に回した 1 回) であることを見る
- **繋がっている間は延ばした間隔で、切れたら元の間隔で定期同期する。**元の間隔を鳴らない長さに、延ばした
  間隔を短くして、どちらが効いているかを見分ける。繋がり方が変わったことは null の合図で知らされ、次の tick を
  決め直す (セッションは作り直さない)
- 止めた後は合図でも取りに行かない
