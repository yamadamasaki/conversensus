# ensureOwnGenesis のテスト仕様

## 何を

**名簿の起点 (`participation.genesis`) が無い File に、後から起点を置き直す**手続きを検証する。
起点があるか (`hasGenesis`)、置いてよい File か (自分だけで書かれているか)、置いた結果
それまでの招待が有効になるか、の 3 つが対象である。

## なぜ

**dev 環境で実際に壊れた形をテストにしたものである** (2026-09-03)。

招待ボタンを押しても表が空のままだった。PDS を直接見ると招待レコードは 3 件書けており
(`clock` 6, 7, 8)、**起点だけが無かった**。起点が無いと `foldParticipation` は招待を
`issuerNotParticipating` で捨てる — 「最初の 1 人は genesis でしか決まらない」の裏返しである。
そして捨てられた招待は一覧に行を持たない (`rosterRows` が `invalid` として出すのは捨てられた
**承認**だけで、招待された人は名簿のどこにも現れない)。結果、**画面にも console にも
何も出ないまま名簿が永久に空になる**。

起点を書いていたのは `bootstrapParticipation` (step1 で作られた File のための移行) だけで、
これは端末 × DID ごとに 1 回しか走らない。**移行の後に作られた File には誰も起点を置かなかった。**

File 作成時に起点を書く経路を足しても、ログアウト中に作った File (DID がまだ無い) は残る。
そこで**名簿を読むたびに起点の有無を見て、無ければ置く**。単体テストが 1249 件緑のまま
この欠陥が実機まで残ったので、**同じ形を単体で固定する**のがこのファイルの目的である。

## どのように

- **`hasGenesis`**: 起点を含む / 招待だけ / 空、の 3 つ。判断ログは複数 repo 分の和なので、
  「どの repo のものでもよい」を素直に反映して batch 列だけを見る
- **所有の判定**: `fetchBatches` の返す op-log に他人の actor を 1 つ混ぜ、置かないことを見る。
  起点は「この File を作ったのは自分だ」という主張なので、確かめずに書いてはならない
- **べき等**: 2 度呼んで**同じ batch id** になることを見る。rkey は id から決まるので、
  id が同じなら PDS の同じレコードに収束する。id が乱数だと消えないゴミが 2 つ残る
- **後から置けること (回帰)**: 実機と同じ「起点なし + 招待 3 件」を組み、
  - 置く前は `invited` が空で `rejected` が 3 件 `issuerNotParticipating`
  - 置いた後は `participating` に自分がいて `invited` に相手がいて `rejected` が空

  を **`foldParticipation` を通して**確かめる。これが成り立つのは genesis の clock が 0 に
  固定されていて誰にも割り当てられないからで、**後から置いても既存の招待より必ず前に来る**。
  モックした畳み込みではこの性質を検証したことにならないので、本物の fold を通している

## 引かなかったもの

- **性質 (PBT) にしていない。**主張が「あらゆる入力で」の形をしていない — 検証したいのは
  「起点が無ければ置く / 他人の File には置かない」という分岐そのもので、例で尽きる
- `putJudgment` の失敗経路。呼び出し側 (`refresh`) が例外を拾って画面に出すので、
  ここで握り潰す設計を固定してしまわない

## ⚠️ 手元に 1 件も無い File には置かない (2026-09-05)

`isSolelyOwnedBy` は**空の op-log を「自分の File」と答える**。`bootstrapParticipation` の
文脈ではそれが正しい — あちらの入力はローカルに存在する File なので、空は「この端末で
作られたばかり」を意味する。

**こちらでは意味が逆になる。**`ensureOwnGenesis` は名簿を読むたびに呼ばれるので、空は
「そもそも手元に無い」でありうる。**承認した直後の File がまさにそれである** — 判断ログには
承認があるが、グラフの batch はまだ 1 件も来ていない。

そこへ起点を置くと何が起きるか:

1. 作った人の起点が `duplicateGenesis` で捨てられる (起点は File に 1 つ)
2. その人が参加者でなくなる
3. その人が出した依頼が `issuerNotParticipating` で落ちる
4. 依頼が無いので承認も `issuerNotInvited` で落ちる

しかも**起点の clock は 0 に固定**されているので、後から書いても順序で覆せない。
**名簿が壊れたまま固定される。**同じ File を作り直すまで直らない。

したがって「op-log が空なら置かない」を、この層の条件として固定する。
