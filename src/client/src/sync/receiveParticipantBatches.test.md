# receiveParticipantBatches テスト仕様 (step2 Phase 2 S2)

対象: `receiveParticipantBatches.ts` — 他 actor の repo からグラフの op-log を取り込む。
設計: [step2 Phase 2](../../../../deepse/plans/step2-phase2-sync.md) §2〜§3 /
アーキテクチャ: [step2](../../../../deepse/architecture/step2.md) §2。

## 何をテストするか

step1 の同期は自分の repo に閉じていた。ここが**「書くのは自分の repo だけ、読むのは
N 人の repo」の読み側**そのものなので、テストの主題は 3 つになる。

1. **誰の repo を読むか** — 名簿が決める
2. **どこからどこまでを取り込むか** — 参加期間が決める
3. **1 人が読めなかったときに何が起きるか**

## なぜこの形なのか

### 引数が `Participation` から始まる

「読む順序は名簿 → グラフに固定される」(アーキテクチャ §2) は実装の都合ではなく意味論から
出る順序である。名簿が確定する前にグラフを取りに行けないので、**型の形でその順序を強制**
している。テストも名簿を先に組み立てる形になる。

### 自分の repo を読まない

`receiveRemoteBatches` (自分の repo = 別端末の分) と対になる。二重に読んでも
`appendReceivedBatches` のべき等性で無害だが往復が倍になるので、**参加者から自分を除く**
ことを固定する。

### 読む順序を DID 昇順に固定する

`participating` は `Set` なので反復順は挿入順である。挿入順は名簿を読んだ順に依存し、それは
`readRoster` が repo を回った順に依存する。**誰の手元でも同じ結果になるべき**なので、
ここで DID 昇順に整える。テストは挿入順と逆になる名簿を渡してこれを見る
(`readRoster` が結果を DID で並べ直しているのと同じ判断)。

### `outsidePeriod` が 0 でないことは異常ではない

取り消された actor の repo には、取り消し後の op がそのまま残る (相手はそれを消さない)。
この数は**その op が手元に入っていないことの証拠**であり、完了基準 3「参加を取りやめた後、
その操作が相手に反映されなくなる」の観測点である。だから結果に載せる。

### 取り込んでいないときは clock を進めない

`observeRemote` は「取り込んだものより後」を名乗るための Lamport 受信規則である。全部が
期間の外で 1 件も書いていないのに clock だけ進むと、**次に発番する batch が取り込んで
いない編集より後を騙る**。「全部が期間の外なら書き込みに行かない」のケースで、
`appended` だけでなく `observed` も空であることを見ているのはこのためである。

### 1 人の失敗で全体を止めない

相手の PDS が一時的に応答しないことは正常に起こる。読めた分は取り込み、読めなかった相手は
理由とともに返す。名簿の読み出し (`readRoster` の `unreadable`) と揃えた判断である。
黙って落とすと「相手が参加しているのに編集が出てこない」が原因不明のまま残る。

### 集めることと書くことを分けてある

`collectParticipantBatches` (集めるだけ) と `receiveParticipantBatches` (集めて書く) に
分かれているのは、**書く前に見なければならない判断が 1 つある**ためである — 発見経路
(`discoverParticipatingFiles`) は、引いた op-log に `file.remove` があればその File を
materialize してはならない (ANA-127 の remove-wins)。書いてから消す形は取れない
(ローカル正典から File を取り除く口が無く、削除は tombstone でしか表せない)。

書き込みは**1 回にまとめる**。repo ごとに書くと、1 サイクルの間にローカル正典が中途半端な
状態を何度も通る。既読位置を持たないので、途中で落ちても次のサイクルが同じものをもう一度
読む。

## テストケース

### 誰の repo を読むか

| ケース | 何を固定するか |
|---|---|
| 参加者から自分を除いた repo を読む | 自分の repo は `receiveRemoteBatches` の担当 |
| 読む順序を名簿の反復順に依存させない | DID 昇順。誰の手元でも同じ結果になる |
| 参加者が自分だけなら 1 件も読まない | 単独作業の File で余計な往復をしない |

### 参加期間で絞る

| ケース | 何を固定するか |
|---|---|
| 期間の中の batch だけを取り込む | 参加前・参加中・取りやめ後の 3 点を 1 つの repo に混ぜて見る |
| 全部が期間の外なら書き込みに行かない | `appendReceived` を呼ばず、**clock も進めない** |
| 相手の repo にある genesis は期間によらず取り込む | 落とすと承認した側が起源を持たない op-log を畳む |

### 取り込み

| ケース | 何を固定するか |
|---|---|
| 取り込んだ最大 clock で自端末 clock を進める | Lamport 受信規則。**書き込みが成功してから**進める |
| 他ファイル宛の batch は落とす | 孤児 batch を作らない不変条件を rkey 形式の正しさに依存させない (4d 設計 §1.11 D-4)。0 でなければ rkey とボディが食い違っている |
| 2 回呼んでも書き込みは同じ内容になる | 既読位置を持たないので毎回全部読む。べき等性は受信側が担う |

### 1 人の失敗で全体を止めない

| ケース | 何を固定するか |
|---|---|
| 読めなかった repo は理由とともに返し、残りは取り込む | 失敗が名簿の一部で止まり、残りの参加者の編集は届く |

### 競合検出は追記の前に挟む (step2 Phase 3 T5)

分岐点は**受信前の手元の状態**なので、書いてからでは「私が見ていたグラフ」が失われる。
検出そのものの規則は `conflicts.test.md` にある。ここで見るのは経路の側である。

- **新着が手元の編集を壊せば競合として返す**。消された対象の名前も一緒に返る。
  **implicit merge は止めない** — 導出であって判断ではないので、競合があっても取り込みは
  続ける。止めると「相手の編集が届かない」になる。
- **🔴 既に受け取った batch は新着に数えない**。受信は既読位置を持たず毎回全件読むので、
  ここで絞らないと**同じ競合が毎サイクル通知される**。「通知の畳み方」がここで効いている。
- **新着が無ければ検出しない**。
