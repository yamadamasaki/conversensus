# planInvitations のテスト仕様

## 何を

参加依頼を**書く前**に、通る相手と通らない相手を仕分ける手続きを検証する。
仕分けの 4 つの理由 (見つからない / 自分自身 / 既に参加している / 別の PDS) と、
仕分けであって可否判定ではないこと。

## なぜ

**書いても畳み込みが捨てるものを書かない。**見つからないハンドル、既に参加している人、
別 PDS のアカウントは、判断ログに書いたところで pre 条件で落ちる。書いてから捨てるのは
2 つの意味で悪い — 判断ログに永久に残るゴミが増えるし、**なぜ相手が一覧に出ないのかが
画面に出ない** (捨てた理由は `rejectedNote` に出るが、「今押した操作がどうなったか」
としては遅い)。

**通る分は書く。**5 人中 1 人が見つからないときに 4 人分を捨てると打ち直しになる。
これは可否の判定ではなく仕分けである、というのがこのモジュールの性格で、
テストの中心もそこにある。

**なぜ hook から切り出したか。**`useParticipation` は `resolveHandle` や `putJudgment` を
直接 import して束ねているので、単体で触るにはモジュールのモックが要る。この
リポジトリでは `mock.module('zod')` がプロセス全体に効いて無関係なテストを壊した
経緯があるので (2026-09-01)、**モックを増やさずに済む形に切り出す**方を採った。

## どのように

- **4 つの理由をそれぞれ 1 つずつ**。文言もそのまま固定する — これは画面に出る文であって、
  内部のコードではない
- **自分自身は、参加中かどうかの前に止める。**ここが判断の中身である。参加中なら
  `isParticipating` が拾うが、**離脱中の自分は素通りする** — 名簿の入力欄に自分の
  ハンドルを入れて 1 件書かれた (2026-09-05 実機)。畳み込みは必ず捨てるものの、
  捨てられた op は判断ログに永久に残るので、書かせない方に倒す。
  **他の人の分は通す**ことも同時に見る (仕分けであって可否判定ではない)
- **仕分けであることを、混在した入力で見る。**通る 2 人と通らない 1 人を混ぜ、
  `targets` に 2 人・`problems` に 1 件が同時に返ることを確かめる。
  「どれか 1 つでも駄目なら全部駄目」に退化していないか
- **理由は依頼した順に並ぶ。**3 種類を 1 度に混ぜて順序を見る。並びが入れ替わると
  「どれのことを言われているのか」が読み手に分からなくなる
- **重複と空白は落ちる。**`,` 区切りの入力は打ち間違いを含むので、
  引く回数 (`asked`) まで見る — 結果が同じでもリクエストが増えていないか
- **既に依頼済の人は通す。**参加コードの再発行は正当な操作で、畳み込みも
  「既に招待済でも捨てない」と決めている。**通らない側に倒していないこと**を明示する

## 引かなかったもの

- **性質 (PBT) にしていない。**主張は「あらゆる入力で」ではなく理由ごとの分岐の網羅で、
  例で尽きる。ただし「`targets` と `problems` の総数 = 重複を除いた入力の数」は性質に
  できる。仕分けの取りこぼしを捕まえるので、理由が増えたら足す価値がある
- `resolveHandle` / `isLocalDid` が例外を投げる場合。呼び出し側 (`useParticipation`) が
  拾って画面に出すので、ここで握り潰す設計を固定してしまわない
