# appendJudgment.test.ts — 判断 op の書き込みのテスト仕様

## 何を

`appendJudgment` (判断 op を 1 つの batch にまとめて書く) と `maxJudgmentClock` を検証する。

## なぜ

ここが **clock 空間の共有**を成立させる一点である。

pre 条件は「記録された承認が、**この操作より前に**記録されていること」のように「より前」を
含むので、判断ログとグラフの op-log を**同じ物差しで並べられなければならない**
(U6-P2 スパイクの検証 5 — 別空間にすると、承認が済んでいるのに正当な再 merge が落ちる)。

しかも「同じ `LamportClock` を使う」だけでは足りない。tap の clock は**グラフの op-log の
最大値**から seed されるので、判断ログの方が進んでいると衝突する。衝突すると順序は
`(actor, id)` の tiebreak で決まり、「より前」が意図どおりにならない。

**この 2 つが揃って初めて成立する**ので、両方を固定する。

## どのように

### clock

- **グラフと同じ clock から発番する。**独立した採番器を作ると pre 条件の「より前」が壊れる
- **判断ログの方が進んでいれば、そこまで引き上げてから発番する。**引き上げないと同じ clock の
  batch が 2 つできる
- **グラフの方が進んでいれば引き下げない。**`seed` は下限の引き上げなので、既に大きい値には
  影響しない (`observe` と違い +1 しない)
- **連続して書くと単調に増える**

`known` (今わかっている判断ログ) を**引数にして省略できないようにしてある**。既定値を
持たせると、渡し忘れたときにグラフ側の clock だけで発番してしまい、しかも**多くの場合は
たまたま動く** — 判断ログがグラフより進んでいるときにだけ壊れる。

### batch

- **op をまとめて 1 つの batch にする。**判断は原子的である (「招待して同時に別の誰かを
  取り消す」)
- **op が空なら書かない。**語彙上ありえない (`min(1)`) ので、レコードにする前に落とす
