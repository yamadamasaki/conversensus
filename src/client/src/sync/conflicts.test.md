# conflicts.test.ts — implicit merge の競合検出のテスト仕様 (step2 Phase 3 T5)

## 何を

同期で届いた op と手元の op の間の競合を検出する (`detectIncomingConflicts`)。
競合の対象を人が読める名前にする対応表も作る (`labelsOfConflicts`)。

## なぜ

着手前の調査で分かった最大の事実は「**implicit merge は競合を 1 件も検出していない**」
だった。`mergeBranches` の呼び出し元は explicit branch merge の 1 箇所だけで、受信経路には
競合の概念が無かった。共同作業で競合が起きるのは主に implicit merge の側なので、
ここが無いと T1-T4 は branch を使う人にしか効かない。

## 分岐点をどう定めたか

explicit merge の `meta.base.at` に相当するものが無い。**受信前の手元の状態**を分岐点に
する、と決めた (未決 ③, 2026-09-07)。

設計の素直な案 (受信した batch の最小 clock の直前) は実装と噛み合わなかった — 受信は
既読位置を持たず**毎回頭から全件読む**ので、最小 clock は毎回ログの先頭になる。新規分に
限っても、clock は端末をまたぐと単調でないので「その時点の状態」が曖昧である。

受信側の状態を分岐点にすると、**相手が何人いても分岐点は 1 つ**になる。③ が心配していた
「複数 actor から同時に来ると 1 つに畳めない」は構造的に消える。

## ⚠️ ours は「手元の全部」ではない

**実装の途中でここを踏んだ。**手元の op を全部 ours にすると、
**「相手が私の文章を読んで直した」が競合になる** — `lastByKey` は「私の最後の値」と
「相手の新しい値」を比べるので、順次編集がすべて競合として出た (実測)。

絞る根拠は Lamport の保証の対偶である。`a → b` (因果) ならば `clock(a) < clock(b)` なので、
**`clock(m) >= clock(t)` なら `m → t` ではない** — 相手はその op を見ずに `t` を出した。

> **ours = 手元の op のうち、新着の最小 clock 以上のもの**

これで「相手が既に見ていた私の編集」は落ちる。**偽陽性が構造的に出ない。**

境界に最小 clock を使うのは近似である。新着が複数あるとき、より新しい相手の op から見れば
見えていた可能性のある私の op も混じる。**取り逃すよりは出す**方に倒した。

### 片側で取り逃しても、相手側が捕まえる

clock が小さい側は検出しない。**それでよい** — そのとき相手の clock は大きいので相手の手元
では検出され、fork は競合そのものから同一性が導かれるので、相手の書いた fork が同期されて
私にも届く。「相手同士の競合は見ない」と同じ論法である。clock が同値なら両方が検出し、
fork は畳まれる。**テストはこの対称性を 1 件で押さえている** (同じ 2 つの op を、向きを
入れ替えて 2 回検出にかける)。

## テストケース

| 例 | 何を守るか |
| --- | --- |
| 新着が無ければ検出しない | 毎サイクル走るので空振りを軽くする |
| 別のものを触っていれば競合にしない | 偽陽性の基本 |
| 🔴 手元と新着がぶつかれば content の競合 | ours = 手元 / theirs = 新着 の対応も固定する |
| 🔴 新着の削除が手元の前提を壊せば削除依存 | implicit merge 側の S2 |
| 🔴 グループ削除で子への編集を検出 | **分岐点を状態にした意味。**op に書かれているのは親の id だけである |
| 🔴 消された対象の名前が分岐点から引ける | 適用後のグラフには居ない。通知が id しか出せなくなる |
| layout も拾う | 3 段が implicit merge でも効く |
| 🔴 順次編集は競合にしない | **ours を絞る理由そのもの** |
| 🔴 clock が小さい側は検出せず、相手側が検出する | 対で完全であることの確認 |

`labelsOfConflicts` は空文字をそのまま返す (「名前が無い」と「引けなかった」は別の話で、
言い換えは見せる側が決める)。

### 名前の形 (Phase 5 P7)

node は **「ラベル + 本文の先頭」** (`反論: 気温の記録は…`)、edge は label である。
**Phase 5 を Phase 3 T7 より先に入れた理由がここにある** — T4 の競合通知と T8 の上書きの
報告は「どれのことか」を対象の名前で伝えるが、node は名前を持たず markdown の本文が
そのまま出ていた。長い本文のノードは通知の中で識別できない。

**ただしこれは絞り込みであって特定ではない。**ラベルはクラス名の位置づけなので
「反論」は一つのグラフに複数ある。通知から実物のノードを指すのは step3 である。
*本文だけの現状より狭まる*、というのが Phase 5 の効きの正確な大きさである。

- **ラベルがあれば「ラベル: 本文の先頭」**: 両方を出す。ラベルだけでは複数に当たり、
  本文だけでは今までと変わらない。
- **本文が長ければ先頭だけ / 切っていなければ `…` を付けない**: 通知は 1 行なので、
  長い markdown がそのまま流れ込むと読めない。切ったかどうかが見て分かる必要がある。
- **ラベルが空なら「: 」を出さない**: 区切りだけが浮くと名前が壊れて見える。
- **edge は label のまま**: template が当たっていれば種類名 (`支える`) がそのまま名前に
  なる。edge には本文が無いので足すものが無い。

**ここで template を引いていない。**node が `label` を**値として持っている**ためである
(設計 D3 の「label も併せて持つ」)。*op-log を読むだけの側が template を要らない* という
その判断の、主な受益者がここである。

## テストしていないこと

- **相手同士の競合 (Bob vs Carol)**。2 側構造では出ない。上記のとおり、彼らがそれぞれ
  検出して書いた fork が私にも届く。
- **真の並行性の判定**。因果を持たないので近似である (T2 の add-wins と同じ壁)。
  vector clock の導入は op の形と同期量に効く決定なので、未決に積んである。
