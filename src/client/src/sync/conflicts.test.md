# conflicts.test.ts — implicit merge の競合検出のテスト仕様 (step2 Phase 3 T5 / step3 Phase 1 D4)

## 何を

同期で届いた op と手元の op の間の競合を検出する (`detectIncomingConflicts`)。
競合の対象を人が読める名前にする対応表も作る (`labelsOfConflicts`)。

## なぜ

着手前の調査で分かった最大の事実は「**implicit merge は競合を 1 件も検出していない**」
だった。`mergeBranches` の呼び出し元は explicit branch merge の 1 箇所だけで、受信経路には
競合の概念が無かった。共同作業で競合が起きるのは主に implicit merge の側なので、
ここが無いと T1-T4 は branch を使う人にしか効かない。

## 分岐点をどう定めたか

explicit merge の `meta.base.at` に相当するものが無い。**受信前の手元の状態**を分岐点に
する、と決めた (未決 ③, 2026-09-07)。

設計の素直な案 (受信した batch の最小 clock の直前) は実装と噛み合わなかった — 受信は
既読位置を持たず**毎回頭から全件読む**ので、最小 clock は毎回ログの先頭になる。新規分に
限っても、clock は端末をまたぐと単調でないので「その時点の状態」が曖昧である。

受信側の状態を分岐点にすると、**相手が何人いても分岐点は 1 つ**になる。③ が心配していた
「複数 actor から同時に来ると 1 つに畳めない」は構造的に消える。

## 競合は「並行な組」だけ (step3 Phase 1 D4)

手元の op を全部 ours にして `mergeBranches` を当て、出てきた組 (手元の batch, 新着の batch)
のうち**並行なもの**だけを残す (`relationOfPair`)。

**全部を ours にするだけでは足りない** — step2 の実装の途中で踏んだとおり、「相手が私の文章を
読んで直した」が競合になる (`lastByKey` は「私の最後の値」と「相手の新しい値」を比べる)。
それを落とすのが因果の判定である。

### step2 の境界と、その穴

step2 は vector を持たなかったので、Lamport の保証の対偶 (`clock(m) >= clock(t)` なら
`m → t` ではない) で ours を「新着の最小 clock 以上」に絞っていた。対偶は片側でしか
言えないので、

- **clock の小さい側は、並行でも検出できない** (相手の手元で出ることに頼っていた)
- **clock が大きくても、相手が見ていたなら並行ではない**のに競合になりうる
- 境界が「新着の集合」で決まるので、**同じ組が端末によって別の側に振られる**
  (競合 / 上書きの報告, step3-entry §2.1)

いまは組の関係だけで決まるので、**どの端末・どの受信でも同じ組は同じ側に振られ**、
並行は対称なので**当事者は両方とも検出する**。fork は競合そのものから同一性が導かれるので、
両方が書いても畳まれる。

### 性質で書く

「どの履歴でも」の形の主張なので、性質にした (`fast-check`)。2 台の端末 (alice / bob) の
履歴を「書く / 相手の分を全部受け取る」の 4 動作の列として引き、実際の `CausalClock` で
発番する。受け取りのたびに、追記の前に競合と上書きを検出して次の 2 つを確かめる:

- **排他**: 同じ組 (整列した batch id の対) が、別の端末・別の受け取りで反対の側
  (競合 / 上書き) に振られない
- **完全**: 受け手の**いまの値** (単位 A を書いた batch のうち全順序で最後のもの) と並行な
  新着は、どれも競合として出る

生成器の判断:

- **受け取りは「相手の分を全部」**に限る。部分的な配送はここでの問いではない。受け取りを
  混ぜることで clock が片側に偏る履歴が出る (受け取った側は clock が跳ぶ) — step2 の境界が
  取り逃したのはそこである
- **値は毎回違う**ものを書く。同じ値だと差が無いとして組にならず、検出の対象から外れる
- 単位は 1 つ (node A の content) に絞る。単位が増えても組の判定は変わらず、衝突が薄まるだけ

**最初に書いた性質は間違っていた。**「互いの最後の編集を見ていなければ、両方の手元で同じ組が
競合になる」と書いたら反例が出た — bob の最後の編集が、bob の手元で既に alice の別の編集に
上書きされている (その対立は前の受け取りで検出済み) と、alice の新しい編集は bob の
**いまの値**から見て順次編集になる。対称なのは「組の振り分け」であって、「誰の手元で
どの組が比べられるか」ではない。完全性は**いまの値**に対して言う形に直した。

step2 の境界 (新着の最小 clock) に戻す変異で、この性質と下の例 3 件が落ちることを確かめた。

## テストケース

| 例 | 何を守るか |
| --- | --- |
| 新着が無ければ検出しない | 毎サイクル走るので空振りを軽くする |
| 別のものを触っていれば競合にしない | 偽陽性の基本 |
| 🔴 手元と新着がぶつかれば content の競合 | ours = 手元 / theirs = 新着 の対応も固定する |
| 🔴 新着の削除が手元の前提を壊せば削除依存 | implicit merge 側の S2 |
| 🔴 グループ削除で子への編集を検出 | **分岐点を状態にした意味。**op に書かれているのは親の id だけである |
| 🔴 消された対象の名前が分岐点から引ける | 適用後のグラフには居ない。通知が id しか出せなくなる |
| layout も拾う | 3 段が implicit merge でも効く |
| 🔴 順次編集は競合にしない | **組を因果で絞る理由そのもの** |
| 🔴 並行なら clock の大小によらず両方で検出する | step2 では clock の小さい側が空だった |
| 🔴 clock が大きくても、相手が見ていたなら競合にしない | Lamport の clock は因果の必要条件でしかない |
| 新着の方が前 (知っていたが遅れて届いた) なら競合にしない | 3 つ目の関係 (`other`)。因果の知識は batch より先に届きうる |

fixture の `deps` は**その batch を書いたときに見ていたもの**である。相手が分岐点 (A と B を
作った l1) を見ていたことは `SAW_L1` で書く — 見ていなければ、node の追加そのものとも
並行になってしまう。

`labelsOfConflicts` は空文字をそのまま返す (「名前が無い」と「引けなかった」は別の話で、
言い換えは見せる側が決める)。

### 名前の形 (Phase 5 P7)

node は **「ラベル + 本文の先頭」** (`反論: 気温の記録は…`)、edge は label である。
**Phase 5 を Phase 3 T7 より先に入れた理由がここにある** — T4 の競合通知と T8 の上書きの
報告は「どれのことか」を対象の名前で伝えるが、node は名前を持たず markdown の本文が
そのまま出ていた。長い本文のノードは通知の中で識別できない。

**ただしこれは絞り込みであって特定ではない。**ラベルはクラス名の位置づけなので
「反論」は一つのグラフに複数ある。通知から実物のノードを指すのは step3 である。
*本文だけの現状より狭まる*、というのが Phase 5 の効きの正確な大きさである。

- **ラベルがあれば「ラベル: 本文の先頭」**: 両方を出す。ラベルだけでは複数に当たり、
  本文だけでは今までと変わらない。
- **本文が長ければ先頭だけ / 切っていなければ `…` を付けない**: 通知は 1 行なので、
  長い markdown がそのまま流れ込むと読めない。切ったかどうかが見て分かる必要がある。
- **ラベルが空なら「: 」を出さない**: 区切りだけが浮くと名前が壊れて見える。
- **edge は label のまま**: template が当たっていれば種類名 (`支える`) がそのまま名前に
  なる。edge には本文が無いので足すものが無い。

**ここで template を引いていない。**node が `label` を**値として持っている**ためである
(設計 D3 の「label も併せて持つ」)。*op-log を読むだけの側が template を要らない* という
その判断の、主な受益者がここである。

## テストしていないこと

- **3 台以上の配送の順序**。性質の生成器は 2 台で、受け取りは全部か無しかである。第三者の
  検出は届き方で決まる (前に受け取った片側と、いま届いたもう片側) ので、例ではなく
  `receiveParticipantBatches.test.ts` の fork の到着で押さえている。
