# searchSheet.test.ts — シート内検索のテスト仕様

## 何を

`searchSheet.ts` の検索本体 (`searchSheet`) と、それが依っている 3 つの判断 — **何を走査するか / どこまでを 1 件とするか / 抜粋をどう切り出すか** — を検証する。

## なぜ

検索は**壊れても静かである**。落ちも警告も出さず、ただ「見つからない」で終わる。利用者から見ると、書いたはずの文字列が出てこないのか、そもそも無いのかが区別できない。したがって**取りこぼしの方向の誤りが本質的に危ない**のであり、テストの重心はそこに置く。

加えて、検索の範囲は仕様が明示的に狭めている。「自分の projection」「現在表示している sheet, あるいは branch」「時間を遡らない」の 3 つで、これを広げると step 3 に送った話 (op-log の検索、複数グラフの串刺し) を先取りしてしまう。**狭さそのものが仕様である**以上、狭いことを固定する必要がある。

## どのように

### 走査する欄は 3 つで、取り違えると静かに落ちる

| 欄 | node | edge | 備考 |
| --- | --- | --- | --- |
| `label` | ある (template の種別名) | ある | **template が当たっていなければ `undefined`** |
| `content` | **ある (本文)** | 無い | Phase 5 P0 で本文と label の語を分けた |
| `property` の値 | ある | ある | system は除く (後述) |

**`label` と `content` を取り違えないことが要点である。**Phase 5 P0 で「本文は `content` であって `label` ではない」と語を分けたが、検索は両方を走査するので、**片方しか見ていなくても半分はヒットする**。テストは「label だけに含まれる語」「content だけに含まれる語」をそれぞれ別に引いて、両方が独立に効くことを固定する。

**edge に `content` は無い。**node と同じ関数で走査しているので、`'content' in element` の判定を落とすと edge で `undefined` を検索することになる。

### 型は宣言から来る (値から推論しない)

結果一覧が出す「型」は、仕様が求める `property は名前, 型も表示` に対応する。

**値から推論しない** (利用者判断 2026-09-20)。型を指定するのは実装コードか template の
ような拡張であって、入力された値ではない。step 2 は宣言の仕組みを持たないので、
出るのは一律 **`string`** である。**property editor (Phase 4) と同じ規則**で、同じ
プロパティが片方で「日付」、片方で「文字列」に見えてはいけない。

> **⚠️ 当初は `inferPropertyType` で値から推論していた**が、関数ごと撤去した。
> 推論した型を**使う場面が無い**ためで、`2026-09-20` という文字列に「日付」と出すのは
> 宣言されていない型の推測だった。

### system のプロパティは検索に出さない

仕様の property editor は system を「**見えない, 追加/変更/削除できない**」と定めている。画面に出ないものが検索だけで出てくると、**開けない結果**になる — 結果一覧をダブルクリックしても、ハイライトする先の property が画面に無い。

固定するのは 2 つ。

- `app.conversensus.image` のような system は**ヒットしない**
- `jp.co.metabolics.toulmin.kind` のような **extension はヒットする**。仕様は extension を「一部は不可視」としており、既定は見える側である。ここを system と同じ扱いにすると、template の種別で検索できなくなる

判定は `propertyCategory` に任せており、この 2 件はその委譲が効いていることの確認でもある。

### 1 つの要素が複数件になる

同じノードの label と content の両方に検索語が含まれていれば **2 件**である。1 件に畳むと、結果一覧が「どの欄で当たったか」を出せなくなる — それは仕様が要求している情報である (「要素の種類 (node/edge, label/content/property)」)。

**同じ欄の中の 2 つ目以降は拾わない。**`indexOf` は最初の 1 つしか返さない。仕様は「部分一致で検索する」までしか求めておらず、1 つの欄の中での出現回数は問うていない。ここを増やすと結果一覧が同じ要素で埋まる。

### 大小文字のトグル

仕様が挙げるトグルはこれ 1 つである (完全一致と正規表現は step 3 送り)。

- 既定は**無視する**。`caseSensitive` を渡さなければ `Hello` で `hello` が見つかる
- `caseSensitive: true` なら見つからない

**位置は元の文字列の上で数える。**`toLowerCase` した文字列の上で位置を取ると、大小で長さが変わる文字 (トルコ語の `İ` など) でハイライトがずれる。ほとんどの文字では一致するので**テストでは露見しない種類の誤り**であり、コード側のコメントで断ってある。字形の正規化は検索の仕事ではない (→ step 3)。

### 空の検索語は 0 件

空文字列はあらゆる文字列に含まれるので、素直に当てると**全要素がヒットする**。それは検索の結果ではなく一覧である。入力欄が空のまま Enter を押す経路が UI 側にあるので、ここで止める。

**空白だけの検索語は止めない。**空白は正当な検索語である (「A B」で区切りを探す)。`trim` して空になるかで判定すると、空白の検索ができなくなる。

### 抜粋は窓であって全文ではない

仕様は「content の場合は, 前後のテキストも部分的に表示」と求める。markdown ノードの本文は長くなりうるので、そのまま結果一覧へ流すと 1 件で画面が埋まる。

- ヒットの前後 `SNIPPET_CONTEXT` 文字を添える
- **切れている側にだけ省略記号を付ける**。短い文字列で両端に `…` が付くと、実際には全文が見えているのに省略されたように読める
- **`matchStart` は省略記号の分だけ後ろへずれる**。ここを足し忘れると、結果一覧のハイライトが 1 文字ずれる。**先頭でヒットしたときだけ正しく見える**ので、テストは「前が切れている」場合を明示的に引く

### 値の文字列化

仕様「property の値 (文字列に変換して)」。

- 数値・真偽値は `String` に落とす。`42` を `42` で探せる
- **配列は要素を並べる** (`JSON.stringify` ではない)。`["a","b"]` にすると**引用符と角括弧が検索語に混ざる**。人が打つのは `a` であって `"a"` ではない
- 構造体は `JSON.stringify` に落とす。**実際には検索に乗らない** — step 2 で構造体を持つのは `app.conversensus.image` だけで、それは system なので除かれる。それでも落とし先を決めてあるのは、extension が構造体を持ち込んだときに黙って「検索に出てこない」になるより、読める形で出る方がましだからである

### 結果の順序は安定する

node → edge、要素の中では label → content → property。並びが実行のたびに変わると、**同じ検索で結果一覧の見え方が変わる**。`Object.entries` の順序は挿入順なので、properties の中の順序も安定している。

## テストしていないこと

- **branch を開いているときの範囲**。branch を開くと `activeFile.sheets` の当該シートが branch の projection に差し替わるので (`useBranchOperations`)、この関数から見れば同じ `Sheet` である。差し替えそのものは branch 側のテストが見ている
- **op-log の検索**。仕様が step 3 へ送っている。この関数は畳み込んだ後の `Sheet` しか受け取らないので、構造的に遡れない
- **複数シートの串刺し**。同上 (→ step 3)
- **結果一覧の表示とハイライト**。UI のスライスで別に見る
