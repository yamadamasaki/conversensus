# folderTree.test.ts — Folder の木の導出のテスト仕様

## 何を

`buildFolderTree` (Folder・File の置き場・File の一覧 → 表示する木と、書くべき改名) と
`isEmptyFolder` を検証する (step3 Phase 6 S6-2a, 設計 §2.3)。

## なぜ

Folder と置き場は項目ごとに端末間で併合されるので、仕様の制約 (同じ階層で名前が重ならない・行き先が
ある・削除された File は出ない) は**同期の時点で破れうる**。どんな組み合わせが届いても表示でき、
しかも 2 台が同じ結論 (同じ改名) に達しなければならない。改名は書かれる (Q4) ので、2 台が別の名前を
書くと後勝ちで片方が消え、次の同期でまた重なる。

## どのように

### 性質

述べたいのは「**どんな**入力でも」なので性質で書く。

- **File**: 一覧の File はちょうど 1 回ずつ現れ、一覧に無い File は現れない (削除された File は黙って外れる)
- **Folder**: どの Folder もちょうど 1 回ずつ現れる。親が無くても、親が輪になっていても落ちない
- **名前**: 同じ階層の表示名は重ならない
- **入れ子**: 子の親は入力の親である (表示のために親を付け替えるのはトップ・レベルへ出すときだけ)
- **並びに依らない**: Folder と置き場の並びを入れ替えても、同じ木と同じ改名になる。PDS の list の順と
  手元の写しの順は端末ごとに違う
- **収束する**: 出てきた改名を当てて作り直すと改名はもう出ず、表示名も変わらない。2 台が同時に改名を
  書いても同じ値で、次の同期で重ならない

**生成器の判断**: どれも**小さなプール**から引く。

- Folder の id は 5 つ、名前は `a` / `b` / `a (2)` の 3 つ、作成日時は 2 つ。名前が重なる組、作成日時が
  同じで id で順を決める組、改名の候補 (`a (2)`) が既に使われている組を頻繁に引く
- 親はプールの id と**プールに無い id** (= 削除された Folder) から引く。自分自身や互いを親にする輪も引く
- 置き場の Folder にもプールに無い id を混ぜる (行き先の無い File)。一覧はプールの部分集合なので、
  置き場はあるが一覧に無い File (削除された File) も引く
- 同じ Folder id・同じ File の置き場は 1 つだけ (PDS の rkey と同じ)

### 例

性質では読み取りにくい具体的な振舞いを固定する。

- 同じ名前は後に作られた方が「研究 (2)」になり、改名に出る / 別の階層なら同じ名前でよい
- 行き先の無い File・親の無い Folder はトップ・レベル
- **輪の中の Folder はトップ・レベルに出て、輪の外からぶら下がる Folder は親を保つ** (輪に巻き込まない)
- 削除された File しか持たない Folder は空とみなす (見た目が空なのに消せない Folder を作らない)。
  File や下位の Folder を持てば空でない
- トップ・レベルの File は一覧の順

### 変異で確かめたこと

改名しない・輪を見ない・親の不在を見ない、のどれでも落ちる。一覧に無い File の置き場を捨てる検査は
落ちる変異が作れなかった — 置き場は一覧の File から引くので検査そのものが要らず、消した。
