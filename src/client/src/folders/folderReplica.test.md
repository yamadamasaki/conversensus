# folderReplica.test.ts — Folder と置き場の端末の写しのテスト仕様

## 何を

`FolderReplica` (写しへの操作・未送信の印・PDS への送信 `push`・受け取り `pull`・端末の控え・
ログイン前の写しの引き継ぎ `adopt`) を、PDS の偽物で検証する (step3 Phase 6 S6-2b, 設計 §2.4)。

## なぜ

Folder の操作はオフラインでもできなければならない (仕様)。手元で変えたものを失わず、いつか PDS に
載り、別の端末の変更とも揃うこと — この 3 つがここの約束である。崩れ方は次のとおり:

- 送れなかった変更が消える (印を落とす)
- 送っている間の変更が消える (古い値を送り終えたときに、新しい変更の印まで消す)
- 送る前の変更が、受け取った PDS の古い値で上書きされる
- 2 台の写しが揃わない

## どのように

偽の PDS は項目ごとの後勝ち (Map への set / delete) で、本物の rkey ごとの putRecord と同じ畳み方である。
`setFailing` でオフラインを模す。

### 送る

- オフラインの操作は写しに当たって未送信になり、送ると PDS に載って印が消える
- 送れなければ印が残り、次に送り直す (例外にしない)
- **送っている間に同じ項目を変えたら印が残る** — 送信の途中で改名させ、2 回目の送信で新しい名前が載る
- 消した Folder・トップ・レベルに戻した File は PDS から消える

### 受け取る

- 未送信でない項目は PDS に揃い、PDS に無い項目 (別の端末が消した) は消える
- **未送信の変更は PDS の古い値で上書きされない**

### 控えと引き継ぎ

- 控えて読み直すと未送信の印も戻り、読み直した写しから送れる (再読み込みしても送り残さない)
- 壊れた控え・無い控え・localStorage が無い環境は空の写し
- ログイン前の写しを引き継ぐと、すべてがその actor の PDS へ送られる (Q5)

### 2 台の同時編集

- **例**: 2 台がオフラインで同じ名前の Folder を作る。同期した後、どちらの端末も `buildFolderTree` の改名を
  書き、もう一度同期すると、両方とも「研究」「研究 (2)」で揃う (仕様の「片方の名前を変える」)
- **性質**: どんな操作 (作成・改名・削除・置く・戻す) と同期の順でも、最後に両方が送って受け取れば、
  2 台の写しは PDS と同じになり、未送信は残らない。全称命題なので性質で書く

**生成器の判断**: Folder の id は 3 つ、File は 2 つ、名前は 2〜3 個のプールから引く。同じ項目を 2 台が
並行に変える組 (後勝ちの衝突)、片方が消した項目をもう片方が変える組 (消えたものの書き戻し) を頻繁に
引くためである。手順は最大 20 で、途中の同期も 1 つの操作として混ぜる。

### 変異で確かめたこと

受け取りが未送信を上書きする・版を見ずに印を消す・控えから印を戻さない、のどれでも落ちる。
引き継ぎで項目ごとに印を付ける処理は落ちる変異が作れなかった — ログイン前の写しは送り先を持たず、
持っている項目はすべて既に未送信なので、印をそのまま引き継げば足りる。処理を消して単純にした。
