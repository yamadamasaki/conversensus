# smoke のテスト仕様 (E2E)

## 何をテストするか

**WebKit (Safari 相当) でアプリが成立すること。** ANA-125 の S0 時点では起動だけを見る
(サイドバーとキャンバスが出る / 起動でコンソールエラーも未処理例外も出ない)。
主要導線の通しは S2 でここへ足していく
(`../deepse/plans/step1-refinement-ana125-safari.md` §5)。

## なぜテストするか

配布形態の到達点である **Tauri v2 は macOS で WKWebView = Safari と同じ WebKit** の上で動く。
**Chrome での「動いた」は Tauri の証拠にならない**。使い込みで積み上げる機能が増えるほど
後から検証し直す対象が増えるので, **WebKit を常時回せる形**にしておく。

**本命は webkit, chromium は対照である。** #51 のように「WebKit だけ壊れる」ものは,
両方を並べて初めてエンジン差と言い切れる。逆に「WebKit を直して Blink を壊した」も
対照が無いと気付けない。

## どのようにテストするか

- **専用ポートで自前のサーバを起動する** (daemon :3100 / client :5174)。
  利用者が動かしている dev サーバ (:3000 / :5173) を再利用すると
  **E2E が利用者の `data/` にファイルを作ってしまう**。
  デーモンのデータは `data-e2e/` に置き, **起動のたびに消す**
- **画面が正しく見えることを合格条件にしない**。どのテストも `pageProblems.ts` を併用し,
  **未処理例外・コンソールエラー・読み込み失敗が 0 件**であることを見る。
  step1 では送信が数週間全滅していたのに画面は正常だった前例がある
- 失敗と見なさないものは `pageProblems.ts` の `IGNORED` に集める。
  **理由を書けるものだけ**を足す (今は vite の HMR 接続だけ)

## ここでテストしないこと

- **クリップボード (Cmd+V)・ファイル選択ダイアログ・描画品質** — Playwright では判定できない。
  実 Safari のチェックリスト (計画書 D5 / S4) の領分
- **トラックパッド由来の挙動** — 合成イベントでは再現しない (計画書 §2.3)
- **単体で確かめられるロジック** — `src/**` の `*.test.ts` の領分。
  E2E は「エンジンをまたいで壊れるもの」だけを見る
