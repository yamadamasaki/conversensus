# multiTab.spec.ts — 同じブラウザの複数のタブ (step3 Phase 2 S2-4)

## 何を

- タブごとに別の deviceId (= actor) を持つこと (設計 D4)
- 別のタブの書き込みが、再読み込みなしに画面へ出ること (設計 D3)

## なぜ

PWA ではブラウザのタブを 2 つ開くのは普通のことである。

- **同じ deviceId のタブが 2 つあると、同じ因果の点 (actor, seq) を発番する。**PDS の rkey は
  点で決まるので、後から書いた方が前の batch を上書きする。因果の判定 (同じ actor なら seq の
  大小) も壊れる (設計 F4)
- タブはそれぞれ Worker を持ち同じ OPFS の DB に書くので、**別のタブの書き込みは DB に入っても
  画面は知らない**

どちらも Web Locks・BroadcastChannel・OPFS というブラウザの機能に頼るので、bun の単体では
確かめられない (単体は `deviceClaim.test.ts` / `localChanges.test.ts` で偽物を使って論理を見る)。

## どのように

**同じ context の 2 つの page** が「同じブラウザの 2 つのタブ」に当たる。開発ビルドが出す口
(`window.__conversensus.deviceId`) でタブの deviceId を読む。

| テスト | 見ること |
| --- | --- |
| 🔴 別の deviceId / 閉じた id の再利用 | 2 つのタブの id が違う。2 つ目を閉じて開き直したタブが、閉じた id を使う (actor が増え続けない) |
| 🔴 File とノードが再読み込みなしに出る | 1 つ目のタブで作った File が 2 つ目の一覧に出る。両方で開き、1 つ目で置いたノードが 2 つ目のキャンバスに出る。両方のタブで未処理例外・コンソールエラーが 0 件 |

## テストしていないこと

- **因果の知識への取り込み** — 別のタブの書き込みは、画面より先に `causal.restore` で因果の
  知識に入る (`useEventSyncTap`)。画面からは見えないので App 結合 (`App.app-test.tsx` の
  「同じブラウザの別のタブの書き込み」) で見る
- **2 つのタブが同じ瞬間に同じ DB へ書くこと** — SQLite のロックが順番を取る (S0-4 で 2 つ目の
  接続が開けることは確かめた)
