# U6-P2 スパイクレポート: pre 条件つきの判断 op を projection に混ぜられるか

> 日付: 2026-08-31 / Phase: 0 ([step2 実装計画](../plans/step2-implementation.md) §5 の U6)
> スパイク: `src/client/src/spikes/u6/judgmentFold.ts` + `.spike.test.ts` (投棄前提)
> production コードの変更: **ゼロ**

## 判定: ✅ **Go** — 判断ログ側 (participation collection) に置いてよい

問いは「pre 条件つき承認 op を projection に混ぜたとき、`projectBatches` / `projectFile` に
**分岐を足さず routing だけで**分離できるか」だった。**分岐は要らない。**しかも
`isFileOp` → `foldFileStructure` の前例より弱い仕掛けで済む。

前例は同じ op 列を 2 回走査して述語で振り分ける形だった。今回は **collection が別**なので、
routing は述語ですらなく「どちらの collection から来たか」になる。判断の畳み込み器と
グラフの畳み込み器は、互いの型を一度も参照しない。

## 検証タスクの結果

| # | 検証 | 結果 |
|---|---|---|
| 1 | 判断の畳み込みが pre 条件で op を捨てる (呼ばれていない actor の承認) | ✅ C の承認は数えられず、揃うのは B の承認を待った時点 |
| 1b | 起動されていない DtR への承認も捨てる | ✅ `dtr.open` より前の承認は消える |
| 2 | pre 条件を満たさない再 merge が**出した本人の手元でも**捨てられる | ✅ 記録された集合への判定なので端末で結論が変わらない |
| 3 | **本物の `projectFile` を分岐を足さずにそのまま使える** | ✅ 述語で filter してから渡すだけ |
| 4 | 依存が一方向 (判断 → グラフ) で循環しない | ✅ `foldJudgments` の引数に `Batch` も `GraphFile` も現れない |
| 5 | 「より前」が決まる条件 | ⚠️ **同じ clock 空間の共有が前提**。下記 |

## 答えの形: 述語にして、畳み込みに入れる前に落とす

再 merge の可否をグラフの畳み込み器の**中で**判定しようとすると、そこに「無効な op がある」
という名簿側の意味論が入り込む。architecture §3 が「混ぜてはならない」と述べたのはこれである。

そうではなく、**畳み込みに入れる前に落とす**。

```ts
const ok = admissible(foldJudgments(judgmentBatches), remergeOf);
const file = projectFile(graphBatches.filter(ok), fileId);  // projectFile は何も知らない
```

`projectBatches` が `if (isFileOp(op)) continue` で file op を素通りさせるのと同じ位置である。
違うのは、素通りではなく**除去**だという点だけで、畳み込み器の本体は 1 行も変わらない。

グラフ側の前提 (「op はすべて有効」) はそのまま保たれる。filter を通った後の列には、
実際に無効な op が 1 つも無いからである。

## 依存が一方向であることの確認

pre 条件は「記録された呼び出し対象の全員の承認が、この操作より前に記録されていること」で、
これに要るのは `dtr.open` (呼び出し対象の記録) と `dtr.approve` だけである。どちらも判断ログに
ある。**グラフの状態を一度も見ない。**

逆向き (グラフ → 判断) も無い。承認の有効性は「記録された集合に居るか」だけで決まり、
グラフが何であるかに依存しない。したがって循環しない。

これは架空の性質ではなく、**S1 で集合を起動時に固定すると決めた帰結**である。集合を名簿への
生きた問い合わせにしていたら、判断の畳み込みが名簿の畳み込みに依存し、その名簿は他 actor の
repo を読む必要があり (不動点計算, architecture §2)、依存が一方向でなくなっていた。

## ⚠️ 前提: 判断ログとグラフの op-log は同じ clock 空間を共有しなければならない

pre 条件が「**この操作より前に**記録されていること」である以上、判断ログの clock と
グラフの op-log の clock が比較可能でなければならない。

検証 5 は、判断ログが独立した clock を持つ場合を模したものである。承認は実際には先に
起きているのに、数として比べると再 merge の方が小さくなり、**正当な再 merge が落ちる**。

- 現状 (step1) の `LamportClock` は 1 端末に 1 つなので、同じ writer を通す限り自然に共有される
- **Phase 1 で participation collection を新設するとき、そこに別の採番を作ってはならない**
- collection を分けることと clock 空間を分けることは別である。**分けるのは畳み込みの意味論だけ**

これは U6 の問いには含まれていなかったが、答えの前提として必ず要る。Phase 1 の設計で
明示的に固定すること。

## Phase 1 に引き継ぐ課題

- **`dtr.open` の二重起動を捨てる規則**が要る。スパイクでは「1 度目が勝つ」にした
  (呼び出し対象の書き換えを許さない)。仕様は起動が 1 度きりであることを明示していない
- **再 merge batch の印をどこに置くか。**スパイクでは外部の Map で代用した。本番では
  batch のメタか op の種別になるが、これは Phase 3 の「branch/commit/merge の op-log 昇格」に
  乗る話なので、そちらと揃えて決める
- **`satisfiedAt` は「揃った瞬間の clock」を持つ。**承認が取り消せるなら単調でなくなるので、
  仕様が承認の取り消しを認めるかを確かめる必要がある (現時点の仕様には記述が無い)
