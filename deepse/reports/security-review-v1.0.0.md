## 1. 直したもの

### H1・H2: 受信した編集と判断の書き手を照合する (#280)

**何が問題だったか.** 各参加者は自分の PDS に op-log を書き、他の参加者の PDS を読む。batch には書き手
(`actor` = `did#deviceId`) が入っているが、受信の側は「どの PDS から読んだか」と書き手を突き合わせていなかった。
PDS の持ち主は自分の repo に何でも書けるので、参加者なら **他人の名前で編集を書ける** ことになる。
参加期間の判定も batch に書かれた名前で行っていたので、名前を借りれば期間の外の編集も通る。名簿の判断ログも
同じ形で、招待されただけの人が他人の名前で判断を書ける。File の起点 (`genesis` という名義の batch) は書き手が
特定の人ではないので、誰の PDS から来ても受け取っていた。

**どう直したか.**

- 受信の入口 (編集: `receiveParticipantBatches.ts`、名簿: `readRoster.ts`) で、
  `didFromActor(batch.actor) === 読んだ PDS の DID` を満たすものだけを通す。満たさないものは数えて捨てる
- `genesis` 名義の batch は **創設者の PDS から読んだものだけ**を通す。創設者は招待の鎖を起点から辿って決める
  (`findFounder`: 誰からも招待されておらず起点を持つ人。創設者が抜けて戻った場合の環も扱う)。名簿に
  `notFounder` の理由を足した
- 採らなかった案: 「genesis の id を ops から計算し直して照合する」。id は ops の hash なので、誰でも自分の
  ops に合う id を作れる。**一致は形の検査であって、書き手の認証ではない**

**検証.** 他人の名前の batch・名簿の判断・創設者でない人の genesis を、それぞれ受け取らないことを単体で見た
(攻撃者の DID を辞書順で先に来るようにして、順序に頼って通っていないことも確かめた)。照合を外すとこれらが落ちる。

### M1・M2: 受信を壊れにくくする (#283)

**何が問題だったか.** PDS から読んだ batch の列を一括で検証していたので、形の壊れた batch が 1 件あると
その File の受信全体が失敗し、PDS からそれが消えるまで止まり続けた。また受信した clock をそのまま
Lamport clock に取り込んでいたので、極端に大きな clock が 1 件あると全員の clock が引き上げられた。

**どう直したか.** PDS の record を 1 件ずつ `isAcceptableRemoteBatch` (`atproto/batchMapper.ts`) で見て、
通らないものは数えて読み飛ばす。clock に上限 (`MAX_REMOTE_CLOCK = 2^48`) を設け、超えるものも読み飛ばす。

**検証.** 単体に加え、App 結合で「壊れた batch が混ざっていても、他の参加者の編集は画面に届く」ことを見た。

### M3: 表示する画像の型を限る (#283)

**何が問題だったか.** 画像を表示するときの MIME type を、node の property (他人が書ける値) から取っていた。
同じ origin の `blob:` URL を任意の型で作れることになる。

**どう直したか.** `displayableImageType` (`atproto/blob.ts`) で、表示するのは png・jpeg・gif・webp に限り、
それ以外は `application/octet-stream` として扱う (SVG も表示しない)。手元の画像と受信した画像の両方に当てる。

### S1: デプロイを専用のユーザーで行う (#281)

**何が問題だったか.** GitHub Actions のデプロイ用の鍵が root でログインできた。GitHub の秘密が漏れると
サーバの root を取られる。

**どう直したか.** デプロイ専用のユーザーを作り、書けるのは配信に要るディレクトリだけ、sudo で許すのは
「Caddy の設定を検査してから入れ直す」1 つだけにした。PDS の秘密はそのユーザーから読めない。Actions の鍵を
そのユーザーに移して root から外し、workflow ではサーバのホスト鍵を固定した。

### S2〜S4・S7・S8: サーバ

- **S2**: ssh のパスワード認証を切り (root は元から鍵だけ)、fail2ban を入れた。点検の時点で 7 日に 9 万回を
  超えるログインの失敗があった (どれも通っていない)
- **S3**: ファイアウォール (ufw) で 22・80・443 以外を拒む。PDS のコンテナの外向きの通信が通ることを確かめた
- **S4**: 更新を当てて再起動した
- **S7**: PDS の秘密を置いたファイルと、その控え・データの archive を所有者だけが読める権限にした
- **S8**: PDS の登録が開いていて、bot がアカウントを作っていた。登録を招待コード必須にし、作られたアカウントを
  消した。登録が開いていたのは、PDS を立てるときに一時的に開けた設定を
  戻し忘れたため

## 2. 確かめて問題なしとした点

- **秘密**: 本番の秘密は git の履歴に一度も入っていない (履歴の値と本番の値を hash で比べた)
- **サーバ**: PDS と Caddy の管理口は localhost にだけ開いている。自動更新は有効
- **アプリ**: `dangerouslySetInnerHTML`・`eval` は無く、他人の書いた文字はすべて React のテキストとして描く。
  Markdown は生の HTML を描かず、`javascript:` の URL を落とす。OAuth は DPoP・固定の redirect・最小の scope で、
  token は取り出せない鍵とともに IndexedDB に置く。パスワード認証は本番の bundle に入っていない。import は
  zod で検証して id を振り直す。送信するのは自分の DID の batch だけ

## 3. 学んだこと

- **「形が正しい」と「書いた人が正しい」は別の検査**。zod の schema も、内容から計算した id の一致も前者で、
  分散した書き手を扱うときは「どこから読んだか」との照合が要る
- **一時的に開けた設定は、戻すことを手順に書く**。S8 は手順の途中で開けた登録が残っていた
- **公開のリポジトリでは、直す前の所見を issue に書かない**。報告をリポジトリの外に置き、直して出してから載せた
