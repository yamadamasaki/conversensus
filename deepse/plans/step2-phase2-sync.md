## 0. この Phase が決めること

**書くのは自分の repo だけ、読むのは N 人の repo** を実際に成立させる。Phase 0 が
`collections.ts` の読み口に repo 引数を通し、Phase 1 が「誰の repo をいつからいつまで
読むか」を答える名簿を作った。この Phase はその 2 つを繋いで**グラフを畳む**。

**Exit で完了基準 1 と 3 が揃う** (完了基準 2 = DtR は Phase 3〜6)。加えて #202
(他端末・他窓の編集がファイルを開き直すまで反映されない) をここで回収する。

## 1. コードを読んで判明した、この Phase の形を決める事実

### 事実 A: ⚠️ catch-up が受信した batch を自分の repo へ送り返す

`FanoutSyncProvider.catchUpRemote` は **ローカル正典の全 batch**を引いて、remote に無い
ものを push する。

```ts
const { batches } = await this.local.pull(INITIAL_CURSOR);
await this.remoteQueue.catchUp(batches, this.fileId);
```

step1 ではこれが正しかった。ローカル正典に入る batch は**自分の DID の端末が書いたもの
だけ**で、全端末が同じ repo へ push するので、送り返しても同じ rkey の上書き
(= べき等) にしかならなかった。

**Phase 2 で受信が他 actor の batch を正典へ入れた瞬間、これは「相手の op-log を自分の
repo へ複製する」経路になる。** 起きることは 3 つある。

- 各 repo が参加者数分の op-log を持ち、**転送量が参加者数の二乗**で効く
- 「参加期間の分だけ読む」という約束が**費用の面で無意味になる** (期間外の op も、
  複製された先の repo から取ってきてしまうため。畳み込みは落とすので正しさは崩れない)
- 参加を取りやめた actor の op が、**取りやめた後も全員の repo に残り続ける**

→ **catch-up の対象を「自分の DID が書いた batch」に絞る** (S0)。`Batch.actor` は
`<did>#<deviceId>` なので `didFromActor` で判定できる。**この柵を先に立てる** — 受信を
繋いでから直すと、繋いだ瞬間に PDS が汚れて後始末が要る。

### 事実 B: 発見経路は他 actor の repo を列挙しなくてよい

U6-P1 が出した宿題は「他 actor の repo に `listFileHeads` を回すとその actor の File が
全部見える (実測 23 個)」だった。計画は「発見の対象を名簿で絞る」と書いていたが、
**名簿で絞る前に、そもそも他 actor の repo を列挙する必要が無い**。

自分が参加する File には、**自分の repo に必ず判断ログがある**。

| 立場 | 自分の repo にある判断 op |
| --- | --- |
| File を作った | `participation.genesis` |
| 参加を承認した | `participation.accept` |
| 誰かを依頼した (= 自分は参加者) | `participation.invite` |

判断ログの rkey は `batches` と同じスキーム (`v1~<fileId>~<clock>~<batchId>`) なので、
**自分の repo の `judgments.listFileHeads()` が「自分が関わった File の fileId」を返す**。
他人の repo は 1 件も列挙しない。

→ **発見の入口は自分の judgment collection である** (S3)。名簿による絞り込みは
「列挙した後に落とす」フィルタではなく、**そもそも列挙に他人が現れない**構造になる。
U6-P1 の宿題はこの形で閉じる。

### 事実 C: 既読位置 (cursor) は今も持てない

アーキテクチャ §2 は「cursor は DID ごとに持つ」と書いているが、step1 Phase 7 で
**既読位置を持たない契約**を選んだ理由 (`atprotoSyncProvider.ts` の設計注) は今も生きて
いる。rkey は `v1~<fileId>~<clock>~<batchId>` になったので**ファイル内では clock 順**に
並ぶが、**clock は端末をまたぐと単調でない** — 遅れていた端末が後から書いた batch は、
保存済み cursor より小さい rkey を持ちうる。DID ごとに分けても、1 DID が複数端末を持つ
以上この性質は消えない。

→ **DID ごとに「そのファイルの範囲を毎回頭から読む」を維持する。** 取りこぼしゼロを
構造で保証し、二重取り込みは `appendReceivedBatches` のべき等性が無害化する。
1 サイクルの費用は `参加者数 × そのファイルの履歴` になる。**まず測ってから最適化する**
(U4 と同じ判断: 書かないと決めた以上、projection は毎回全量である)。

### 事実 D: 他 actor の画像は「誰の blob か」が分からないと引けない

`resolveImageUrl` は 3 段目 (PDS) で `loggedInDid()` を渡す。配管
(`fetchRemoteBlob(did, cid, mimeType)`) は最初から他 DID に対応しているので、
**閉じているのは「その画像を誰が持っているか」を知る手段の方**である (U2)。

→ §5 で決める。

## 2. 同期の 1 サイクル

アーキテクチャ §2 の手順をコードの形に落とすと次になる。

```
syncNow(fileId):
  1. 名簿を読む       readRoster({ fileId, seed: 自分 })        ← 判断ログ collection
  2. 送信              catchUpRemote()  ※自分の batch だけ (事実 A)
  3. 受信              参加者ごとに pullRemoteForFile(fileId, repo=did)
                       → 参加期間の外の batch を落とす
                       → ローカル正典へ受信追記
  4. 再 projection     reprojectAfterReceive (既存)
```

**1 と 3 の順序は入れ替えられない** (アーキテクチャ §2「読む順序は名簿 → グラフに固定
される」)。2 と 3 が独立に catch するのは step1 のままである (送信の失敗が受信を止めない)。

### 名簿は誰が持つか

現状、名簿を読むのは `useParticipation` (ダイアログを開いたときだけ) である。同期経路が
毎サイクル名簿を要るので、**読み出しをダイアログから引き剥がして File 単位の供給元に
する** (S1)。ダイアログと同期はそれを共有する。

**TTL は持たない** (S1 で確定)。「N 秒は読み直さない」形にすると、**「相手の参加が
見えるまでの遅れ」を根拠の無い定数で決めてしまう**。その遅れを決めるのは同期の間隔 (S4)
であって、その内側にもう 1 つ時定数を置かない。

代わりに**同時に走った読みだけを畳む** (in-flight dedup)。同期サイクルの最中にダイアログが
開く場面は普通に起きるが、そこで名簿を 2 回読む理由は無い (1 回の読みが参加者数分の
リクエストである)。

⚠️ **書き込みの直後は畳んではならない** (`readFresh`)。判断ログを書いた直後に、書く前から
走っていた読みへ相乗りすると書く前の名簿が返り、ダイアログは「依頼したのに表に出ない」を
見る。呼び分けは呼び出し側に残す — 供給元の側で「書き込みがあったか」を知る術は無い。

**起点の修復 (`ensureOwnGenesis`) も読みの一部として扱う。**同期サイクルしか触らない File
(ダイアログを一度も開いていない File) でも修復が要るからである。

## 3. 参加期間フィルタ

畳み込みに入れる前に落とす (U6-P2 の答え: 「判断の畳み込みの結果を述語にして、グラフの
畳み込みに**入れる前に**落とす」)。`projectFile` は無変更である。

```ts
const keep = (batch: Batch) =>
  wasParticipatingAt(participation, didFromActor(batch.actor), batch.clock);
```

- 述語は既にある (`wasParticipatingAt` / `periodsOf`)。Phase 1 で `history` を
  「参加期間の列」から「出来事の列」に広げたのは、この期間を導けるようにするためだった
- **判定に使う DID は「batch の著者」であって「読んだ repo の持ち主」ではない。**
  事実 A の柵があれば両者は一致するが、**一致に依存しない** — 過去に複製されたレコードが
  PDS に残っていても、著者で判定すれば結論は変わらない
- **落とす位置は受信の前である。** 正典に入れてから畳み込みで落とすと、参加していなかった
  期間の op が手元に永久に残る (仕様の「参加期間の op-log だけを同期する」に反する)
- `didFromActor` は `Did` ではなく `string` を返し、未ログイン時は `'local'` になる。
  **述語の側で「名簿に載っていない DID は参加していない」に落ちる**ので特別扱いは要らないが、
  型の変換をどこかに置く必要はある

### ⚠️ 自分の batch は落とさない

自分の repo から読む分にこの述語をかけると、**genesis より前に自分が書いた batch**
(step1 時代の File) が落ちる。名簿の起点が無かった File を `ensureOwnGenesis` が後から
拾う形にしたので (Phase 1)、genesis の clock は最初の編集より後になりうる。

→ **フィルタは他 actor の repo から読んだ batch にだけ適用する。** 自分のローカル正典は
権威であって同期の対象ではない。

## 4. 定期ポーリング (#202 / U3)

仕様が step2 の同期方式として挙げたもの。step1 は「1 回あたり remote 取得 1 往復の
コストを常時払う」ことを避けて手動同期にしたが、**多アクタでは「相手の編集が見えるまでの
遅れ」がそのまま体験になる**ので、ここで入れる。

- **既存の `syncNow` をそのまま間隔で叩く。**送信 catch-up と受信を分けない (契機を
  増やさない)。`syncNow` はべき等なので、手動同期と重なっても二重適用しない
- **止める条件を持つ**: タブが不可視のとき (`document.hidden`)、オフラインのとき、
  前回のサイクルがまだ終わっていないとき。**間隔ではなく「前回の完了から N 秒」**で
  回す (遅い PDS で要求が積み上がらない)
- **間隔は定数として定義する** (コーディング規約 3)。初期値 30 秒。**根拠は無いので
  実機で測って決め直す**前提にする
- **cursor を共有して二重適用しない**という仕様の要求は、既読位置を持たない契約
  (事実 C) が構造的に満たしている

## 5. 他 actor の blob (U2)

`ImageNode` が持つのは `cid` と `mimeType` だけで、**誰の repo に上がっているかを
持っていない**。案は 3 つある。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| (a) 由来を projection が運ぶ | op を適用するとき `batch.actor` を画像ノードに残す | **採用**。`projectBatches` は batch を回しているので actor は手元にある |
| (b) 参加者を順に試す | 自分 → 名簿順に `getBlob` する | 見つからない画像で参加者数分の 404 を出す。キャッシュが効くので一度きりだが、失敗が観測を汚す |
| (c) 受信時に自分の repo へ複製 | bytes を持っていないので不可 | 却下 |

(a) は **projection の出力に由来 (provenance) を持たせる最初の例**になる。**画像に限る**
— 「誰が書いたか」を全 op に持たせ始めると projection の出力が膨らみ、Phase 3 の
競合表示が「由来はどこまで正確か」に引きずられる。画像だけなのは、**blob が op-log の
外にあり、参照するのに repo を名指しする必要がある唯一のもの**だからである。

`resolveImageUrl` の 3 段目に渡す DID を「そのノードの由来 DID、無ければ自分」にする。
1 と 2 (メモリ / ローカル blob ストア) は content-addressed なので変えない。

## 6. 再参加時の同期義務

仕様 (participation ワークフロー 6-3): 非参加期間の操作に依存する新しい操作は相手に
エラーを起こすので、**再度参加する前に標準 projection へ同期しなければならない**。

- **検出**: 再参加 (`accept` で 2 つ目以降の参加期間が開く) の直後に、その File の同期を
  1 サイクル強制する。名簿を読み直した結果で自分の期間が増えていれば分かる
- **誘導**: 同期が終わるまでその File を**読み取り専用にする**。ダイアログや通知で
  「同期してください」と頼む形にはしない — 頼んで守られなかった場合に相手が壊れる
- ⚠️ **これは「取りこぼした op を後から入れる」ではない。**再参加した actor は、非参加
  期間の他人の op を**期間フィルタで落とさない** (フィルタは著者の期間であって読み手の
  期間ではない)。落ちるのは自分が非参加だった期間に自分が書いた op である

## 7. この Phase で決めた「やらないこと」

### branch batch は remote に出さない (step1 §9.2 を維持する)

計画は「単一端末前提が消えたので撤回するか維持するかを明示的に決める」としていた。
**維持する。**

- Phase 2 の完了基準は **trunk の相互反映**である。branch を出しても完了基準は動かない
- 出すと `discoverRemoteFiles` に「branch の file_id は File ではない」判別が要る。
  これは Phase 3 が作る**器** (branch / commit / merge の op-log 昇格) の一部であって、
  そこで一緒に決めた方が形が揃う
- ⚠️ **Phase 3 はこの判断の対価を払う**。fork を「書く」と決めた以上、器である branch が
  同期対象でなければ書いても相手に届かない。**Phase 3 の最初のスライスがこれになる**

### 収束の性質は書くが、範囲を限る

**「同じ op 集合を見た 2 つの手元は同じ projection を出す」を性質として書く** (計画 §7 で
Phase 2 必須としたもの)。ただし**入力は batch 列であって PDS ではない** — 配送順・分断の
モデル化は生成器の設計が本体になるので、ここでは「順序を入れ替えた同じ集合」までとする。

## 8. スライス

| | 内容 | 検証 |
| --- | --- | --- |
| **S0** | catch-up を自分の DID の batch に絞る (事実 A の柵) | 単体。他 actor 由来の batch が push 対象に入らない |
| **S1** | 名簿の読み出しを File 単位の供給元に切り出す (ダイアログと同期で共有) | 単体。書き込み後に読み直す |
| **S2** | 他 actor の repo からグラフを読み、参加期間で絞って受信する | 単体 + 実 PDS (2 アカウント) |
| **S3** | 発見の入口を自分の判断ログにする (承認した File が materialize される) | 単体 + 実 PDS |
|  | ⚠️ S3 で分かったこと: **削除の判定は書く前に要る** (ローカル正典から File を取り除く口が無く、削除は tombstone でしか表せないので「削除済みの File を作ってから削除し直す」ことになる)。`collectParticipantBatches` (集めるだけ) を `receiveParticipantBatches` から切り出した | |
| **S4** | 定期ポーリング (#202) | 単体 (時計を注入)。実機で #202 の再現手順 |
| **S5** | 他 actor の blob (由来 DID を projection が運ぶ) | 単体 + 実 PDS |
| **S6** | 再参加時の同期義務 (検出と読み取り専用) | 単体 |
| **S7** | 収束の性質 (PBT) | `bun test` |
| **S8** | 引き取り (`participation.reopen`) — 名簿が空になった File の行き止まりを開ける | 単体 (畳み込み + 一覧 + 性質) |
|  | 実機で行き止まりを確認した (2026-09-05)。最後の 1 人が降りると招待は `issuerNotParticipating`、起点の置き直しは `duplicateGenesis` で落ち、**誰も二度と参加依頼を出せない**。仕様に activity を追加 (`spec/participation.md`)。**引き取りは新しい期間を開くだけ**とし、誰もいなかった間の op は届かない — 遡って開くと完了基準 3 を「名簿を空にしてから引き取る」経路で迂回できてしまう | |

**S0 が最初なのは順序の問題ではなく安全の問題である** — S2 を先に入れると、その瞬間から
PDS に他人の op-log が複製され始める。

## Exit

1. **2 アカウントが同一 File に参加し、双方の編集が相手のグラフに反映される** (完了基準 1)
2. **一方が参加を取りやめた後、その操作が相手に反映されなくなる** (完了基準 3)
3. **#202**: 同一ユーザの別端末・別窓の編集が、ファイルを開き直さずに反映される
4. 他 actor が貼った画像が表示される
5. 相手の repo に自分の op-log が複製されていない (事実 A の柵が効いている)

1〜4 は実 PDS の 2 アカウント (`alice.test` / `bob.test`) で確かめる。5 はレコード数で見る。

## 未決のまま持ち越すもの

- **ポーリング間隔の根拠** (U3)。初期値 30 秒は仮である
- **畳み込みコスト** (U4)。参加者数 × 履歴を毎サイクル読む。まず測る
- **参加者が増えたときの名簿の深さ** (U1 の 1 パス既定)。単一 PDS + 依頼制で浅いという
  見込みのままである
