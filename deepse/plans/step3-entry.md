## 2. 批判的レビューの結果

**致命的な発見は無い。**データ破壊も収束 (SEC) の破れも見つからなかった。ただし
**利用者の既知リストに入っていない限界が 1 つ**出た (§2.1 の「4 つ目」)。

### 2.1 clock — 1 つの決定ではなく 2 つだった

これが今回いちばんの収穫である。「vector clock は step3 の優先事項」としていたものが、
**費用も緊急度も違う 2 つ**に割れた。

| | 何を解くか | 費用 | いつ |
| --- | --- | --- | --- |
| **分岐点** (`Commit.at` → version vector) | 「merge していない trunk の変更が branch に混ざる」 | **op 語彙の追加 1 つ** | **最初** |
| **batch への vector** | add-wins の半端さ / 検出の非対称 | **畳み込みの規則の変更** | 競合の見せ方の直前 |

#### 分岐点は vector clock では直らない

🔵 `branchLog.ts:166-168` の `batchesUpTo` は `b.clock <= commit.at` で切る。`Commit.at` は
**単一の scalar 切断面**なので、後から低い clock の batch が届くと**分岐時には見えていな
かったものが遡って base に入る**。

**batch に vector を載せてもこれは直らない。**batch の vector が答えるのは「この 2 つの op は
並行か」であり、`base` が答えるべきは「**分岐した瞬間、私は何を見ていたか**」— 後者は
1 点の状態であって op 間の関係ではない。

**代案**: `Commit.baseVector: Record<Actor, Lamport>`。切り出しは
`b.clock <= baseVector[stackedBy(b)] ?? -1` になる。知らない actor は `-1` (= 1 件も含めない)
— 分岐時に存在を知らなかった actor の batch は、定義上、見えていなかった。

**成立の前提は「actor ごとの clock の単調性」だけである。**🔵 `unified.ts:733-735` の
`tick()` は `this.value += 1` なので、同一 actor 内では厳密に単調。**actor をまたいだ比較を
一度もしない**ので、下記の 4 つ目の限界がここには入らない。

**費用**: 🔵 lexicon を触らない (`lexicons/app/conversensus/graph/batch.json:29-30` の `ops` は
`"type": "unknown"`、`CommitSchema` は `OpSchema` の中)。SQLite も触らない (T7-1 以降、
branch/commit の権威は op-log の畳み込みに移っている)。既存データも移行不要
(`baseVector` を持たない commit は `at` にフォールバック)。**vector が載るのは commit であり、
File あたり数十件である** — batch が数千件なのに対して、同期量への影響は実質ゼロ。

**後回しの損は複利で効く。**分岐点が曖昧なまま DtR の解決 branch が branch 機構に乗ったので、
**解決グラフの内容そのものが「分岐時に見えていなかった trunk の変更」に汚染されうる**。
承認は「その解決グラフを見た上で」行うものなので、**汚染は承認の意味まで届く**。
PR #227 で直したのは表示だけで、projection の穴は残っている。

#### ⚠️ 4 つ目の限界 — 参加期間の判定が actor をまたいだ scalar の比較になっている

既知の 3 つ (add-wins が半端 / 通知が片側 / 未 merge の trunk が混ざる) に入っていない。

🔵 `participation.ts:319-346` の `periodsOf` は、期間の `from` を**承認した本人**の clock で
開き、`to` を**取り消した人**の clock で閉じる。🔵 `participationFilter.ts:54-67` の
`isWithinParticipation` はそれを**対象者本人**の batch clock と比べる。**別々の actor が
独立に進めた scalar 同士の比較**であり、因果で並んでいる保証がない。

🔴 実行して確認した。

```
periods = [{from: 5, to: 50}]      from = 承認した本人 / to = 取り消した人
A@12 (取り消し未観測) = true       ← 通る
A@60 (取り消し未観測) = false      ← 落ちる
A@51 (取り消し観測後)  = false
```

**真ん中の 2 行が問題である。**どちらも A は取り消しを見ていない (見ていれば clock は 51
以上になる)。**因果関係は同一 = 並行**。にもかかわらず結果が逆になり、分けているのは
*A が無関係な相手とどれだけ同期したか* だけである。

**これは完了基準 3 の一般形である。**「一方が参加を取りやめた後、その操作が相手に反映
されなくなる」は、**2 台が同期し合っている経路では成立し、取り消しが最も必要になる場面
(相手と同期していない) で崩れる**。

**なぜテストが緑だったか**: 🔵 `participationFilter.test.md` は境界を「19 / 20 / 21 の 3 点」で
見ている。これは**同値 (tie) の扱い**を固定するテストであって、*別 actor の clock が比較
可能か*という問いを立てていない。

収束は壊れない (誰の手元でも同じ答えを出す決定論的な判定である) ので致命的ではない。
**ただし vector clock でしか解けない種類の問題であり、A の優先度を押し上げる材料である。**

#### 検出の非対称 — T8 に本物の競合が混ざる

🔵 `conflicts.ts:146-153` は Lamport の対偶で絞り込む (`clock(m) >= clock(t)` なら相手は
m を見ていない)。偽陽性は無いが**偽陰性がある**。そして T8 (`overwrites.ts:162`) は
その**厳密な補集合**を取る (`if (mineClock >= oldestIncoming) continue;`)。

🔴 実行して確認した。同じノード本文を二人が並行に書き換え、私の clock が 5・相手が 10:

```
競合として検出 = 0
報告として検出 = 1 (content)
```

**純粋な並行なのに、clock の大小だけで「競合」から「変わりました」へ振り分けられる。**

設計は「相手の手元では検出されるので対で完全」としてこれを埋めており、fork の同期 (T7) が
成立した以上、実害は「両側で見え方が非対称」までに留まる。**ただし layout は fork を
作らない**ので、layout の並行変更だけは片側で「競合」・もう片側で「変わりました」と
**永久に違う言葉で語られる**。ここは対が閉じていない。

#### batch への vector の代償

- ⚪ **scalar は捨てられない。**🔵 `unified.ts:95-104` の `compareByClockActorId` が与える
  **全順序**が projection の決定論 = SEC の土台である (`convergence.test.ts` が性質として
  固定している)。vector は半順序しか与えないので**必ず tiebreak が要り、それが今の
  scalar である**。→ **vector は置き換えではなく「追加」**でなければならない
- 🔵 rkey が scalar を埋め込んでいる (`batchRkey.ts`, `CLOCK_DIGITS = 12`)。順序の正しさは
  rkey に依存していない (受信側が正規化ソートする) が、置き換えるなら `v2~` への移行が
  要り、それは step1 Phase 7 が払った費用 (`migrateRemoteRkey.ts` 229 行) の再演になる
- ⚪ `did#deviceId` は増える一方なので、**actor の退役規則**が無いと vector が伸び続ける

#### step3 の設計の前提に置くべき 1 行

> **スキーマの変更はレコードを弾くのでうるさく失敗するが、畳み込みの規則の変更は静かに
> 違う答えを出す。**

step2 は「追記のみのログにスキーマを厳しくするのは破壊的」という教訓を得た (`TemplateId` の
逆順ドメイン強制で前日のログが parse 失敗)。**この教訓は半分しか正しくない。**
より破壊的なのは畳み込みの規則の変更であり、**batch への vector はそちらに当たる**。

### 2.2 二本立て (判断ログ / グラフ op-log) — 分離は維持。ただし判別を移す

**分離そのものは正しい。**依存の一方向性 (判断 → グラフ) を支えており、コードで実証されて
いる。問題は**原子性の欠如が「名前による判別」と組んだときに実害になる**ことである。

#### 孤児の DtR は「本物と区別がつかない」

🔵 起動の書き込み順は `startDtr.ts:289-295`:

```
await deps.createResolveBranch(...)      ← グラフ log
deps.recordSheetCreated(...)             ← グラフ log (:111 が `=> void`、await 無し)
await deps.appendJudgment(..., dtr.open) ← 判断 log
```

2 つのログに原子性は無い。**「残りやすい側を先に置く」でしのいでいる**が、判断ログへの
書き込みが落ちると器だけが残る。そして🔵 画面の判別は**名前の接頭辞**である
(`Sidebar.tsx:407,555,566,579` が `isDtrSheetName` / `isDtrResolveBranchName` /
`dialogueSheetNameOf`)。

🔴 **後始末が無いことを確認した。**`useBranchOperations.ts:877-882` は `startDtr` を独立した
`try/catch` に入れ、失敗時は `console.warn` するだけで、**catch 節に器を片付ける処理が無い**
(`startDtrFromFork` 側の 789-802 行も同じ)。

孤児はこう振る舞う。

| | 振る舞い |
| --- | --- |
| サイドバー | **`⇄` 付きの解決 branch として出る** |
| 対話 sheet | **タブから隠される** |
| 💬 (対話グラフを開く) | **押せる** (名前から引くので) |
| `foldDtr` | **見えない** — 承認も再 merge も永久にできない |

**「本物と区別がつかない、決着しない DtR」が生まれる。**D5 が 2 度下した判断
(「押せないボタンを作らない」) が、**失敗経路から破られている**。

**「残りやすい側を先に置く」は緩和になっていない** — 片方だけ書かれる確率は下げるが、
**片方だけ書かれたときの害**を下げていない。

**判別を `dtr.open` に移すと両方が消える。**孤児の器は「変な名前のただの branch/sheet」
(無害、タブに出るのも正しい)、器の無い `dtr.open` は**検出して人に報告できる**
(いまは検出すらできない)。書き込み順は「どちらでもよい」に落ちる。

**なぜ着手前か**: ① 承認 UI が名前判別の上に乗る (いま剥がす範囲は `startDtr.ts` の 4 関数に
閉じ込めてある。UI を作った後だと画面側に散る) ② **名前は人が変えられる** — 解決 branch を
改名した瞬間その DtR は画面から消え、実データが増えるほど事故の記録が混ざる。

#### clock 空間の共有は「設計は健全、保持は規律頼み」

判断ログとグラフ op-log は同じ clock 空間を共有する (pre 条件が「この操作より前」を問うため)。
支えているのは `appendJudgment.ts:78-83` の seed と `useEventSyncTap` の `observeRemote`。

⚪ 破れうる所が 3 つ: ① `known` は呼び出し側が渡す (名簿読み出しの既定は 1 パスなので
1 ホップ先の判断は入らない) ② tap 不在の経路 ③ 開いてから最初の同期サイクルまでの窓。

**保証する構造物が無い。**`appendJudgment` が `known` を引数にして「省略できないようにして
ある」こと自体が、規約でしか守れていない証拠である。**省略は防げたが、間違った値を渡す
ことは防げていない。**

#### 承認 UI の最大の障害

🔵 `useFileSheetOperations.ts:310` の `dtrJudgmentsRef` は `useRef` である (D3 が意図して
そうした — projection の `useCallback` が安定参照を要求するため)。**ref は再描画を起こさない。**

D6 の留保「承認は判断ログへ直に書いて判定した」は、時間が無かったのではなく

## 3. 実装者側の懸念 — 2 件のうち 1 件は誤りだった

### 3.1 スケール特性 — 焦点は畳み込みではなく取得だった

振り返りの当初、私は「参加者 n 人・op m 件で毎回 n×m を畳んでおり、2 アカウントでしか
検証していない」と懸念した。**測ったら、懸念の所在が違っていた。**

🔴 `projectFile.bench.ts` の実測:

```
N=5000 batches, 1 sheet   median=0.77ms   [予算 50ms]
N=5000 batches, 5 sheets  median=1.01ms
```

**畳み込み本体はまったく問題になっていない** (予算に対して 50〜65 倍の余裕)。

**ただしこのベンチが測っているのは op 数 (m) の軸だけで、単一 actor の合成ログである。
参加者数 (n) の軸は測られていない。**

n が効くのは畳み込みではなく**取得**の側である。参加者ごとに repo を読み、相手のログは
自分より大きいのが普通で、**cursor を持たないと決めた** (clock は端末をまたぐと単調でない
ため) ので毎回全件読む。範囲取得が「効率の話」から「正しさの話」に変わったのは Phase 0 で
観測済みである。

**したがって解決策は 3 つの方向がある。**

1. **per-actor cursor を持てるようにする。**cursor を諦めたのは scalar clock が端末を
   またいで単調でないからで、**vector clock が入れば actor ごとの cursor は正しく持てる**。
   → **スケール対策と vector clock は対立しない。同じ方向を向いている**
2. **畳み込みの中間結果をキャッシュする。**step1 で snapshot を撤去した (「op-log が唯一の
   正典」) が、**正典ではなくキャッシュとしてなら筋を損なわない** — 畳み込みは冪等なので
   再計算で検証できる。ただし上の実測を見る限り**いま要らない**
3. **測ってから決める。**n の軸のベンチが無い。`projectFile.bench.ts` の形を借りて
   「n 人 × m 件」を測る台本は安く書ける

**優先すべきは 3 → 1 である。**2 は現時点で不要。そして 1 は A (分岐点) とは別の決定だが、
**batch への vector を入れる動機に「同期量の削減」が加わる**ことは、順序の判断材料になる。

> **決めるべき問い**: 10 人が同じ File を編むとき、同期の往復と取得量は成立するか。
> 崩れるとしたらどこからか。**vector を入れる前に測るか、入れながら測るか。**

### 3.2 可用性 — ⚠️ 私の懸念は誤りだった (訂正)

振り返りの当初、私は「分散の形をしているのに可用性が集中している。各自の PDS が落ちれば
その人の履歴は誰にも読めない」と述べた。**これは誤りである。**

🔵 `receiveParticipantBatches.ts:76,271` の `appendReceived` は、他の参加者から集めた batch を
**ローカル正典へ追記する**。🔵 `eventStore.appendBatch` は actor で選別しない (空 ops を
拒むだけ)。S0 の `filterBatchesForRemote` は **remote へ送り返さない**ための柵であって、
ローカル保存とは無関係だった。

**一度同期した相手の履歴は自分の手元に残る。相手の PDS が落ちても過去は読める。**

正確に言い直すと、可用性が問題になるのは 2 つの場合だけである。

- **まだ同期していない期間** — 分散型として当然であり、設計の欠陥ではない
- **新規参加者が過去を取りに行く場合** — その人の PDS が落ちていれば、その人の履歴は
  新規参加者には届かない。**歴史の入手経路が著者の PDS 1 点に依存する**

🔵 なお保持には設計上の限界がある。`receiveParticipantBatches.ts:180` が
`filterByParticipation` を**追記の前**に当てているので、手元に残るのは**自分が見る資格の
あった範囲**である。これは欠陥ではなく仕様だが、「過去の可用性」の範囲を決めている。

> **決めるべき問い (step3 以降)**: 新規参加者が、著者の PDS に到達できないまま過去を
> 得る道を用意するか。用意するなら、それは誰の手元の写しを正とするのか。

### 3.3 ATProto との適合性 (所感)

**思想的な適合は高く、機構的な適合は中くらい**、というのが実装を終えての実感である。

**よく乗った 3 つ**: repo が「個人の追記ログ」であること (op-log と素直に噛み合う) /
content-addressed な blob (「その cid がどの repo にあるか」は cid の性質なので、ノードに
由来を持たせずに済んだ) / rkey のスキーム (判断ログの rkey を batches と揃えたので、
**自分の repo を見るだけで「自分が関わった File」が取れる** — 他人の repo を列挙せずに済んだ)。

**摩擦は 1 つの根から出ている**: 書き込みが自分の repo にしかできないこと。正しい制約だが、
「複数人で 1 つの構造物を編む」という要求とは**向きが逆**である。結果として implicit merge の
結果をどこにも書かないと決め、毎回全量を畳むことになった。

**構造的にはこう見える。**ATProto は「個人が発信し、他人が購読する」モデルである。発信
モデルでは真実は各自の repo にあり、読む側が集約する。ところが共同編集では、**真実は
「全員のログの畳み込み」にあり、それはどの repo にも存在しない。**step2 の実装は、ほぼ
このギャップを埋める作業だった。

実際に使ったのは repo と blob と DID だけで、feed generator も firehose も app view も
label も使っていない。つまり **ATProto を「署名付きの個人ログ置き場 + identity」として
使っている**。固有の利得ははっきりある — **identity の可搬性と、データが利用者自身の repo に
あること**。対話と合意の記録が個人に属するという conversensus の思想と、ここは正面から合う。
