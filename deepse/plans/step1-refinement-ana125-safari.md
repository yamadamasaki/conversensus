## 1. 結論

**#51 の症状は再現し, 原因も確定した。CSS flex の縮み方の差である。**
`Sidebar.tsx` のヘッダ行は `<input style={{flex: 1}}>` + ボタン 2 つで組まれているが,
**flex アイテムは既定で `min-width: auto`** なので, 入力欄は自分の固有幅 (`size` 属性由来) より
細くならない。その固有幅が **Chromium より WebKit の方が広い**ため, WebKit でだけ行が
サイドバーの幅を超え, 右端の import ボタンが外へ押し出される。

どちらのエンジンも仕様違反ではない。**縮む前提を書いていないレイアウトが, 固有幅の差で
露出しただけ**である。だから直し方も「Safari 用の分岐」ではなく「縮む前提を明示する」になる。

一方で, **#51 以外に何が壊れているかは分かっていない**。Safari で通しの操作をした記録が無く,
コンソールも見られていない。**本課題の主な仕事は「直すこと」より「洗い出すこと」**であり,
そのために **WebKit を自動で回せる土台**を先に作る。

## 2. 診断 (Playwright WebKit で実測, 2026-08-13)

### 2.1 import ボタンは本当にサイドバーの外へ出ている

同じページを Chromium と WebKit で開き, サイドバーのヘッダ行を実測した
(viewport 1280x800, サイドバー幅 240px)。

| 計測点 | Chromium (Blink) | WebKit | 差 |
|---|---|---|---|
| ファイル名入力の幅 | 161px | **180px** | WebKit が 19px 広い |
| import ボタンの右端 | 235px | **258px** | サイドバー (240px) を **18px はみ出す** |
| 行の `scrollWidth` | 223px | **246px** | 行そのものが溢れている |
| ボタン中心の `elementFromPoint` | `BUTTON` | **`DIV`** (キャンバス側) | **押しても届かない** |
| ボタン左端 (x=230, サイドバー内) の `elementFromPoint` | `BUTTON` | `BUTTON` | ここは押せる |
| Playwright の `click()` | 成功 | **TimeoutError** | 自動操作でも押せない |

**課題本文の「はみ出す」「押しても実行されない」「サイドバー内に残った部分を押すと実行される」の
3 点が, そのまま数値で再現した。**

### 2.2 原因は `flex: 1` + `min-width: auto`

`src/client/src/Sidebar.tsx` のヘッダ行:

```tsx
<input … placeholder="ファイル名" style={{ flex: 1, padding: '4px 6px', fontSize: 13 }} />
<button …>+</button>
<input ref={importInputRef} type="file" style={{ display: 'none' }} … />
<button … title="インポート (.conversensus)" onClick={() => importInputRef.current?.click()}>↑</button>
```

- `flex: 1` は `flex-shrink: 1` を含むが, **`min-width` の既定は `auto`** なので
  アイテムは**内容の固有幅より細くならない**。`<input>` の固有幅は `size` 属性 (既定 20) と
  フォントから決まり, **その値がエンジンごとに違う**
- サイドバーは `overflow: visible` なので, はみ出した分は**切り取られずに描画される**。
  だから「見えているのに押せない」という分かりにくい壊れ方になる
  (押せないのは, その位置の最前面がキャンバス側の要素だからである)

**`display: none` の file input は無実である** — Chromium でも WebKit でも
`importInputRef.current.click()` は file input に届いており (WebKit でも
ボタン左端を押せば import が走る), 症状はレイアウトだけで説明が付く。

### 2.3 ANA-115 (カーソル) は**別々の 2 つの症状**である

> **前提 (ユーザー報告, 2026-08-13): 症状 A・B とも「ポインティング・デバイスが
> トラックパッドのときにだけ起こり, マウスでは起こらない」。**
> ブラウザだけの問題ではなく **OS レベルの問題である可能性が高い** — 同じ Web ページに
> 同じ操作をしても入力デバイスで結果が変わるということは, 差はイベントを作る側
> (トラックパッドドライバ → macOS のイベント配送) にある。
> **本課題でアプリ側を触って直せる範囲かどうかも, この前提の下では疑わしい。**
> 以下の測定と方針はすべてこの前提の上に立つ。

#51 のコメントに集約されている WKWebView の 2 件 (Linear では ANA-115 / ANA-104。
どちらも 2026-08-07 に Canceled) のうち, **ANA-115 は測ってみると 2 つに分かれた**。

**症状 A — カーソルの絵が閉じた手のまま**: Playwright で両エンジンの pane を測ったところ,
初期 / ダブルクリック直後 / **ノード作成直後** / 300ms 後 / パン直後 のいずれでも
`react-flow__pane draggable` (computed `cursor: grab`) で, **`dragging` クラスは一度も残らない**。
Chromium と完全に同じである。つまり**アプリにも React Flow にも状態の壊れは無く**,
壊れているのは WebKit が描いているカーソルの絵だけである。WebKit はカーソルをポインタ移動の
契機で更新するので, トラックパッドで指を離すと移動が起きず古い絵が残る。
**報告の「マウスなら問題なし」と整合する** (マウスは微小な移動が必ず入る)。

**症状 B — ノードがカーソルに付いてくる** (2026-08-13 にユーザーから追加報告): markdown ノードを
作り, テキストを入れ, **確定のためにノードの外をクリックすると, そのままノードがカーソルに
ついて移動する**。Chrome では起きない。**こちらもトラックパッドでのみ起こる。**
絵の問題ではなく**ドラッグ状態が終わっていない**ということなので, 症状 A とは別種である
(D4 の区分では「操作が成立しない」= 直す側)。

**症状 B は合成イベントでは再現しなかった。** Playwright WebKit で同じ手順
(ノード作成 → ダブルクリックで `textarea` → 入力 → 外をクリックで確定) を踏み,
**手順が成立していること自体も確認した上で** (確定後の `innerText` に入力文字が入る),
ボタンを押さずにカーソルを動かしてもノードの `transform` は 1px も動かなかった。
Chromium も同じである。

**→ 症状 B の観測には実 Safari + トラックパッドが要る。** 報告自体が「trackpad の場合」と
言っており, Playwright のマウスは必ず正しい `pointerup` を送るので**構造的に再現しない**。
この種の落とし穴は本リポジトリで前例がある (画像 D&D の検証で合成 `DragEvent` の
当たり判定に嵌った — `../reports/review_2026-08-11_ana116-image.md` §9 N2)。

### 2.4 分かっていないこと

- **#51 以外の壊れ方**。Safari で通しの操作 (ノード編集・グループ化・ブランチ・同期・画像) を
  した記録が無い。同じ「縮む前提が無い」パターンが他の行にもあるかは未調査
- **Cmd+V (`navigator.clipboard.read`)**。Phase 8a で「function として存在することだけ確認,
  実挙動は未検証」のまま持ち越されている。WebKit ビルド上では API は生えているが,
  **権限とユーザー操作の要件は実 Safari でしか確かめられない** (§3)
- **Firefox**。課題タイトルは "non-chrome" だが, 報告されているのは Safari だけである (§8 Q1)

## 3. 検証手段 — 誰が何を確かめるか

WebKit には忠実度の違う 3 つの器がある。**取り違えると「直したのに直っていない」が起きる**ので,
何をどれで確かめるかを先に決める。

| 器 | 何ができるか | 忠実度 | 誰が回すか |
|---|---|---|---|
| **Playwright WebKit** | レイアウト・DOM・イベント・スクリプト。**自動で何度でも** | WebKit のビルドだが Apple の Safari とは別物。**UI シェル・権限・ネイティブ連携は別** | **エージェント** |
| **実 Safari** | 実際の権限ダイアログ・クリップボード・ファイル選択・描画 | 使い込みの本番。WKWebView の代理 (Phase 8a S4) | **ユーザー** |
| **Tauri (WKWebView)** | 配布形態そのもの | 本番 | Phase 8 で |

**方針: 機械判定できるものは Playwright WebKit へ, できないものだけ実 Safari のチェックリストへ。**
#51 のような**レイアウトの壊れは前者で完全に判定できる** (§2.1 の実測がその証拠) ので,
人間の目視に頼らず**回帰テストとして固定する**。

> Playwright と `webkit` ブラウザは**既に入っている** (`@playwright/test` 1.62.1,
> `playwright.config.ts` に webkit プロジェクトあり)。ただし `tests/example.spec.ts` は
> 雛形のまま (playwright.dev を開くだけ) で, **E2E は 1 本も書かれていない**。
> `bunfig.toml` は `tests/` を bun のテストランナーから除外済なので, 置き場の衝突は無い。

## 4. 設計方針

### D1: 直し方は「Safari 対応」ではなく「縮む前提を書く」

`min-width: 0` を足すのが最小の修正だが, **同じ罠が他の flex 行にもあるなら個別に直すのは
また同じ穴に落ちる**。次の順で決める。

1. まず `Sidebar.tsx` のヘッダ行を直す (`min-width: 0` を入力欄に与える)
2. **同じ形 (`flex: 1` を持つ入力欄) が他にもあるか** を grep で洗い, まとめて同じ形にする
3. エンジン分岐 (`navigator.userAgent` 判定) は**使わない**。分岐は両方のエンジンで
   別々に腐り, どちらが正しいか分からなくなる

### D2: 洗い出しは「通しスモーク」と「はみ出し検査」の 2 本立て

- **通しスモーク**: 主要導線を WebKit で一通り操作し, **未処理例外とコンソールエラーを 0 にする**。
  step1 が一貫して守ってきた「無言の失敗を作らない」と同じ理由で,
  **画面が正しく見えることを合格条件にしない** (W3d5 では PDS への送信が数週間全滅していたのに
  画面は正常だった)
- **はみ出し検査**: 「この要素はこの器の中に収まっていること」を機械判定する。
  #51 は目視では「ボタンの形が少し違う」程度にしか見えないが, **数値なら 18px はみ出しは一意**である。
  検査対象は当てずっぽうに広げず, **壊れが確認された箇所と, 同じ形をしている箇所**に限る

### D3: 回帰は常設テストで防ぐ

WebKit スモークを `tests/` に常設し, `bun run test:e2e` で回せるようにする。

- dev サーバは Playwright の `webServer` で起動する (手動起動の手順を覚えなくてよい)
- **`DATA_DIR` はスクラッチに向ける** — 利用者の `data/` を E2E が汚さない
- **Chromium も対照として回す** — 「WebKit だけ直して Blink を壊した」を検出するため。
  §2.1 のように**両エンジンの実測値を並べる形**が, そのまま回帰テストの形になる
- CI 搭載は**この課題では決めない** (§8 Q2)。現状 CI は deploy だけで `bun test` すら載っていない

### D4: 何を「対応した」と呼ぶか

**操作が成立しないものを直す。見え方の差は直さない。**

| 区分 | 扱い |
|---|---|
| 押せない・入力できない・落ちる | **直す** (本課題の中身) |
| レイアウトのはみ出し | **直す** (押せなくなる原因になる) |
| テキストのぼやけ・フォントの太さ | **直さない** — エンジン差と判定済 (Phase 8a, ANA-104 Canceled) |
| WKWebView 固有 (カーソル固着など) | **直さない** — ANA-115 Canceled, Tauri は Phase 8 |

### D5: 実 Safari でしか確かめられないものはチェックリストにする

Playwright WebKit で判定**できない**もの:

- **クリップボード** (`navigator.clipboard.read` の権限とユーザー操作要件, Cmd+V の画像貼り付け)
- **ファイル選択ダイアログ** (import は Playwright では `setInputFiles` で迂回してしまう)
- **描画の質**・スクロールの慣性・トラックパッド由来の挙動

これらは `user-test-environment.md` §7 のチェックリストに項目として足し,
**使い込みフェイズの中でユーザーが確認する**。**エージェントは実 Safari を操作できない**
(computer-use はブラウザを read 相当でしか触れない) ので, ここは必ず人間の手が要る。

### 7.1 測った上で見送るもの (2026-08-13, ユーザー確認済)

**「気にしていない」のではなく「測った上で割に合わないと判断した」**ものを, 根拠と再開条件つきで
残す。Phase 8 で蒸し返されたときに同じ調査をしないためである。

#### ANA-104 (文字がボケる) — 見送り

**別物が 2 つ混ざっている可能性が高い。**

1. **エンジン差のラスタライズ** — Phase 8a で実測済 (非 Retina で WebKit の方が柔らかく出る)。
   **不具合ではなく直せない**
2. **レイヤーを古い解像度でラスタライズしたまま `scale()` で引き伸ばす** (+ `translate` の小数で
   サンプリングが滲む) — **直せるが高い**

**見分け方 (安い)**: 開いた直後 (zoom 100%) の文字と, ズームを上げた後の文字を比べる。
ズームに依存しなければ 1 で打つ手なし, ズーム後だけ劣化するなら 2 である。
**S4 のチェックリストに 1 項目として入れる** (実 Safari で数分)。

> **S4 の実測 (2026-08-13): 用意した 2 択のどちらでもなかった。**
> ボケるのは **`textarea` で編集している間がほとんど**で, **画面をクリックする・ノードを
> 触るなど何か操作すると解消する** (ユーザー観測)。つまり **ズーム倍率ではなく編集モードに
> 結び付いており, かつ一過性**である。
>
> これは 2 (古い解像度のレイヤーを引き伸ばす) の一種ではあるが, 引き金がズームではなく
> **編集中に現れる `textarea` の合成レイヤー**である可能性が高い。だとすれば対処も
> 「常時 `will-change`」ではなく「編集の開始/終了でそのノードだけ再ラスタライズさせる」
> という狭いものになりうる。
>
> **それでも見送りは変えない**: 触れば直る一過性の見え方であり, 使い込みを止めない。
> かつ**自動判定できない** (ボケは DOM にもスクリーンショットにも出ない)。
> **再開条件を差し替える**: 「編集中の可読性が実際に困る」と分かったとき。
> そのときは編集の開始/終了に絞った再ラスタライズを 1 箇所だけ試し, 効かなければ即撤回する。

既知の解法 (issue #51 に貼られた記事) は 3 点セットで, うち 2 つが重い:

| 対処 | 我々にとってのコスト |
|---|---|
| `.react-flow__viewport / __node / __edges` に `will-change: transform` を常時 | ノード数だけ合成レイヤーが増える。大きなグラフでメモリを踏む |
| ズーム確定時に `will-change` を `auto` へ落として戻し再ラスタライズ | ライブラリ所有の DOM への命令的操作 + 「確定」の検知が要る |
| パン中の小数 `translate` を MutationObserver で毎フレーム整数に丸める | **最も汚い**。React Flow が書く transform を毎フレーム上書きする。滑らかさと内部状態の不一致リスクがあり, React Flow の更新で壊れる |

**見送りの理由**: 効果が「この非 Retina モニタでどう見えるか」に依存し, テストで固定できず,
ライブラリ更新で壊れる保守負債になる。**再開条件**: 上の切り分けで「ズーム依存」と分かり,
かつ Tauri で日常的に耐えられないと分かったとき。

#### ANA-115 症状 A (カーソルの絵) — 見送り

**トラックパッドでのみ起こり, マウスでは起こらない** (§2.3)。**状態は正しい**ので,
直すなら**再描画を強制する以外に手が無い** — 操作完了時に
`cursor` を一瞬別の値にして戻す, 1px の transform を入れて戻す, といった類である。
実装は数行だが: ライブラリ所有の要素に外から触る / **効いたかを自動で確かめる手段が無い**
(カーソルの絵は DOM にもスクリーンショットにも出ない) / Safari で効いても WKWebView で
効く保証が無い / 意図の伝わらない呪文が 1 つ増える。

**再開条件**: 実 Safari または Tauri の使い込みで日常的に邪魔になったとき。
その場合も**「1 箇所だけ入れて効かなければ即撤回」を前提**にする。

#### ANA-115 症状 B (ノードが付いてくる) — **S4 で観測し, 直した (2026-08-13)**

> **結論**: 観測どおり原因が特定でき, **アプリ側で直せた** (commit `d7dca2e`)。
> 症状は「ノードが付いてくる」ではなく **「掴んだ先 (ノード or キャンバス) が付いてくる」**。
> トラックパッドの**タップでのみ**起き, 押し込んだドラッグでは起きない。
> 詳細と実測値は §9 の S4, および `tests/paneDrag.spec.md` にある。
> 以下は観測を始める前に書いた計画であり, 記録として残す。

これは絵ではなく**ドラッグ状態が終わっていない**ので, D4 の区分では「直す」側である。
ただし合成イベントでは再現しない (§2.3) ので, **S2 のスモークには入れられない**。

**S4 で実 Safari + トラックパッドから観測する。** 診断は **Web インスペクタのコンソールへ
貼るスニペット**で行い, **製品コードには何も入れない** — `pointerdown` / `pointerup` /
`pointercancel` / `lostpointercapture` と, ノードの `transform` の変化を記録し,
**どのイベントが来ていないか**を見る。原因が「特定のイベントが来ない」ことだと分かれば,
そこを埋める修正は呪文にならず, テストも書ける可能性がある。

**ただし §2.3 の前提 (トラックパッドでのみ起こる = OS レベルの疑い) から,
「アプリ側では直せない」が結論になりうる。** その場合も観測自体には意味がある —
**同じマシン・同じ操作でマウスとトラックパッドを比べ, 届くイベント列の差を記録する**ことが,
「アプリの問題ではない」ことの証拠になり, Phase 8 で同じ議論を繰り返さずに済む。

#### Firefox (Gecko) — 対象外

**どの配布形態にも Gecko は出てこない**: macOS/iOS = WebKit, Windows = WebView2 (Blink),
Linux (Tauri) = WebKitGTK, Android = System WebView (Blink)。Gecko が OS の描画エンジンで
あるものは実質存在しない (歴史的な Firefox OS / KaiOS くらいで, 我々の配布形態と無関係)。
つまり Firefox 対応は**「Firefox で見に来る人がいるか」だけの話**であり,
Tauri 配布の前提にはならない。**放置する** (ユーザー判断, 2026-08-13)。
必要になれば Playwright のプロジェクトを 1 行足すだけで回せる。

### S1. #51 の修正 — 完了 (2026-08-13)

**赤くしてから直した。** `tests/sidebarLayout.spec.ts` (+ `.spec.md`) が

**測って分かった訂正**: §2.1 では「WebKit でだけ行が溢れる」と書いたが,

縮まなければギアボタンが押せなくなり #51 と同じ壊れ方になる。

`tests/walkthrough.spec.ts` (+ `.spec.md`) を追加した。**ファイル作成 → ノード作成 →

往復しても編集が残る」といった**状態を跨ぐ壊れ方**が見えない。#51 と同じく
「操作は成功するのに次の操作ができない」形の不具合はそこにしか出ない。

**決めたこと**:

1. **`<img>` が居ることを合格条件にしない。** 参照だけ書けて実体が取れていなくても

### S4. 実 Safari での確認 — 完了 (2026-08-13, ユーザー参加)

D5 のチェックリストを実 Safari + Web インスペクタで通した。**通し操作はすべて動いた**
(ファイル作成 → ノード作成・編集 → Cmd+V の画像貼り付け → 選択中の画像ノードへの貼り付けで
差し替え → export → import)。**#51 の import ボタンも実機で押せる**ことを確認した。

**その上で 3 件を発見し, 3 件とも直した。** どれも Playwright だけでは出なかったものである。

#### (1) ResizeObserver のループ通知でコンソールが埋まる — 直した (`c4bac9b`)

**WebKit のみ**。ノードのサイズ変更ハンドルを掴んで動かすと
`ResizeObserver loop completed with undelivered notifications.` が**未処理例外として**
数百件上がる。Chromium では 0 件 (両エンジンで実測)。

出所は `@xyflow/react` (12.6.4) の中の `ResizeObserver` 2 箇所で, どちらも rAF で
包まれていない。**我々のコードに `ResizeObserver` は 1 つも無く**, 直す場所が無い。
仕様上も非致命である。

**壊れるからではなく, コンソールが読めなくなるから止めた** — コンソールは step1 が
一貫して「無言の失敗」を見つけるために使ってきた道具である (§7.2 / D2)。
「無言の失敗を作らない」への意図的な例外なので, **消す範囲を単体テストで固定した**
(既知の 2 文の前方一致だけ / `ResizeObserver` を含む別のエラーは消さない / 解除できる)。

#### (2) 小数座標で PDS 送信が全部詰まる — 直した (`2f1e6a3`)

**ブラウザ非依存**。import した後, どのファイルで何をしても
`Expected one of null, boolean, integer, ... (got 740.5) at $.record.ops[2].x` が出続ける。

ATProto のデータモデル (DAG-CBOR) に float 型が無く, 小数を含む op を載せた batch は
`putRecord` が 400 で弾く。**outbox は先頭が詰まると以降が全部止まる**ので,
1 つの小数が同期を丸ごと殺していた。

編集経路 (`client/events/toUnified.ts`) は W3d5-7 で丸めていたが, **genesis 側に
もう一つ生成口があり素通しだった**。「`node.setLayout` の唯一の生成口」とコメントに
書いてあるのに 2 つあったのが本質なので, **生成口を shared の `nodeSetLayoutOp` へ
一本化して構造で塞いだ**。

**これは使い込みでしか出ない類である** — 単体テストは丸める側だけを見ており,
E2E は未ログインで走るので remote 送信を通らない。

#### (3) タップで始まったドラッグが終わらない (ANA-115 症状 B) — 直した (`d7dca2e`)

症状は「ノードが付いてくる」ではなく **「掴んだ先が付いてくる」** (ノードのことも
画面全体のこともある)。**トラックパッドのタップでのみ**起き, 押し込んだドラッグでは
起きない。もう一度クリックするまで止まらない。

Web インスペクタで測った事実:

| | 押下 | 移動中 |
|---|---|---|
| 押し込んだドラッグ (正常) | `buttons=1` `pressure=0.5` | `buttons=1` |
| タップ (暴走する) | `buttons=0` `pressure=0` | `buttons=0` |

加えて **WebKit は `mouseup` を `mousedown` より先に配送することがある** (観測ログに
`up` の 2ms 後に `down` が来る列がある)。先に来た解放は誰も待っていないので捨てられ,
後から来た押下で始まったドラッグを**終わらせる解放が残らない**。
React Flow のドラッグは d3-drag で動き, **d3-drag は移動中に `buttons` を見ない**。

対策 `src/client/src/stuckDragGuard.ts`: 移動の `buttons` が 0 なら合成 `mouseup` を
投げて打ち切る。**エンジンで分岐せず, イベントの事実 (押されていない) だけで判定する**。

**§7.1 の見立ては外れていた。** 「トラックパッドでのみ = OS レベル = アプリ側では
直せない」と書いていたが, 実際は **d3-drag が `buttons` を見ないという穴**であり,
WebKit だけがその穴を突く列を配送していた。#51 が「WebKit 固有」ではなく
「両方に在る穴が WebKit で出る」形だったのと同じ構造である。

#### 合成イベントで再現できたもの・できなかったもの

- **(1) と (3) は最終的に Playwright で再現できた** — (3) は `page.mouse` では作れない
  (必ず `buttons=1` になる) ので, **ページの中で `MouseEvent` を組み立て,
  `view: window` を立てて**投げた (d3-drag は `event.view` にリスナを張るため,
  Playwright の `dispatchEvent` では動かない)。**S2 の時点で「合成では再現しない」と
  していたのは, 何を投げればよいかが分かっていなかっただけである**
- **(2) は E2E では出ない** — 未ログインなので remote 送信を通らない

#### ANA-104 (文字がボケる) — 見送りは変えず, 診断を差し替えた

用意した 2 択 (ズーム依存かどうか) のどちらでもなかった。**`textarea` の編集中がほとんどで,
何か操作すると解消する**。§7.1 に追記し, 再開条件を「編集中の可読性が実際に困ったとき」へ
差し替えた。
