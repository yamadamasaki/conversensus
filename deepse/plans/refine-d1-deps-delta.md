## 1. 調べたこと

🔵 = 事実、⚪ = そこからの帰結。

### F1: 2 人の開発環境でも、batch の 3〜4 割が deps

🔵 開発用 PDS の batch レコードを実測した (2026-10-13、読むだけ):

| repo | batch 数 | 1 件の平均 | うち deps | deps の割合 | deps の actor 数 (平均 / 最大) |
| --- | --- | --- | --- | --- | --- |
| alice.test | 71 | 979 B | 399 B | 41% | 6.2 / 9 |
| bob.test | 64 | 914 B | 316 B | 35% | 5.1 / 9 |

🔵 actor は `did:plc:…#端末の UUID` で 1 項目約 65 B。actor は「人 × 端末」で、使われなくなった端末の項目も
vector に残り続ける。

⚪ 前提の規模 (数十人 × 各自 2〜3 端末, 連合の前提) では deps だけで 1 batch あたり数 KB になり、node を 1 つ動かした
batch の大半が deps になる。細い回線の前提と合わない。

### F2: 受け手は File ごとに全レコードを毎回読む

🔵 受信は File ごとに、その File の batch レコードを先頭から全部読む (`listByFile`, Phase 7 p7-2)。既読位置は持たない。

⚪ ある batch の差分の基 (同じ actor の前の batch) は、送られていれば**同じ取得の中にある**。受け手は取得した
レコードだけで全体の deps を復元できる。

### F3: 送り手は送れない batch を飛ばして後を送ることがある

🔵 `pushRemote` は、画像の実体が手元に無い batch を飛ばし、後の batch を送り続ける (`PartialPushError`)。

⚪ 差分の基を「手元の前の batch」にすると、基が PDS に無いまま差分だけが届き、受け手は復元できない。**基は
この端末から実際に送れた batch に限る。**送った実績が無ければ (起動して最初など) 全体を送る。

### F4: 手元の正典は全体の deps を持つ

🔵 因果の判定 (`happenedBefore`・`concurrent`・競合の検出・timeline の切断面) はすべて `batch.deps` を全体として読む。

⚪ 差分は**送受信の境目だけ**にする。手元の正典・畳み込み・判定は全体の deps のままで、変えない。

## 2. 設計

- レコードに `depsBase?: number` を足す。有れば `deps` は「同じ File の、同じ actor の seq = `depsBase` の batch の
  全体の deps」に足す差分。無ければ `deps` は全体 (今までのレコードはすべてこれ)
- **送る** (`atprotoSyncProvider.pushRemote`): File × actor ごとに「この端末が送れた最後の batch の seq と全体の deps」を
  覚える (送れたときに更新)。覚えていれば差分 (`deltaDeps`) と `depsBase` を送り、無ければ全体を送る。覚えは
  プロバイダの中だけに持つ (起動ごとに最初の 1 件は全体になる)
- **受ける** (`toRemoteBatches`): 取得したレコードを actor ごとに seq の順に畳み、`depsBase` を持つものは基の全体に
  差分を足して全体に戻す (`restoreDeps`)。基が取得の中に無ければ、その batch は今回は受けない (数えて警告する)。
  受信は毎回先頭から読むので、基が届けば次の回に受かる
- 差分 = 全体のうち、基の値より大きい項目。deps は actor ごとに減らないので、`join(基, 差分)` で全体に戻る

### 互換

- 今までのレコード (`depsBase` 無し) は全体として読める
- **古い版の受け手は差分を全体として読む** — 知っていることを少なく見積もるので、並行でない編集を並行と見て競合を
  余計に出しうる。データは壊さない。新しい版の知らせ (#262) で揃う

## 4. 記録 (2026-10-13)

### E1・E2

- `client/src/atproto/depsDelta.ts`: `deltaDeps` / `DepsDeltaEncoder` (送れた batch だけを基にする) / `restoreDeps`
- レコードに `depsBase?` を足し (`types.ts`)、受け取るときは自分より前の seq でなければ弾く (`isBatchRecordValue`)
- `AtprotoSyncProvider.pushRemote` が送るときに差分にし、送れたら覚える。`toRemoteBatches` が File ごとに全体へ戻し、
  基が届いていないものは数えて警告し、今回は返さない
- 性質: 「送り手がどこで送れなくても (飛ばしても)、順不同で届いても、届いたものはすべて全体の deps に戻り、戻せないものは
  無い」。App 結合 (偽の PDS を通る) も緑で、端末をまたいだ往復が通る
- ファイル名を引く経路 (`remoteFileName`) と調査の検査 (`remoteBatchChecks`) は deps を使わないので変えていない

### E3 (見積もり)

いまの開発用 PDS のレコードに差分の規則 (File × actor ごとに 1 つ前を基にする) を当てはめた:

| repo | deps (全体) | deps (差分) | 差分に載る actor 数 | 1 batch (今) | 1 batch (差分) |
| --- | --- | --- | --- | --- | --- |
| alice.test | 399 B | 64 B | 0.77 | 979 B | 644 B |
| bob.test | 316 B | 58 B | 0.67 | 914 B | 656 B |

deps は 8 割以上、batch は約 3 割小さくなる。差分に載る actor は平均 1 未満で、規模 (参加者 × 端末) によらない。
実際には起動ごとに File × actor の最初の 1 件が全体になるので、これより少し大きい。

### U2 (actor の退役) について

使われなくなった actor は差分に載らないので、**送る量については退役が要らなくなった**。手元の正典の deps は全体のまま
増え続けるが、手元だけの量で、送受信には効かない。退役は手元の量が問題になったら改めて考える
