## 1. コードを読んで判明した事実

🔵 = コードで確認 / ⚪ = 推論

### F1: オフラインで起動すると、ログアウトした扱いになる

🔵 起動時のセッションの復元 (`oauthAuth.resume`) はネットワークを要る — OAuth の client の読み込み、token の更新、
handle を引く `describeRepo`。オフラインではどれかが失敗し、`resumeSession` は例外を飲んで `null` を返す
(`atproto/client.ts`)。以後その窓は未ログインで動き、actor は `local#<deviceId>` になる。**オンラインに戻っても
復元をやり直さない** (`useAtprotoSession` は起動時に 1 回だけ)。

### F2: 未ログインの batch は送られない

🔵 送信は自分の DID の batch だけを送る (`remoteFilter`, step2 Phase 2 S0 — 受信した他人の batch を自分の repo へ
書き戻さないための柵)。`local#…` の batch は対象外なので、ログインした後もそのまま手元に残る。

### F3: 既存の作りは「`local` の batch はログイン前の自分」とみなしている

🔵 名簿の起点を置く処理 (`bootstrapParticipation` の `isSolelyOwnedBy`) は、`local` の actor の batch を
「自分の端末で自分が作ったもの」として扱う。Folder もログイン前の写しをログインした人へ引き継ぐ (Phase 6 Q5)。
⚪ 帰結: 「出し直す」は既存の考え方の延長であって、新しい規則ではない。

### F4: 写し (`copyOf`) では出し直せない

🔵 畳み込みは「同じ元を指す写しが複数あれば 1 つだけ残す」が、**元と写しが同じ log にあるとき元を落とさない**
(`orderBatches`)。写しは新しい clock で log の末尾に付くので、二重に効くうえ、後から入った他人の編集を古い値で
上書きする (merge の写しが branch の後勝ちになるのと同じ)。
⚪ 帰結: **手元の batch を、位置 (clock) を保ったまま書き換える**。未ログインの batch は一度も送られていない (F2)
ので、手元で書き換えても誰とも食い違わない。

### F5: 同じ端末の `local#X` と `did#X` は、同じ端末 id を使う

🔵 actor は `composeActor(did ?? 'local', deviceId)` で、deviceId は端末 (タブ) ごとに 1 つ。
⚪ 帰結: `local#X` を `did#X` に書き換えると、`did#X` が既に書いた batch と連番 (seq) がぶつかる。
**新しい actor 名 (`did#<新しい id>`) に書き換え、seq はそのまま使う**。`local#X` の seq は 1 から歯抜けなく
振られているので、新しい actor の連番としてもそのまま正しい。他の batch の `deps` にある `local#X` の項目も、
同じ名前に読み替える。

### F6: 書き換えた後は、今の送り直しの経路に乗る

🔵 起動時・`online`・「今すぐ同期」の catch-up は、手元にあって PDS に無い自分の batch を積み直す。
⚪ 帰結: 書き換えれば、送るための新しい経路は要らない。出し直した後に catch-up を 1 回走らせればよい。

## 2. 設計

### L-1: ログインしたら、未ログインの batch を自分の batch に書き換える (利用者の案)

```
adoptLocalBatches(did):
  for each File (branch 用の op-log も含む):
    local actor ごと (local#X, local#Y …) に:
      新しい actor A = did#<新しい uuid>
      その actor の batch の actor を A にする (clock・seq・中身はそのまま)
      その File の全 batch の deps の local#X の項目を A に読み替える
  catch-up を走らせる (F6)
  名簿の起点が無い File には置く (未ログインで作った File, 既存の ensureOwnGenesis)
```

- **保存の中で 1 トランザクションで書き換える** (`EventStore` に操作を 1 つ足す)。途中で止まって半分だけ
  書き換わった log を作らない
- 画面と因果の発番器は、書き換えの後に log から組み直す (再読み込みと同じ経路)

### L-2: オンラインに戻ったら、セッションの復元をやり直す

オフラインで起動した窓は、オンラインに戻ったら `resumeSession` をもう一度呼ぶ。ログインの情報 (token) は
保存されているので、通れば**ログインし直さずに**ログイン済みに戻り、L-1 で出し直される。

### L-3: 届いていない編集があることを見えるようにする

未ログインで `local` の batch があるとき、左下の「この端末にだけ保存」を目立つ形にする (件数と、ログインすると
送られること)。L-1 と L-2 で、ログインさえすれば届くようになるので、知らせるのは「ログインしていない」ことで足りる。

## 5. 実施記録

### L-1a: 保存の中で actor を付け替える (2026-10-05)

`EventStore.renameActor(from, to)` を 1 トランザクションで — batch の actor 列、`deps` の鍵、写しの元 (`copyOf`)、
op の中 (branch のコミットの vector など) の、`from` にちょうど一致する文字列をすべて `to` にする。`to` が既に
batch を持っていれば断る。`listLocalActorBatches` で File と actor ごとに数える。`LocalStore` → `LocalBackend` →
Worker → `api.ts` に通し、別のタブには関わった File を知らせる。

検証: 例 3 件と性質 1 つ (どんな手元の log でも、付け替えの前後で projection が同じ・元の actor がどこにも残らない・
付け替えた actor の連番が 1 から歯抜けなく並ぶ)。

### L-1b: ログインしたら訊いてから出し直す (2026-10-05)

`sync/adoptLocalActors.ts`: 未ログインの batch があれば件数と File 名を見せて訊き (Q1)、承けたら `local` の actor
ごとに新しい自分の actor (`<did>#<新しい uuid>`) へ付け替え、関わった File ごとに catch-up で送る。ログインの後の
手順 (発見 → 名簿の起点 → 参加 File の発見) の**前**に走らせる。断られたら、同じ人のこのセッションの間は訊き直さない
(ログアウトしたら、次のログインでまた訊く)。

**分かったこと**: 断っても **File の起源 (genesis: 名前・最初のシート) は送られる**。genesis は step1 から
「File の起源」としてログインで送っていて、他の端末の発見がそれに乗っている。編集は送られない。File の名前を
含む骨組みが PDS に載ることは、送らない答えの範囲の外になる (直していない)。

検証: 単体 4 件 (`adoptLocalActors`)、App 結合 2 件 (送る → 同じ人の別の端末に届く / 送らない → 編集は載らず手元に
残る)。変異: 出し直しを外すと 2 件とも落ちる。

### L-2: オンラインに戻ったら復元をやり直す (2026-10-05)

- `useAtprotoSession`: 未ログインの間は `online` で `resumeSession` をやり直す。通ればログイン済みに戻り、L-1 へ進む
- `oauthAuth.resume`: **失敗を覚えない**。最初の `init` の Promise と client を `??=` で持っていたので、オフラインで
  失敗するとやり直しても同じ失敗が返っていた。失敗したら client ごと作り直す (`init` は client ごとに 1 回の契約)
- Q4 の「今すぐ同期」の契機は入れていない — そのボタンはログイン中にしか出ない

検証: 単体 3 件 (オフラインで起動 → `online` でログイン済み / ログイン中はやり直さない / 自分でログアウトした後は
ログアウトのまま)。変異: `online` を聞かないと落ちる。**OAuth の経路 (`oauthAuth`) は単体でも App 結合でも見ていない**
(App 結合はパスワードの認証) — 実機で確かめる。

### L-3: この端末にだけある編集を知らせる (2026-10-05)

**それまでの「この端末にだけ保存」の表示は一度も出ていなかった** — `SyncStatusIndicator` の未ログインの分岐は、
サイドバーがログイン中にしか indicator を描かないので届かない。未ログインのときにログインの入口の上へ帯
(`LocalOnlyBanner`) を出す: 「未ログイン: この端末にだけ N 件の編集があります。ログインすると送られます」、押すと
ログイン。件数は `useLocalOnlyCount` が未ログインの間だけ数え、このタブと別のタブの書き込みのたびに数え直す。
起動時の復元が済むまでは数えない (ログイン済みの人に一瞬出さない)。0 件なら出さない。

検証: 単体 3 件 (`LocalOnlyBanner`)、App 結合 (L-1 の件で、ログイン前に帯が件数つきで出る)。
