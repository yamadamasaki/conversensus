# deepse ドキュメントの記号の凡例

`D1` / `S3` / `U2` / `R4` / `N1` のような **英字 + 番号**の識別子が文書中に出てくる。
**頭文字は節の種類を表す**が, どこにも書いていなかったので, ここに集約する
(実際の用例から起こしたものであり, 新しい規約を決めたものではない)。

## 設計・計画書 (`plans/step1-refinement-*.md`)

| 記号 | 節 | 意味 |
|---|---|---|
| **D** | 設計方針 | **Design** — 決めたこと。「なぜそうするか」を伴う |
| **S** | 実装スライス | **Slice** — 実装の単位。`S0` から始まることが多い |
| **U** | 未決事項 | **Undecided** — 実験や実測で決める問い。決まったら「確定: …」を追記する |
| **Q** | 着手前に決めたいこと | **Question** — ユーザーに訊く判断。既定案を添える |
| **N** | 非目標 | **Non-goal** — 節見出しとして使う (番号は付けないことが多い) |

## レビュー記録 (`reports/review_*.md`)

| 記号 | 節 | 意味 |
|---|---|---|
| **R** | 要修正 (correctness) | 直さないと壊れているもの |
| **D** | 要検討 (設計の穴) | **Design** — 直し方に判断が要るもの |
| **Q** | 改善 (quality) | **Quality** — 壊れてはいないが読みにくい・重複しているもの |
| **T** | テストの穴 | **Test** |
| **N** | 対応中に見付かったもの | **New** — レビュー時点には無く, 修正作業の中で新たに見つかった指摘 |

## アーキテクチャ (`architecture/step1.md`)

| 記号 | 意味 |
|---|---|
| **D** | **Decision** — 設計上の決定 (D1 = 配布形態, D7 = 同期カテゴリ など) |
| **O** | **Open** — 未決の問い (O1 = ストレージ実体, O2 = 配布形態) |
| **B** | 配布形態の選択肢 (B1 = Tauri v2, B2 = 軽量 B) |

## フェーズ文書 (`plans/step1-phase*.md`, `plans/step1-w3*.md`)

- **`W3c1` / `p5-4` / `4e-2b`** のような識別子は**フェーズやスライスの名前**であって,
  指摘の分類ではない
- **`C1` / `H2` / `M1` / `L3`** は **critic レビューの指摘**で, 頭文字は**重大度**である
  (**C**ritical / **H**igh / **M**edium / **L**ow)。`【Critical C1】` のように
  見出しに重大度が併記されている

## 同じ字が違う意味になる 2 箇所

**遡って統一はしない** (既存の参照が大量にあり, 番号を振り直すと過去の記録との対応が切れる)。
読むときはどちらの文書かで判断する。

| 字 | 設計・計画書 / アーキテクチャ | レビュー記録 |
|---|---|---|
| **D** | 決めた設計方針・決定 | **要検討 = 設計の穴** (まだ決まっていない) |
| **Q** | ユーザーに訊く **Question** | **Quality** の指摘 |

例: ANA-116 の `D1` は文脈で 2 つある — 設計書の D1 は「blob 正典 + op-log は参照だけ」
(決めたこと), レビュー記録の D1 は「export / import で画像が失われる」(穴) である。

未決を表す字も **U** (計画書) と **O** (アーキテクチャ) に分かれている。
