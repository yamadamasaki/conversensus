# step 2 の要件仕様

step 2 の目標は, 共同作業できるようにすることである. そのためには, 多くのプラットフォームの拡張, ユーザ機能の追加が必要になる. また, step 1 でやり残した個人作業のための機能もいくつか追加したい.

step 2 ではやらないが, step 3 (あるいはそれ以降) で実現したいことの一部も記述しておく. これはアーキテクチャを立案する際にあらかじめ勘案し, もし必要ならばロードマップの変更も考える.

## 完了基準

以下が観測できたら step 2 の完了とする.

- 2 アカウントが同一 File に参加し, 双方の編集が相手のグラフに反映される
- 一方が branch を切って merge し, 競合したときに DtR graph が起動し, 双方の承認で再 merge される
- 一方が参加を取りやめた後, その操作が相手に反映されなくなる

## アカウントを作成する

- 招待コード生成 (admin)
- 招待コードを使ったアカウント作成 (ユーザ自身)

ここでいう「招待コード」は PDS のアカウントを作成するためのものである. File の共同作業に参加するための「参加コード」(→ [participation](./spec/participation.md)) とは別物なので, 混同しないよう名前を分けている.

将来的には UI が必要になるが, step 2 では今と同じ curl を用いたもので良い. その際, アプリケーション内に UI を作るか, PDS 用の管理アプリケーションを用意するかは検討が必要 (→ step 3).

## File に招待する

アカウントを File に招待する. これは, そのアカウントが, その File に対する変更履歴を積み重ねることを意味する.

したがって, 招待した側も招待された側も, その File に対する変更履歴を取り込み, その変更を自分のグラフに反映させることになる.

[participation](./spec/participation.md) を参照

ATProto/PDS での方法としては,

- 手動 (現在の実装)
- 定期的なポーリング (step 2)
- Firehose による streaming (step 3)

がある.

最終的にはリアルタイム同期を File ごとに, あるいは一時的にでも選択できる必要はある (→ step 3) が, まずは定期的なポーリングで良い.

また, step 2 では招待できるアカウントは特定の一つの PDS に属している (step 1 の実装と同じ) ものとする. それ以外のアカウントの招待は無効とする (不特定の PDS に属するアカウントの招待は → step 3).

[merging](./spec/merging.md) を参照

### 設計の視点

- DID ごとの rkey cursor を用いることによって効率化できる
- 上記の三つの同期方法の選択は, 排他的なものとは限らない
- 他のアカウント上にある blob (現時点では画像のみだが) の取り込みの検討が必要. step 2 では step 1 (PDS 内の blob を利用) を踏襲する
